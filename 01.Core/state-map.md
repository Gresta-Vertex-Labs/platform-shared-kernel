## Active Work

Of the eight phases design-locked in the earlier pass, `SK.01.P443` (`SharedKernel.Validation`), `SK.01.P444` (`SharedKernel.Validation.FluentValidation`, depended on the now-shipped P-443), `SK.01.P446` (async `IEncryptionKeyProvider`, breaking), `SK.01.P447` (`SharedKernel.Cryptography.KeyVault.Azure`, depended on the now-shipped P-446), `SK.01.P451` (RFC 6238 TOTP/RFC 4226 HOTP, additive), `SK.01.P474` (`SharedKernel.DataPrivacy`), `SK.01.P482` (`SharedKernel.Localization`), and `SK.01.LoggingRangesNewDomains` (the `Idempotency`/`Scheduling`/`Reporting` domain-base constants) have since shipped end to end. `SK.01.P487` (WO-080 — `IEncryptionKeyProviderProbe`/`EncryptionKeyProviderHealth`, closing the P-449 blocker) has also since shipped, additive to both `SharedKernel.Cryptography` and `SharedKernel.Cryptography.KeyVault.Azure`.

**New this pass (WO-081, a coordinated, `01.Core`-first breaking wave — the foundation six other domains' own planners dispatch against once these ship):** `SK.01.P491` (associated-data/AAD on `ISymmetricEncryptionService`, breaking), `SK.01.P492` (a synchronous-provider capability gate replacing the silent sync-bridge blocking hazard, reused again by P-493), `SK.01.P493` (async `IAsymmetricKeyProvider`/`IAsymmetricSignatureService` + a key-disposal-ownership fix + `Verify`/`Sign` minimum-key-size parity, breaking, depends on P-492), `SK.01.P494` (Azure Key Vault Keys remote-signing `IAsymmetricKeyProvider` implementation, depends on P-493), `SK.01.P495` (a new package, `SharedKernel.Cryptography.Argon2`), and `SK.01.P496` (Azure Key Vault provider hardening — connection reuse, compact rotating key identifiers, a real rotation story — depends on P-494). All six were design-locked in that pass (every `D-*` task `●`); `SK.01.P491` (7/7), `SK.01.P492` (9/9), and `SK.01.P493` (12/12) have since shipped end to end — the remaining three's `S-*`/`C-*`/`T-*`/`DO-*`/`P-*` implementation tasks remain `○`, mirroring the WO-067/068/069/076/078 "lock design ahead of implementation" precedent. P-491's own acceptance criteria required inventorying every production `ISymmetricEncryptionService` call site across `02.Caching`/`06.Persistence`/`07.Messaging`/`15.Integration`/`17.Workflows`/`16.Testing` — that inventory is recorded in P-491's own phase notes below; the per-domain fix itself ships as those domains' own WO-081 phases (P-497–P-502), out of this file's jurisdiction. See Overall Progress for per-phase task counts.

## Phase: P-236 — Reflection-Free Failure-Factory Contract for Generic `Result<T>` Construction <!-- phase-key: SK.01.P236 -->

> Additive extension to `SharedKernel.Primitives`: adds a self-referential (CRTP) contract, `IFailureFactory<TSelf>`, built on a C# static abstract interface member, so a caller who knows only an open generic `TResponse` — never the inner `T` — can construct a failure `Result<T>` via a `where TResponse : IFailureFactory<TResponse>` compile-time constraint and a direct `TResponse.Failure(error)` call. `Result<T>` implements `IFailureFactory<Result<T>>` through its existing `Failure(Error error)` static factory (P-001/C-01) — no new member is added to `Result<T>`, no existing signature changes.
> Motivation: `05.Application.Behaviors`'s `FailureResponseFactory`/`ResultOfTDispatcher<TResponse>` was supposed to become reflection-free once `IResultOfT<T>` (P-230) shipped — P-232's acceptance criteria claimed exactly that. ## Phase: P-292 — Result Exception-Boundary and Error-Aggregation Railway Extensions <!-- phase-key: SK.01.P292 -->

> Additive extension to `SharedKernel.Core`'s existing `Result<T>` railway-extension surface (`Map`/`MapError`/`Bind`/`Match`/`Tap`): two new static classes, `ResultTry` (exception-boundary wrapping — sync `Try` and async `TryAsync`, converting any thrown exception, including a flattened `AggregateException`, into `Result<T>.Failure(Error.Unexpected(...))` rather than letting it propagate) and `ResultCombine` (`Combine` overloads for `params Result[]`/`IEnumerable<Result>` and a generic value-collecting `Result<T>` variant, folding a batch of independent outcomes into a single aggregate success or a `ValidationResult`/`ValidationResult<IReadOnlyList<T>>` carrying every collected `Error`, never short-circuiting on the first failure). > Motivation: every domain in the platform standardizes on `Result<T>`, but two everyday patterns still push developers toward hand-rolled code — wrapping a throwing third-party/BCL call, and combining several independent validation checks into one aggregate outcome. > Pure additive — no change to `Result<T>`, `Result`, `ValidationResult`, `ValidationResult<T>`, `IHasSuccessFlag`, `IResultOfT<T>`, or `IFailureFactory<TSelf>`. No new NuGet dependency.

## Phase: P-293 — Sequential Identifier Generation Primitive <!-- phase-key: SK.01.P293 -->

> New `SharedKernel.Primitives` abstraction: `IIdGenerator` (`NewId() → Guid`) with a default sealed implementation, `UuidV7IdGenerator`, backed by `Guid.CreateVersion7()` (RFC 9562 UUID version 7) instead of the fully-random `Guid.NewGuid()` (UUID v4) that aggregate factories and other identifier call sites use today. Zero third-party dependency — pure BCL.
> Motivation: the platform is Postgres-first, and a fully-random v4 GUID as a clustered/primary-key index value is a well-documented Postgres/SQL Server performance anti-pattern (random B-tree insert points → page splits and fragmentation at scale). UUID v7 embeds a millisecond timestamp in its high bits, so values generated close together sort close together, restoring sequential-insert locality while keeping distributed, no-central-coordinator generation. Purely additive and opt-in — no existing identifier call site is forced to change.
> Ships with **no package-owned DI extension method** — `SharedKernel.Primitives` never references `Microsoft.Extensions.DependencyInjection.Abstractions` (zero-NuGet-dependency rule) and ships no DI extensions at all (existing rule, mirrors `IClock`). A consuming service registers `IIdGenerator` with a plain `services.AddSingleton<IIdGenerator, UuidV7IdGenerator>()` call at its own composition root — this is this phase's deliberate, jurisdiction-preserving reading of the "DI registration extension" requirement.
> Cross-referencing `03.Domain`'s `IAggregateFactory` guidance to mention this option is explicitly **out of `01.Core`'s jurisdiction** — flagged here for a future `domain-arch-planner` follow-up phase, not tracked as a task in this file. `03.Domain/CLAUDE.md` and `IAggregateFactory`'s own shipped contract are unchanged by this phase.

## Phase: P-446 — Async-Capable `IEncryptionKeyProvider` + Envelope Encryption + Key-Caching Seam (BREAKING) <!-- phase-key: SK.01.P446 -->

> **Source correction carried forward from the WO-068 dispatch input:** `IEncryptionKeyProvider` already lives in `01.Core/SharedKernel.Cryptography/Symmetric/IEncryptionKeyProvider.cs` — it is not being extracted from `06.Persistence.EfCore`, it is already the shared seam `06.Persistence.EfCore`, `15.Integration.Webhooks`, `16.Testing`, and `17.Workflows.Temporal` all consume. The real, narrow gap: `GetCurrentKey()`/`GetKey(string)` are synchronous, structurally incompatible with a genuine network-bound KMS/HSM call (Azure Key Vault, AWS KMS, HashiCorp Vault) without a blocking-on-async anti-pattern.
> **Breaking change to `IEncryptionKeyProvider`:** its two members become `GetCurrentKeyAsync(CancellationToken ct = default) → ValueTask<CryptographicKey>` and `GetKeyAsync(string keyId, CancellationToken ct = default) → ValueTask<CryptographicKey?>` — the synchronous members are removed outright, not kept as an additive overload (a KMS-backed implementer must not be allowed to silently offer a synchronous, thread-blocking path). Every implementer must migrate.
> **`ISymmetricEncryptionService` gets new async overloads, additively** (`EncryptAsync`/`DecryptAsync`/`EncryptToStringAsync`/`DecryptToStringAsync`, all `CancellationToken`-aware). The existing synchronous `Encrypt`/`Decrypt`/`EncryptToString`/`DecryptToString` members are **retained**, not removed, and internally bridge to the now-async key provider via `.GetAwaiter().GetResult()` on the returned `ValueTask` — safe and genuinely non-blocking when the registered `IEncryptionKeyProvider` resolves synchronously (the config-based default, and `CachedEncryptionKeyProvider` on a cache hit), but a real thread-blocking call when a registered provider is genuinely network-bound (a raw KMS call on a cache miss). XML docs on the sync overloads must say this in capitals and direct hot-path/high-throughput callers to the new `*Async` overloads instead. This resolves the ripple that a fully-async `ISymmetricEncryptionService` would otherwise force onto five downstream domains (`02.Caching`, `06.Persistence`, `07.Messaging`, `15.Integration`, `17.Workflows`) — most acutely `06.Persistence`'s EF Core `ValueConverter` pipeline, which is **structurally synchronous-only** and cannot be made to await anything; that specific problem is `06.Persistence`'s own follow-on phase (P-448, out of this domain's jurisdiction), not solved here, but this design decision is what keeps it solvable there at all rather than forcing a platform-wide breaking cascade from this one phase.
> **New additive envelope-encryption contract**, `IEnvelopeEncryptionProvider` (`GenerateDataKeyAsync` — ask the KMS-held master key to generate+wrap a fresh symmetric data key, returning both the plaintext data key for immediate local use and its wrapped form safe to persist; `UnwrapDataKeyAsync` — ask the KMS to unwrap a previously-wrapped data key by master-key id, so master key material never leaves the KMS boundary) — distinct from and non-breaking to `IEncryptionKeyProvider`'s direct-retrieval consumers. A provider (e.g. P-447's Azure Key Vault one) may implement both interfaces.
> **New additive caching decorator**, `CachedEncryptionKeyProvider` (wraps any `IEncryptionKeyProvider`, bounded-TTL, `TimeProvider`-driven, single-flight-per-key refresh to avoid a cache-stampede thundering herd on expiry — never a stale-serve-while-revalidating pattern; an expired entry always re-fetches from the inner provider before any caller proceeds). Ships with **no package-owned DI extension** (mirrors the `IIdGenerator`/`SystemClock(TimeProvider)` precedent) — a consuming service composes it explicitly: `services.AddSingleton<IEncryptionKeyProvider>(sp => new CachedEncryptionKeyProvider(new MyKmsProvider(...), TimeProvider.System, ttl))`.

## Phase: P-447 — New Package: `SharedKernel.Cryptography.KeyVault.Azure` — Azure Key Vault Keys Provider <!-- phase-key: SK.01.P447 -->

> A new, **tenth `01.Core` package**, `SharedKernel.Cryptography.KeyVault.Azure`, implementing the now-async `IEncryptionKeyProvider` and the new `IEnvelopeEncryptionProvider` (P-446) against Azure Key Vault Keys (`Azure.Security.KeyVault.Keys` + `Azure.Identity` for credential resolution). A genuine vendor-SDK package, kept out of the zero-third-party-dependency `SharedKernel.Cryptography` core — the same reasoning that puts `SharedKernel.Storage.S3`/`.Obs` in their own packages rather than inside a dependency-free abstractions core, and explicitly **not** the same case as WO-034's declined RSA/ECDSA split (that was one BCL provider selectable by keyed DI; this is a genuine external vendor system reached over the network).
> **Design resolution for "implements both envelope-wrap and direct-retrieval modes" (a real tension, recorded honestly rather than glossed over):** Azure Key Vault Keys does not export raw HSM-protected key material by default — the vendor-idiomatic operation is `CryptographyClient.WrapKeyAsync`/`UnwrapKeyAsync` (RSA-OAEP or AES-KW depending on key type), which is exactly `IEnvelopeEncryptionProvider`'s shape. `AzureKeyVaultEncryptionKeyProvider`'s `IEncryptionKeyProvider` (direct-retrieval) implementation is therefore built **on top of** its own `IEnvelopeEncryptionProvider` implementation internally, not as two independent code paths: `GetCurrentKeyAsync` generates (or returns a process-lifetime-cached) local AES-256 data key via `GenerateDataKeyAsync`, exposing only the already-in-memory plaintext data key as `CryptographicKey.Material` — the vault's own master key material never crosses the process boundary either way. This satisfies the letter of "implements both modes" via one coherent internal mechanism rather than a second, parallel raw-export code path that Azure Key Vault Keys does not sanely support in the general (HSM-backed) case. This resolution is recorded here as a design decision, not left implicit for the implementer to improvise.
> **Fail-closed**: any Azure SDK exception (unreachable vault, `RequestFailedException` for permission/auth failure) during `GetCurrentKeyAsync`/`GetKeyAsync`/`GenerateDataKeyAsync`/`UnwrapDataKeyAsync` propagates directly — no silent fallback, matching P-446's structural fail-closed contract exactly.
> **Composes with, never duplicates, P-446's caching decorator**: this package ships zero caching of its own — a consuming service wraps `AzureKeyVaultEncryptionKeyProvider` in `CachedEncryptionKeyProvider` explicitly if it wants bounded-TTL caching, avoiding two independent caches with different TTL semantics colliding.
> **Depends on P-446** — cannot be implemented before the async `IEncryptionKeyProvider`/`IEnvelopeEncryptionProvider` contracts exist.
> Distinct from `13.ServiceDefaults`'s existing `AddSharedKernelKeyVaultConfiguration()` (P-398) — that wires Azure Key Vault as an `IConfiguration` source; this is a key-management contract implementation. The two are unrelated and never reference each other.
> Design-locked in this pass (D-53, marked `●`); Scaffold/Core/Tests/Docs/Published (S-22, C-66/C-67, T-54, DO-28, P-24→P-26) remain `○` pending a future implementation pass.

## Phase: P-451 — RFC 6238 TOTP / RFC 4226 HOTP Generation, Verification, and Replay Guard <!-- phase-key: SK.01.P451 -->

> An additive extension to the existing `SharedKernel.Cryptography` package (no new package — a pure cryptographic primitive with no identity-stack dependency, the same reasoning that already keeps password hashing and AES-GCM here rather than in `12.Security`). Adds: `Base32` codec (RFC 4648, unpadded — the encoding authenticator apps expect); `IHotpGenerator`/`HotpGenerator` (RFC 4226 core — HMAC-SHA1 default per the RFC, SHA-256/SHA-512 opt-in per common TOTP-era extensions, dynamic truncation per RFC 4226 §5.3); `ITotpGenerator`/`TotpGenerator` (RFC 6238 — composes `IHotpGenerator` internally with a time-derived counter, `IClock`-sourced "now" when no explicit timestamp is supplied — never `DateTime.UtcNow`); a provisioning-URI builder producing the `otpauth://totp/...` Key Uri Format authenticator apps consume for enrollment; `ITotpReplayGuard` (pluggable, mirrors `12.Security.Oidc`'s DPoP replay-check seam — implemented by the consuming service, never a direct `02.Caching` reference from this package) plus `TotpVerifier` (the orchestration type composing `ITotpGenerator.ValidateCode` + `ITotpReplayGuard` so a valid code cannot be accepted twice inside its validity window); and `RecoveryCodeGenerator` (backup codes via `ISecureRandomGenerator` — this type only generates plaintext codes shown once to the user; hashing them at rest via the existing `IOneWayHasher` before persistence is the consuming service's job, exactly like any other secret).
> A repo-wide grep confirmed zero existing TOTP/HOTP/OTP matches anywhere on the platform. `12.Security` shipped the surface to *read and gate on* a second-factor signal in WO-058/WO-062 (`IUserContext.AuthenticationMethods`/`.AuthTime`/`WasAuthenticatedWith`, `[RequireFreshAuthentication]`/`[RequireAuthenticationMethod]`) but nothing can actually *perform* one — this phase closes that half. The replay guard must live alongside the generator/verifier in the same package, never split out, because `TotpVerifier` needs it internally to reject a reused code — splitting it into a separate package would create a circular dependency between the two halves.
> `ITotpGenerator.ValidateCode` itself stays pure/stateless (no replay awareness) — replay protection is composed one layer up in `TotpVerifier`, keeping the generator honest as a testable, side-effect-free RFC implementation and the replay-guard orchestration a separate, independently swappable concern.
> Design-locked in this pass (D-54→D-57, marked `●`); Core/Tests/Docs (C-68→C-72, T-55→T-57, DO-29) and the additive repack (P-27) remain `○` pending a future implementation pass.

## Phase: P-492 — Core: Gate Synchronous `Encrypt`/`Decrypt` Behind a Synchronous-Provider Capability <!-- phase-key: SK.01.P492 -->

> A capability marker, `ISynchronousEncryptionKeyProvider : IEncryptionKeyProvider` (zero-member marker interface), implemented only by a provider that can genuinely guarantee `GetCurrentKeyAsync`/`GetKeyAsync` never perform a blocking network/IPC round trip — the config/environment-backed default. A new static class, `EncryptionKeyProviderCapabilities`, exposes `IsGenuinelySynchronous(IEncryptionKeyProvider provider) → bool`. The four retained synchronous `ISymmetricEncryptionService` members (`Encrypt`/`Decrypt`/`EncryptToString`/`DecryptToString`) compute this check **once**, at `AesGcmEncryptionService` construction time (cached as a private `bool` field — the registered provider instance is immutable for the service's lifetime), and throw a clear, structural `NotSupportedException` directing the caller to the `*Async` overloads when the check is false, instead of silently bridging via `.GetAwaiter().GetResult()`. Behavior is byte-for-byte unchanged when the registered provider genuinely is synchronous (zero behavior change for the common config-backed case).
> **`CachedEncryptionKeyProvider`'s relationship to the marker, decided explicitly (the phase's own named acceptance criterion):** `CachedEncryptionKeyProvider` itself **never** directly implements `ISynchronousEncryptionKeyProvider` — its own true synchronous-safety is entirely a function of what it wraps (a cache *hit* is always fast regardless of the inner provider, but a cache *miss* re-enters the inner provider, and if that inner provider genuinely blocks on network I/O, so does the decorator on that path). `CachedEncryptionKeyProvider` gains a new public read-only `Inner → IEncryptionKeyProvider` property exposing the wrapped instance specifically so `EncryptionKeyProviderCapabilities.IsGenuinelySynchronous` can see through the decorator: it returns `true` when the provider implements `ISynchronousEncryptionKeyProvider` directly, **or** when the provider is a `CachedEncryptionKeyProvider` whose `.Inner` also (recursively) satisfies this same check — `false` for every other case, including any unrecognized third-party decorator type (the check fails toward requiring the `*Async` overloads, never toward silently blocking). This is the resolution to "the check must reflect the INNER provider's true nature, never the decorator's best-case behavior": naively treating `CachedEncryptionKeyProvider` as always-fast because it caches would be exactly that forbidden decorator's-best-case assumption.
> A hand-rolled KMS-backed `IEncryptionKeyProvider` implementer must never implement `ISynchronousEncryptionKeyProvider` unless its author can genuinely assert synchronous safety — this marker is opt-in, never inferred.
> This same gating pattern (a capability marker + a static `IsGenuinelySynchronous` helper) is reused again by P-493 for `IAsymmetricSignatureService`'s own retained sync `Sign`/`Verify`, with its own analogous marker (`ISynchronousAsymmetricKeyProvider`) — "reused" means the architectural pattern, not literally this same interface, since `IAsymmetricKeyProvider` is an unrelated contract from `IEncryptionKeyProvider`.

## Phase: P-496 — Core: Azure Key Vault Provider Hardening — Connection Reuse, Compact Key Identifiers, a Real Rotation Story <!-- phase-key: SK.01.P496 -->

> Three related redesigns to the already-shipped `AzureKeyVaultEncryptionKeyProvider`:
> **(1) Connection reuse** — a single, shared `CryptographyClient` per master key (a `ConcurrentDictionary<string, CryptographyClient>` keyed by Azure key name, created at most once, reused for every subsequent wrap/unwrap/GetKey call), never constructed per call — restores HTTP connection pooling. Mirrors `AzureKeyVaultAsymmetricKeyProvider`'s own cache, which P-494 already baked in from its first implementation specifically to avoid repeating this defect twice.
> **(2) Compact, durable, rotating key identifiers, with a corrected design assumption from the original P-447 shipment** — `CryptographicKey.Id` becomes a short opaque version tag (`"v1"`, `"v2"`, …) instead of the previous self-decodable ~470-byte envelope. This surfaces and fixes a real, previously-undocumented gap: today's "process-lifetime cached current data key" behavior means **every process/pod/replica silently mints its own unique local AES-256 data key** on first use, with no genuine rotation intent behind it and no sharing across replicas of the same service — "current key" was never actually a shared, stable concept, just a per-process accident. P-496 replaces this with a **durable, Key-Vault-Secrets-backed version registry**: a new `Azure.Security.KeyVault.Secrets` client (confined to this package — a second Azure SDK family alongside the existing `Azure.Security.KeyVault.Keys`) stores each version's wrapped-DEK bytes + originating Azure master-key id as a Key Vault secret named by its short tag, plus a single `"current version"` pointer secret every replica reads, so "current" becomes a genuinely shared, deliberately-minted concept rather than a per-process accident. A `ConcurrentDictionary<string, byte[]>` memoizes a version tag's already-unwrapped plaintext data key for the remainder of the process's lifetime once resolved once — a second decrypt citing an already-seen tag costs zero further Key Vault calls (`GetKeyAsync`'s own stated acceptance criterion).
> **Backward-read compatibility, a deliberate design choice avoiding a forced data migration:** `GetKeyAsync` first attempts the new short-tag registry lookup; if the supplied `keyId` does not match the new tag format (e.g. does not match a `"v{N}"`-shaped pattern), it falls back to the **legacy self-decodable envelope parsing path** the original P-447 shipment used, so any already-persisted row encrypted under the pre-P-496 shape remains decryptable indefinitely with no forced migration. `GetCurrentKeyAsync` (used only for new encryption going forward) always mints/returns the new short-tag shape. Because reads stay backward-compatible and no public member's signature changes (`CryptographicKey.Id` is still just `string`), **this phase ships as an additive/MINOR repack, not a breaking one** — a deliberate design choice, not an oversight; the alternative (a breaking repack mandating a data migration for every service with existing encrypted rows) was considered and rejected.
> **(3) A real, explicitly-callable rotation story** — a new public method, `AzureKeyVaultEncryptionKeyProvider.MintNewVersionAsync(CancellationToken ct = default) → ValueTask<string>` (returns the new version tag; **not** part of `IEncryptionKeyProvider`/`IEnvelopeEncryptionProvider` — a provider-specific operational surface, mirroring `06.Persistence`'s `IEncryptionRotationJob` precedent of leaving scheduling to the caller). Generates a fresh local AES-256 data key, wraps it via the master key, stores it as a new version secret, and atomically repoints the `"current version"` secret to the new tag; every previously-minted version's secret is left untouched and remains resolvable via `GetKeyAsync(oldTag)` indefinitely. Automatic/policy-driven rotation scheduling is deliberately out of scope — callable only, from an ops script, a hosted job, or a future `19.Scheduling` job, mirroring how `SharedKernel.DataPrivacy`'s cross-service erasure orchestrator was left out of P-474.
> **`EnvelopeDataKey.MasterKeyId` simplification (envelope-wrap path, distinct from the direct-retrieval path above)** — since `UnwrapDataKeyAsync`'s caller already supplies the actual `WrappedKey` bytes directly (never round-tripped through this provider's own durable store), `MasterKeyId` never needed the oversized self-decodable envelope shape at all; it becomes the real (short) Azure key name + version identifier. This requires no new durable registry — unlike the direct-retrieval path, the envelope path's *caller* is already the durable store for the wrapped bytes.
> **`CachedEncryptionKeyProvider`'s working set is now genuinely bounded** — documented explicitly: every replica resolving `"current"` down to the same shared, deliberately-minted tag (rather than one unique tag per process restart) is what actually bounds a wrapping `CachedEncryptionKeyProvider`'s dictionary by live-key-version count (a small, deliberate, ops-driven number) instead of by pod-restart count (unbounded over a service's whole operational history).
