## Phase: P-293 — Sequential Identifier Generation Primitive <!-- phase-key: SK.01.P293 -->

> New `SharedKernel.Primitives` abstraction: `IIdGenerator` (`NewId() → Guid`) with a default sealed implementation, `UuidV7IdGenerator`, backed by `Guid.CreateVersion7()` (RFC 9562 UUID version 7) instead of the fully-random `Guid.NewGuid()` (UUID v4) that aggregate factories and other identifier call sites use today. ## Phase: P-446 — Async-Capable `IEncryptionKeyProvider` + Envelope Encryption + Key-Caching Seam (BREAKING) <!-- phase-key: SK.01.P446 -->

> **Source correction carried forward from the WO-068 dispatch input:** `IEncryptionKeyProvider` already lives in `01.Core/SharedKernel.Cryptography/Symmetric/IEncryptionKeyProvider.cs` — it is not being extracted from `06.Persistence.EfCore`, it is already the shared seam `06.Persistence.EfCore`, `15.Integration.Webhooks`, `16.Testing`, and `17.Workflows.Temporal` all consume. The real, narrow gap: `GetCurrentKey()`/`GetKey(string)` are synchronous, structurally incompatible with a genuine network-bound KMS/HSM call (Azure Key Vault, AWS KMS, HashiCorp Vault) without a blocking-on-async anti-pattern.
> **Breaking change to `IEncryptionKeyProvider`:** its two members become `GetCurrentKeyAsync(CancellationToken ct = default) → ValueTask<CryptographicKey>` and `GetKeyAsync(string keyId, CancellationToken ct = default) → ValueTask<CryptographicKey?>` — the synchronous members are removed outright, not kept as an additive overload (a KMS-backed implementer must not be allowed to silently offer a synchronous, thread-blocking path). Every implementer must migrate.
> **`ISymmetricEncryptionService` gets new async overloads, additively** (`EncryptAsync`/`DecryptAsync`/`EncryptToStringAsync`/`DecryptToStringAsync`, all `CancellationToken`-aware). The existing synchronous `Encrypt`/`Decrypt`/`EncryptToString`/`DecryptToString` members are **retained**, not removed, and internally bridge to the now-async key provider via `.GetAwaiter().GetResult()` on the returned `ValueTask` — safe and genuinely non-blocking when the registered `IEncryptionKeyProvider` resolves synchronously (the config-based default, and `CachedEncryptionKeyProvider` on a cache hit), but a real thread-blocking call when a registered provider is genuinely network-bound (a raw KMS call on a cache miss). XML docs on the sync overloads must say this in capitals and direct hot-path/high-throughput callers to the new `*Async` overloads instead. This resolves the ripple that a fully-async `ISymmetricEncryptionService` would otherwise force onto five downstream domains (`02.Caching`, `06.Persistence`, `07.Messaging`, `15.Integration`, `17.Workflows`) — most acutely `06.Persistence`'s EF Core `ValueConverter` pipeline, which is **structurally synchronous-only** and cannot be made to await anything; that specific problem is `06.Persistence`'s own follow-on phase (P-448, out of this domain's jurisdiction), not solved here, but this design decision is what keeps it solvable there at all rather than forcing a platform-wide breaking cascade from this one phase.
> **New additive envelope-encryption contract**, `IEnvelopeEncryptionProvider` (`GenerateDataKeyAsync` — ask the KMS-held master key to generate+wrap a fresh symmetric data key, returning both the plaintext data key for immediate local use and its wrapped form safe to persist; `UnwrapDataKeyAsync` — ask the KMS to unwrap a previously-wrapped data key by master-key id, so master key material never leaves the KMS boundary) — distinct from and non-breaking to `IEncryptionKeyProvider`'s direct-retrieval consumers. A provider (e.g. P-447's Azure Key Vault one) may implement both interfaces.
> **New additive caching decorator**, `CachedEncryptionKeyProvider` (wraps any `IEncryptionKeyProvider`, bounded-TTL, `TimeProvider`-driven, single-flight-per-key refresh to avoid a cache-stampede thundering herd on expiry — never a stale-serve-while-revalidating pattern; an expired entry always re-fetches from the inner provider before any caller proceeds). Ships with **no package-owned DI extension** (mirrors the `IIdGenerator`/`SystemClock(TimeProvider)` precedent) — a consuming service composes it explicitly: `services.AddSingleton<IEncryptionKeyProvider>(sp => new CachedEncryptionKeyProvider(new MyKmsProvider(...), TimeProvider.System, ttl))`.
> **Fail-closed is structural, not a documented convention**: an unreachable KMS during `GetCurrentKeyAsync`/`GetKeyAsync` (whether called directly, through `EncryptAsync`/`DecryptAsync`, or through the sync bridge) propagates as a thrown exception — this contract does not adopt `Result<T>` (unchanged from today's shape) and there is no code path that silently proceeds with a placeholder/no-op key. `CachedEncryptionKeyProvider` never serves an entry past its TTL bound under any condition, including a concurrent inner-provider failure during refresh — a failed refresh propagates the exception to every caller waiting on that single-flight resolution, it never falls back to the expired cached value.
> **In-jurisdiction migration**: the one `IEncryptionKeyProvider` implementer inside `01.Core`'s own boundary — the test double used by `SharedKernel.Cryptography.Tests` itself — is migrated in this same phase (C-65/T-53). **Out of jurisdiction, flagged for the owning domain's own planner**: `06.Persistence.EfCore`'s `EncryptionOptionsKeyProvider`/`NullEncryptionKeyProvider` migration (06.Persistence's P-448, where the EF Core `ValueConverter` synchronous-pipeline problem is the central design question), `16.Testing`'s `FakeEncryptionKeyProvider` migration (16.Testing's P-450), and `15.Integration.Webhooks`'s own provider usage (15.Integration's own follow-up) are **not** tracked as tasks in this file.
> Design-locked in this pass (D-49→D-52, marked `●`); Core/Tests/Docs (C-62→C-65, T-51→T-53, DO-27) and the breaking repack (P-23) remain `○` pending a future implementation pass.

## Phase: P-447 — New Package: `SharedKernel.Cryptography.KeyVault.Azure` — Azure Key Vault Keys Provider <!-- phase-key: SK.01.P447 -->

> A new, **tenth `01.Core` package**, `SharedKernel.Cryptography.KeyVault.Azure`, implementing the now-async `IEncryptionKeyProvider` and the new `IEnvelopeEncryptionProvider` (P-446) against Azure Key Vault Keys (`Azure.Security.KeyVault.Keys` + `Azure.Identity` for credential resolution). A genuine vendor-SDK package, kept out of the zero-third-party-dependency `SharedKernel.Cryptography` core — the same reasoning that puts `SharedKernel.Storage.S3`/`.Obs` in their own packages rather than inside a dependency-free abstractions core, and explicitly **not** the same case as WO-034's declined RSA/ECDSA split (that was one BCL provider selectable by keyed DI; this is a genuine external vendor system reached over the network).
> **Design resolution for "implements both envelope-wrap and direct-retrieval modes" (a real tension, recorded honestly rather than glossed over):** Azure Key Vault Keys does not export raw HSM-protected key material by default — the vendor-idiomatic operation is `CryptographyClient.WrapKeyAsync`/`UnwrapKeyAsync` (RSA-OAEP or AES-KW depending on key type), which is exactly `IEnvelopeEncryptionProvider`'s shape. `AzureKeyVaultEncryptionKeyProvider`'s `IEncryptionKeyProvider` (direct-retrieval) implementation is therefore built **on top of** its own `IEnvelopeEncryptionProvider` implementation internally, not as two independent code paths: `GetCurrentKeyAsync` generates (or returns a process-lifetime-cached) local AES-256 data key via `GenerateDataKeyAsync`, exposing only the already-in-memory plaintext data key as `CryptographicKey.Material` — the vault's own master key material never crosses the process boundary either way. This satisfies the letter of "implements both modes" via one coherent internal mechanism rather than a second, parallel raw-export code path that Azure Key Vault Keys does not sanely support in the general (HSM-backed) case. This resolution is recorded here as a design decision, not left implicit for the implementer to improvise.
> **Fail-closed**: any Azure SDK exception (unreachable vault, `RequestFailedException` for permission/auth failure) during `GetCurrentKeyAsync`/`GetKeyAsync`/`GenerateDataKeyAsync`/`UnwrapDataKeyAsync` propagates directly — no silent fallback, matching P-446's structural fail-closed contract exactly.
> **Composes with, never duplicates, P-446's caching decorator**: this package ships zero caching of its own — a consuming service wraps `AzureKeyVaultEncryptionKeyProvider` in `CachedEncryptionKeyProvider` explicitly if it wants bounded-TTL caching, avoiding two independent caches with different TTL semantics colliding.

## Phase: P-451 — RFC 6238 TOTP / RFC 4226 HOTP Generation, Verification, and Replay Guard <!-- phase-key: SK.01.P451 -->

> An additive extension to the existing `SharedKernel.Cryptography` package (no new package — a pure cryptographic primitive with no identity-stack dependency, the same reasoning that already keeps password hashing and AES-GCM here rather than in `12.Security`). Adds: `Base32` codec (RFC 4648, unpadded — the encoding authenticator apps expect); `IHotpGenerator`/`HotpGenerator` (RFC 4226 core — HMAC-SHA1 default per the RFC, SHA-256/SHA-512 opt-in per common TOTP-era extensions, dynamic truncation per RFC 4226 §5.3); `ITotpGenerator`/`TotpGenerator` (RFC 6238 — composes `IHotpGenerator` internally with a time-derived counter, `IClock`-sourced "now" when no explicit timestamp is supplied — never `DateTime.UtcNow`); a provisioning-URI builder producing the `otpauth://totp/...` Key Uri Format authenticator apps consume for enrollment; `ITotpReplayGuard` (pluggable, mirrors `12.Security.Oidc`'s DPoP replay-check seam — implemented by the consuming service, never a direct `02.Caching` reference from this package) plus `TotpVerifier` (the orchestration type composing `ITotpGenerator.ValidateCode` + `ITotpReplayGuard` so a valid code cannot be accepted twice inside its validity window); and `RecoveryCodeGenerator` (backup codes via `ISecureRandomGenerator` — this type only generates plaintext codes shown once to the user; hashing them at rest via the existing `IOneWayHasher` before persistence is the consuming service's job, exactly like any other secret).
> A repo-wide grep confirmed zero existing TOTP/HOTP/OTP matches anywhere on the platform. `12.Security` shipped the surface to *read and gate on* a second-factor signal in WO-058/WO-062 (`IUserContext.AuthenticationMethods`/`.AuthTime`/`WasAuthenticatedWith`, `[RequireFreshAuthentication]`/`[RequireAuthenticationMethod]`) but nothing can actually *perform* one — this phase closes that half. The replay guard must live alongside the generator/verifier in the same package, never split out, because `TotpVerifier` needs it internally to reject a reused code — splitting it into a separate package would create a circular dependency between the two halves.
> `ITotpGenerator.ValidateCode` itself stays pure/stateless (no replay awareness) — replay protection is composed one layer up in `TotpVerifier`, keeping the generator honest as a testable, side-effect-free RFC implementation and the replay-guard orchestration a separate, independently swappable concern.
