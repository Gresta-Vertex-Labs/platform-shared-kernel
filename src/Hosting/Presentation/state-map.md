### SK.14.EdgeErrorContext — One error context at the four edges `○`

**Work order:** WO-087 / P-595 · **Depends on:** SK.01.ObservabilityHelpers (P-580: `ActivityFailureExtensions`, `WellKnownTagKeys.ErrorCode`), SK.16.TelemetryCapture (P-581: span/log capture for every test below), SK.13.HostObservabilityFixes (P-594: tags the server span with `correlation.id`/`tenant.id` before `UseExceptionHandler()`, keeps instrumentation `RecordException` off, never applies inbound actor/tenant headers)

Phase 1 of WO-087 for this domain: the four verified defects, nothing structural (that is `SK.14.PresentationConformance`). **Verdict: accept, with two reshapes** (D-01, D-06). What changes:

1. **Failed spans (HTTP, gRPC).** `SharedKernelExceptionHandler` and `GrpcExceptionInterceptor` never touch the ambient server span, so a 500 or `Unavailable` leaves the trace green with no `error.code`. Both now record through P-580's recorder on `Activity.Current` (the ASP.NET Core server span; this domain starts no span and owns no `ActivitySource`). **Reshape (D-01):** the entry says "set status Error" for every handled exception. OpenTelemetry's HTTP and gRPC server conventions leave a server span's status **Unset** for 4xx and for gRPC client-category codes, and marking every validation failure as a failed span would flood error dashboards. So a **server-category** failure (the same set `ErrorPresentation.IsServerError` already uses for logging and redaction: 5xx, gRPC `Unknown`/`Internal`/`DataLoss`/`Unavailable`/`DeadlineExceeded`) gets the full recorder (status `Error`, exception event, `error.type`, `error.code`), while a **client-category** failure gets only the `error.code` tag, so a trace search by code still works. Client closed the request (499, gRPC `Cancelled`): nothing. The switch is one constant in one helper; if `arch-lead` rules that every handled exception fails its span, change that one line.
2. **SignalR.** `HubErrorMessage` carries only `{code}: {message}`; HTTP carries `traceId`/`correlationId` (`ProblemDetailsCustomizer`) and gRPC carries them in `ErrorInfo.Metadata` (`RpcStatusFactory`). A `HubException` delivers exactly one string, so the ids ride a machine-readable trailer (D-05), read back by a new `HubErrorMessage.TryParse` overload; the existing two-argument `TryParse` keeps returning the message without the trailer.
3. **GraphQL.** `SharedKernelErrorFilter` writes `title = error.Message` and `detail = Exception.Message` in every environment, hard-codes status (default 500) and `type`, has no `errorCode`/`traceId`/`correlationId`, does not know `SharedKernelException` or `ValidationException`, and logs nothing. It becomes the GraphQL form of the HTTP exception handler (D-06): same classification, same status from Core's `ErrorTypeStatusCodeMap`, same client message and redaction from `ErrorPresentation`, same field-error grouping, the exception text only in Development, logged once under GraphQL's own sub-block 14400-14499.
4. **One trace-id source.** HTTP, gRPC, SignalR and GraphQL all read the trace id through one Core helper (D-04); the value does not change (`Activity.Current?.Id ?? HttpContext.TraceIdentifier`).

`ErrorTypeStatusCodeMap` and `GrpcStatusCodeMap` already cover `ErrorType.Timeout` (504 / `DeadlineExceeded`) and both are pinned by an exhaustive `Enum.GetValues<ErrorType>` test; confirmed on disk, no mapping change is needed for the persistence 57014 timeout or any Timeout exception. GraphQL is the only edge without a table, and it now takes the Core one.
