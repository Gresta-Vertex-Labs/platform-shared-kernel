### SK.15.IntegrationLeakFixes — Delivery failure hygiene and fan-out isolation `○`

**Work order:** WO-087 / P-596 · **Depends on:** SK.01.ObservabilityHelpers (P-580, `RecordException` on the fault span), SK.16.TelemetryCapture (P-581, the capture helpers every test below uses)

Closes the two Phase 1 defects of the audit in this domain. (1) **Exception text escapes.** `WebhookDispatcher` copies `ex.Message` of a transport failure into `WebhookDeliveryResult.Error`, then logs it as `{Error}` (`DeliveryFailed`) and publishes it as `WebhookDeliveryExhaustedEvent.LastError` on the bus; `SendGridEmailNotificationSender` and `TwilioSmsNotificationSender` do the same into `NotificationDeliveryResult.Error` and their `DeliveryFailed` logs. A `HttpRequestException` message names the subscriber host or the provider endpoint. The SendGrid attachment path also copies `ex.Message` of `IFileStorageFactory.Open` and `Error.Message` of a storage download into the result. None of these paths passes the exception to the logger, so the stack is lost while the text is kept. (2) **Fan-out is not isolated.** `DispatchToSubscriptionAsync` throws for a subscription with no secrets, for a throwing `IWebhookUrlValidator` or `ISymmetricEncryptionService`, and for any non-listed transport exception; inside `DispatchAsync`'s `Task.WhenAll` this discards every sibling's `WebhookDeliveryResult` (their HTTP calls still happen) and surfaces one exception to the caller, which breaks rule 8. Both families keep the `string? Error` result shape in this phase; the `Error`-carrying result is `SK.15.IntegrationConformance`.

**Design.**
- **Fault boundary** in `WebhookDispatcher.DispatchToSubscriptionAsync`, around the delivery steps only (header check, URL validation, encryption, signing, send), after `deliveryId` exists. It catches every exception except an `OperationCanceledException` raised while `ct` is cancelled (caller cancellation propagates and aborts the fan-out; the gate is released by the existing `finally`). A caught fault returns a failed `WebhookDeliveryResult` (the real `DeliveryId`, `Attempts` = what the tracker counted, fixed reason text), logs `DeliveryFaulted` (Error, exception passed), records the exception on the delivery span, and still reaches `NotifyCompletedAsync`, so a ledger observer sees the failure. `SendTestDeliveryAsync` reuses the path (rule 15). A faulted delivery is not exhaustion: no `WebhookDeliveryExhaustedEvent`.
- **Misconfiguration is not a per-subscription fault.** The `EncryptPayload` without `ISymmetricEncryptionService` `InvalidOperationException` moves out of the per-delivery path to the dispatcher constructor (resolution time), so it can never be swallowed by the boundary or thrown mid-fan-out. A subscription whose `Secrets` is empty is one subscription's data defect: a failed result, not an exception.
- **Fixed reasons, no exception text.** An internal `WebhookDeliveryFailureReasons` / provider-local equivalent holds the closed sentence set (endpoint answered non-2xx with the status code number, endpoint unreachable, timed out, rejected by the resilience pipeline, target rejected, header collision, signing secrets missing, delivery faulted, attachments unresolvable). The caught exception travels beside the result (internal `SendOutcome`) to the logging call only; it is never stored in the result or the event. `DeliveryFailed`/`DeliveryExhausted`/`DeliveryFailed` (providers) lose the `{Error}` placeholder and take `Exception? exception` as last parameter (L4); `ExhaustionEventNotPublished` logs the `ErrorCode` only (no `Error.Message`, L5) and takes the exception when the publisher threw.
- **Exhaustion publish isolated.** `PublishExhaustionAsync` gets its own try/catch (rule 12 already says a failed publish never changes the outcome; today only a failed `Result` is handled, a throwing publisher would escape). `WebhookDeliveryExhaustedEvent.LastError` carries the fixed reason.
- **Sub-block.** Webhooks `15000–15099`: `+5 DeliveryFaulted` (Error). Providers add no EventId.

### SK.15.IntegrationConformance — Integration conforms to the observability gold standard `○`

**Work order:** WO-087 / P-613 · **Depends on:** SK.15.IntegrationLeakFixes (P-596), SK.01.ObservabilityHelpers (P-580), SK.16.TelemetryCapture (P-581), SK.13.WildcardTelemetry (P-582), SK.00.ObservabilityReportOnly (P-583)

Applies every applicable rule of root `CLAUDE.md` "Observability, exceptions and error codes" to the four packages. What changes, by rule:
- **C1-C3, results (breaking, intended).** `WebhookDeliveryResult.Error` and `NotificationDeliveryResult.Error` become `Error?` (`SharedKernel.Primitives.Errors.Error`), `null` exactly when `IsSuccess`. Codes are lowercase `integration.{area}.{reason}`; the `notifications.*` prefix is gone. Public code classes: `WebhookErrorCodes` (Webhooks) and `NotificationErrorCodes` (Notifications.Abstractions); the P-613 text names one `IntegrationErrorCodes`, but the two families cannot share a type (rule 21: providers never reference Webhooks and Webhooks never references Notifications), so each family owns its constants and the shared `integration.` prefix keeps them one namespace on the wire. The notification factory `NotificationErrors` is public (both provider assemblies construct it, the Search/AI/Storage precedent); `WebhookErrors` is internal (one assembly). `WebhookDeliveryExhaustedEvent.LastError` (a wire field of an integration event) becomes `LastErrorCode` (the code string only).
- **L1-L8, logging.** Per package `internal static class {Package}LoggingEventIds` (`WebhooksLoggingEventIds`, `SendGridLoggingEventIds`, `TwilioLoggingEventIds`) built from `LoggingEventIdRanges.Integration + n`; the numeric ids do not change. The nested `Log` classes move to `Diagnostics/{Package}Log.cs` as `internal static partial class`. Templates become one quoted sentence each, with `{ErrorType}`/`{ErrorCode}` instead of any free text, `'{SubscriptionId}'`, `'{DeliveryId}'` and `'{NotificationDeliveryId}'` (the audit gap: delivery ids were in neither logs nor spans). Levels per L6: per-delivery success Debug (was Information), failed `Result` Warning, `DeliveryFaulted` and the observer exception Error (the observer exception was Warning; L6 makes an unexpected exception Error, rule 13 is amended), `ExhaustionEventNotPublished` Warning (a failed `Result`).
- **T1-T6, tracing and metrics.** Both families keep their own `ActivitySource` instance named `SharedKernel.Integration` (the public `Name` constants stay) with version from `TelemetryVersion.Of`. Span names `webhook dispatch` (Internal), `webhook deliver` (Client), `notification send` (Client) replace `WebhookDispatcher.Dispatch`, `WebhookDispatcher.DispatchToSubscription`, `NotificationSender.Send`. Package tag keys move to `WebhookTagKeys` and `NotificationTagKeys`, gain `webhook.delivery_id` and `notification.delivery_id`, and drop their private `outcome` keys for `WellKnownTagKeys.Outcome` with `WellKnownOutcomes` values (the literals `"success"`/`"failure"` at `WebhookDispatcher.cs:134`, `SendGridEmailNotificationSender.cs:91`, `TwilioSmsNotificationSender.cs:65` go). Failure recording is the shared recorder (`RecordFailure(error)` for a failed result, `RecordException` for a fault, cancellation never an error), and its returned outcome string feeds the metric tag. The domain gains its first meter (`SharedKernel.Integration`, through `IMeterFactory`): `sharedkernel.integration.webhook.deliveries` (`{delivery}`), `sharedkernel.integration.webhook.delivery.duration` (`s`), `sharedkernel.integration.notification.sends` (`{message}`), `sharedkernel.integration.notification.send.duration` (`s`). Subscription id, delivery id and recipient are never metric tags. `WithIntegrationTelemetry()` is deleted by `SK.13.WildcardTelemetry` (this phase removes its mentions from the docs), which also fixes the Shop hosts that never called it.
- **T8, propagation.** The dispatcher writes the correlation id through `RequestContextPropagation.WriteHeaders` called with a `null` context and the explicit `CorrelationIds.Current(RequestContextScope.Current)`: the shared helper writes only the correlation id for a null context, so no tenant, actor kind, actor id or client header can leave the platform (rule 2 holds), and the hand-rolled `TryAddWithoutValidation` goes. A subscription header of the same name still wins. Root `CLAUDE.md` "Propagating context on outbound calls" lists Webhooks beside Communication, MassTransit and Temporal as propagating the full context; that is wrong (the correlation id only) and is reported for `/sync-brain`.
- **E2-E4, exceptions.** Misconfiguration moves to startup where possible: an `IValidateOptions<WebhookDeliveryOptions>` (resolved from DI, so it may take `IServiceProviderIsService`) fails `ValidateOnStart` when `EncryptPayload` is set without an `ISymmetricEncryptionService` registration, in addition to Phase 1's resolution-time guard. All thrown messages follow E3. Caller cancellation propagates out of both families' transport `catch` (`TaskCanceledException` is a failure only when `ct` is not cancelled; a client timeout is `Timeout`). This domain declares no classified exception (E1 not applicable: every expected failure is a `Result`/result record); the planner confirms with a grep for `: Exception` in the four packages.
