## Open Work

### SK.18.IdempotencyConformance — Conform Idempotency to the observability standard `○`

**Work order:** WO-087 / P-615 · **Depends on:** SK.01.ObservabilityHelpers (P-580: `TelemetryVersion.Of`, `ActivityFailureExtensions`, `WellKnownOutcomes`, `WellKnownTagKeys.Outcome`, `LoggingEventIdRanges.PackageSubBlockWidth`), SK.16.TelemetryCapture (P-581: every telemetry test asserts through the capture helpers), SK.00.ObservabilityReportOnly (P-583: the domain's finding count must reach zero), and one additive 01.Core constant, `ErrorCodes.Idempotency.StoreUnavailable` = `idempotency.store_unavailable` (see Blocked)

Brings the Abstractions, Redis and EfCore packages (and the fake) to root `CLAUDE.md` "Observability, exceptions and error codes". Today a fail-closed outage rethrows the raw `RedisConnectionException`/`RedisTimeoutException`/`NpgsqlException`, so `IdempotencyBehavior` (05, `SK.05.PipelineTelemetryGaps`) can only map it through its catch-all; the providers emit no span or metric, so fail-open is visible only as a log line; the two log templates are three sentences; Redis checks the purpose lazily inside the key builder while EfCore checks it first. This phase makes the outage a `SharedKernelException` the pipeline passes through unchanged, adds one source and one meter named `SharedKernel.Idempotency`, rewrites the templates and unifies the guards. Atomicity (rules 1-3), token ownership (4), the single opt-out (8) and the stored formats (Redis hash layout, `idempotency_keys` table, 64-hex digest) are untouched: no in-flight reservation is dropped and no migration is needed. Verdict: accept.

**Design (ratified by the D-tasks).**

- **Exception.** `IdempotencyStoreUnavailableException` (sealed, in `Idempotency.Abstractions`, deriving `SharedKernelException`) with the E1 pair `(Error)` and `(Error, Exception)` plus a convenience `(Exception innerException)` that builds the canonical error: `Error.Unavailable(ErrorCodes.Idempotency.StoreUnavailable, "The idempotency store is unavailable.")`, provider-neutral, no host, no key, no inner text. The original provider exception is the `InnerException` (stack trace kept). It lives in Abstractions, not in the providers, because it is the documented failure of `IIdempotencyStore` and the providers are siblings (rule 10). The code is the Primitives constant 01.Core adds; this domain adds no second copy and no `IdempotencyErrorCodes` class (`ErrorCodes.Idempotency` is already the C2 public home, shared with 05 and 14). One code and `ErrorType.Unavailable` for both connectivity and timeout: the caller's remedy is the same (retry) and 05 maps both to Unavailable.
- **Throw sites.** Fail-closed (`AllowExecutionOnStoreUnavailable = false`): all three members throw the exception above in place of `ExceptionDispatchInfo.Capture(...).Throw()`. Fail-open is unchanged (`Started` with an unwritten token / `false`, Warning log) except that it is now counted and traced. Rule 8 holds: only classified connectivity/timeout faults are wrapped; every other exception propagates raw.
- **Cancellation.** `OperationCanceledException` is never classified, never wrapped and never swallowed by fail-open (E4); the span ends Unset and the metric outcome is `canceled`.
- **Classifier.** Redis classifies every `RedisServerException` as unavailable today, so a Lua error or `ERR` reply would be reported as an outage and fail open. Narrow it to the transient server states (LOADING, BUSY, READONLY, MASTERDOWN, CLUSTERDOWN, TRYAGAIN, OOM), tested against real replies where Redis can produce them; a script or syntax error is a defect and propagates raw. EfCore keeps its bounded inner-exception walk.
- **Telemetry (T1, T3-T6).** `IdempotencyTelemetry` (public constants in Abstractions, no instances): `SourceName` = `MeterName` = `SharedKernel.Idempotency`, instrument names, and `IdempotencyTagKeys` (`idempotency.purpose`, `idempotency.operation`, `idempotency.result`, `idempotency.provider`, `idempotency.fail_open`); the cross-cutting `outcome` and `error.*` keys come from Primitives. Each provider owns its own static `ActivitySource` (version from `TelemetryVersion.Of`) and an internal singleton metrics class built from `IMeterFactory` (registered by the provider's `Add…Idempotency` with `AddMetrics()`, as 05 does). The two providers duplicate the small helper (rule 10) and may both be registered (Request on one, Message on the other): instrument definitions are identical and the `idempotency.provider` tag (`redis`, `efcore`) separates the streams. Spans: `idempotency begin|complete|release`, kind Client, tags purpose/provider/result; failure recorded with `RecordException`; a fail-open outage is recorded on the span too (the store failed) and tagged `idempotency.fail_open = true`. Metrics: histogram `sharedkernel.idempotency.operation.duration` (unit `s`; tags operation, purpose, provider, `outcome`, result) and counter `sharedkernel.idempotency.fail_open` (unit `{operation}`; tags operation, purpose, provider). `result` is a closed set: `started`, `in_progress`, `completed`, `fingerprint_mismatch` (begin), `applied`, `lost` (complete/release), `fail_open`. No key, fingerprint, token, tenant or response value is ever a tag, log value or span attribute (L5).
- **Logging (L1-L8).** Per package `{Package}LoggingEventIds` (`RedisIdempotencyLoggingEventIds`, `EfCoreIdempotencyLoggingEventIds`) built from `LoggingEventIdRanges.Idempotency + n * PackageSubBlockWidth` (18000 and 18100, numbers unchanged); the log class moves to `Diagnostics/`. The single template becomes one sentence: `The idempotency store was unavailable during '{Operation}' for purpose '{Purpose}', so the guarded call proceeds without duplicate protection.` (Warning, exception last; the "increases duplicate-execution risk" sentence moves to the README). The fail-closed path logs nothing (the caller logs the refusal; no double logging). Categories stay `ILogger<RedisIdempotencyStore>`/`ILogger<EfCoreIdempotencyStore>`; loggers stay required.
- **Guards and messages (E2, E3).** One public `IdempotencyPurposes.ThrowIfUndefined(purpose)` in Abstractions replaces four copies; both providers and the fake call it first in every member (EfCore's order today; Redis moves from the lazy key-builder throw), message `'{value}' is not a defined IdempotencyPurpose value.`. `AddIdempotencyStore` messages become `An IIdempotencyStore is already registered for IdempotencyPurpose 'Request'. Register one store per purpose.`; EfCore's impossible-row message becomes `The idempotency reservation statement returned no row. Verify the idempotency_keys schema.`. The Redis key builder keeps its exhaustive switch with an `UnreachableException` default arm.
- **Fake.** `FakeIdempotencyStore` gains `SimulateStoreUnavailable()` / `RestoreStore()` (and a `StoreUnavailable` flag): while set, all three members record the call and throw `IdempotencyStoreUnavailableException` exactly like a fail-closed provider. Argument validation matches the providers (`ThrowIfNullOrWhiteSpace` for key, fingerprint and token; the shared purpose guard).
