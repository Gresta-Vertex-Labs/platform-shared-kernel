### SK.07.MessagingErrorSafety — Header leakage, lost stack traces and swallowed failures `○`

**Work order:** WO-087 / P-588 · **Depends on:** SK.01.ObservabilityHelpers (P-580: `IHasError` is satisfied by `SharedKernelException`), SK.13.WildcardTelemetry (P-582: the `SharedKernel.*` wildcard that finally exports the Messaging meter). P-584 is **not** a dependency: this phase adds its own `SharedKernel.Core` reference instead of relying on `Execution` bringing it transitively.

Fixes the four Phase 1 defects found in this domain (audit Part 1, items 1, 5, 7, 8 and 9), verified on disk. (1) `ConsumerBase.Consume` copies **every** `x-sk-*` header into the log scope with a raw `"x-sk-"` literal; that includes `x-sk-actor-id` and `x-sk-client-id`, so the actor id lands on every log line of a consume (L5). It misses nothing it should carry: tenant and correlation already flow ambiently. The scope now carries only an allow-list of well-known headers that are safe to log, built from `WellKnownHeaders` constants. (2) `MassTransitMessageBus.Classify` ends in `throw ex;`, which resets the stack trace of every unrecognised broker or serializer exception (`MassTransitEventPublisher` already uses `throw;`; it is the only site). (3) `MassTransitMessageScheduler.CancelAsync` has a bare `catch (Exception)` that also swallows `OperationCanceledException`, so a caller who cancels is told the cancellation succeeded; worse, the token-to-type entry is removed before the call, so after a swallowed or propagated cancellation the schedule can never be cancelled again. (4) `ConcurrentMessageDeliveryException` and `PayloadTransformMismatchException` are `Exception`-derived with no `Error`: any edge that sees one cannot map it. Both become sealed `SharedKernelException`s. Item 1 of the audit (the Messaging meter `SharedKernel.Messaging` is never subscribed) is fixed by `SK.13.WildcardTelemetry` in 13.ServiceDefaults; this phase only proves it with the real meter owner.

Findings verified on disk that differ from the P-entry's premise: none of the three `*.count` counters needs a unit fix (`messaging.publish.count`, `.send.count`, `.consume.count` already declare `{message}`; `.retry.count` is `{retry}`, `.fault.count` is `{fault}`). The only unit defect is `messaging.consume.duration` in `ms`, fixed in `SK.07.ObservabilityConformance`. `Error.Message` text of `MessagingErrors.InvalidMessage` embeds `ArgumentException.Message` from `EventEnvelope.Wrap`; that is an E3 finding, also left to Phase 2 because it changes a public signature.

**Stored/wire formats:** none touched. Two new error codes are new wire strings (`messaging.concurrent_delivery`, `messaging.payload_transform_mismatch`), pinned literally. The log scope key for the actor kind changes from the header name to a structured key (a log-query change, listed as breaking). No broker header, queue name, CloudEvents attribute or idempotency key changes.

**Per-transport behaviour.** None of this phase is transport-specific: the log scope, the rethrow and the exception types are identical on RabbitMQ and Azure Service Bus. The scheduler fix concerns MassTransit's scheduler abstraction, which both transports reach (RabbitMQ through the delayed-message exchange, Azure Service Bus through native scheduled enqueue and cancel by sequence number); the cancellation rule is the same on both.

**Design.**

| Exception | Code (new, in public `MessagingErrorCodes`) | `ErrorType` | HTTP / gRPC through today's maps | Why |
| --- | --- | --- | --- | --- |
| `ConcurrentMessageDeliveryException` | `messaging.concurrent_delivery` | `Conflict` | 409 / `Aborted` | Another delivery of the same message id holds the reservation; the condition is a contention, not an outage or a defect (C3). Behaviour is unchanged: the message stays unacknowledged and is redelivered, and the type must still not be in `NonRetryableExceptions` |
| `PayloadTransformMismatchException` | `messaging.payload_transform_mismatch` | `Unexpected` | 500 / `Internal` | Publisher and consumer disagree on compression/encryption: a deployment defect, never a caller's bad input (C3) |

- Existing public constructors: `ConcurrentMessageDeliveryException(Guid, Type)` stays (it builds the canonical `Error`); the three BCL-style constructors `()`, `(string)` and `(string, Exception)` are removed because a `SharedKernelException` always carries an `Error` (E1); `(Error)` and `(Error, Exception)` are added. `PayloadTransformMismatchException(string, Exception)` is replaced by `(Error, Exception)` plus `(Error)`. Pre-GA, so the removals are acceptable and are listed under "Breaking changes".
- The canonical `Error` values come from a new **internal** `MassTransitErrors` factory in the core (the exceptions are core types, so the factory has no reason to be public); the codes are public constants on `MessagingErrorCodes` (`.Abstractions`) so a consumer can compare against them. `SK.07.ObservabilityConformance` D-02 decides whether the existing public `MessagingErrors` factory joins `MassTransitErrors`.
- Log-scope allow-list: of the six `WellKnownHeaders` (`CorrelationId`, `TenantId`, `IdempotencyKey`, `ActorId`, `ActorKind`, `ClientId`) only `ActorKind` qualifies (a coarse enum, not an identifier). `ActorId` and `ClientId` identify a person or client, `TenantId` and `IdempotencyKey` are on the L5 never-log list, `CorrelationId` is already the scope's own first entry. The allow-list is a single internal read-only set in `MessagingLogScope`, built from the constants; adding a header to it is a reviewed change with a test.
- Rethrow: the catch block classifies, and when the classifier returns nothing it uses a plain `throw;` (no `ExceptionDispatchInfo` needed inside a catch). `Classify` stops being an expression that throws.
- Scheduler: `catch (Exception ex) when (ex is not OperationCanceledException)` keeps the documented no-op for an already-delivered or unrecognised token; on cancellation the token-to-type entry is restored so the caller can retry the cancel, then the cancellation propagates. Narrowing the remaining catch to recognised transport faults is a Phase 2 decision (it changes behaviour for unknown exceptions).

### SK.07.ObservabilityConformance — Conform Messaging to the observability gold standard `○`

**Work order:** WO-087 / P-605 · **Depends on:** SK.07.MessagingErrorSafety (P-588), SK.01.ObservabilityHelpers (P-580: `TelemetryVersion`, `ActivityFailureExtensions`, `WellKnownOutcomes`, `WellKnownTagKeys.Outcome`, `LoggingEventIdRanges.SubBlockStart/IsInSubBlock`), SK.16.TelemetryCapture (P-581: `ActivityRecorder`, `MetricRecorder`, logger assertions), SK.00.ObservabilityReportOnly (P-583: the zero-findings acceptance). Coordinates with SK.13.WildcardTelemetry (P-582), which narrows `WithMessagingTelemetry()` to the MassTransit source and meter; no ordering needed because this phase keeps the source and meter name `SharedKernel.Messaging`.

Applies every rule of root `CLAUDE.md` "Observability, exceptions and error codes" to the five Messaging packages (`Abstractions` logs and emits nothing; `RabbitMq` and `EfCore` log nothing). T7 does not apply (no client-facing edge here). Per-transport behaviour: every item below is transport-neutral; the only transport-specific work is the Azure Service Bus package's own log moving to its own sub-block, and RabbitMQ and EfCore reserving theirs. No broker semantics, headers, queues or CloudEvents attributes change.
