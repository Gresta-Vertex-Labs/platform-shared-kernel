### SK.07.ObservabilityConformance — Conform Messaging to the observability gold standard `○`

**Work order:** WO-087 / P-605 · **Depends on:** SK.07.MessagingErrorSafety (P-588), SK.01.ObservabilityHelpers (P-580: `TelemetryVersion`, `ActivityFailureExtensions`, `WellKnownOutcomes`, `WellKnownTagKeys.Outcome`, `LoggingEventIdRanges.SubBlockStart/IsInSubBlock`), SK.16.TelemetryCapture (P-581: `ActivityRecorder`, `MetricRecorder`, logger assertions), SK.00.ObservabilityReportOnly (P-583: the zero-findings acceptance). Coordinates with SK.13.WildcardTelemetry (P-582), which narrows `WithMessagingTelemetry()` to the MassTransit source and meter; no ordering needed because this phase keeps the source and meter name `SharedKernel.Messaging`.

Applies every rule of root `CLAUDE.md` "Observability, exceptions and error codes" to the five Messaging packages (`Abstractions` logs and emits nothing; `RabbitMq` and `EfCore` log nothing). T7 does not apply (no client-facing edge here). Per-transport behaviour: every item below is transport-neutral; the only transport-specific work is the Azure Service Bus package's own log moving to its own sub-block, and RabbitMQ and EfCore reserving theirs. No broker semantics, headers, queues or CloudEvents attributes change.

**Logging (L1-L8).**
- L1, sub-blocks of the domain block 7000-7999, one per package, never interleaved: `SharedKernel.Messaging.MassTransit` 7000-7099 (index 0), `.RabbitMq` 7100-7199 (index 1, reserved, no class until it logs), `.AzureServiceBus` 7200-7299 (index 2), `.EfCore` 7300-7399 (index 3, reserved); `.Abstractions` logs nothing. Today the Azure Service Bus warning sits at **7010 inside the core's block**. It becomes the first id of the Azure Service Bus sub-block (7200); 7010 joins 7006 and 7007 as retired and is never reused. The core keeps every other number (7001-7005, 7008, 7009, 7011, 7012). Two `internal static class` holders built by const arithmetic from `LoggingEventIdRanges.Messaging` and `PackageSubBlockWidth`: `MessagingLoggingEventIds` (core) and `AzureServiceBusLoggingEventIds`; no bare literal remains.
- L2, one `internal static partial class` per logging package under `Diagnostics/`: `MessagingLog` (core, replacing the logging partials declared inside `ConsumerBase`, `BatchConsumerBase`, `FaultConsumerAdapter`, `VersionTranslatingConsumer`, `TranslatorRegistrationValidator` and `RequestContextRegistrationAdvisoryHostedService`) and `AzureServiceBusLog`. Plain static partial methods with `ILogger` first (the consumer bases cannot use an `ILogger` field, which also retires the "field-only generator" caveat in the domain `CLAUDE.md`).
- L3/L5, every template rewritten to one sentence ending in a period with quoted identifier values: for example 7001 "Consuming a message of type '{MessageType}' failed.", 7002 "Processing a batch of {BatchSize} messages of type '{MessageType}'.", 7011 states what was found and the one fix ("`IRequestContext` resolves to '{ResolvedType}' instead of the message-aware context. Register `AddSharedKernelRequestContext()` before `AddSharedKernelMessaging(...).Build()`."), 7009 and the Azure Service Bus advisory lose the em-dash and the multi-sentence text. No correlation id, tenant, actor, host or `ex.Message` appears (verified: none does today; the scope carries only the correlation id, which is the sanctioned scope key, rule 25).
- L4, add the logs missing on caught-exception paths, each passing the exception: **7013** (Warning) the bus and the event publisher convert a recognised transport fault into a `Result` and discard the exception, so the cause is nowhere (span only); one event "Dispatching a message of type '{MessageType}' failed during '{Operation}' with error '{ErrorCode}'." with the exception last. **7014** (Warning) the scheduler's cancel path swallows a fault (D-05). 7012 stays Debug.
- L6, levels reviewed event by event: 7004 (`LogFaultHandling`, an observation of an already-dead-lettered message) moves from Error to Warning, 7005 stays Error (a fault consumer threw), 7001/7003 stay Error (unexpected exception), 7008 Debug, 7002 Debug (per-operation success; was Information), 7009/7010→7200/7011 Warning (advisories).
- L7, categories: kernel types only (`FaultConsumerAdapter<,>`, `VersionTranslatingConsumer<,>`, the hosted services) plus one documented exception: the consumer bases log through the `ILogger` the service's consumer passes to its public constructor, so their category is the service's consumer type by design (the log is about that consumer; the constructor is public API and cannot take a different logger). L8, loggers required: the new `ILogger<MassTransitMessageBus>`, `ILogger<MassTransitEventPublisher>` and `ILogger<MassTransitMessageScheduler>` are required constructor parameters (internal types; registrations and test constructions updated), and `ConsumerBase`/`BatchConsumerBase` already reject a null logger (verify, add `ThrowIfNull` if absent).

**Tracing and metrics (T1-T6, T8).**
- T1: public constants `MessagingTelemetry.SourceName` and `MeterName`, both `"SharedKernel.Messaging"`, in the core's `Diagnostics/` namespace (new public type; `MessagingDiagnostics` stays the internal holder). Source and meter version from `TelemetryVersion.Of(typeof(MessagingTelemetry).Assembly)` replacing `SourceVersion = "1.0.0"`. The `ActivitySource` stays static. **The `Meter` stays a process-wide static (D-04)**: instruments are recorded from `ConsumerBase<T>`, `BatchConsumerBase<T>` and static filters whose public constructors take only an `ILogger`, so an `IMeterFactory` cannot reach them without a breaking constructor change on a type services derive from; root T1 says "where DI exists" and here it does not for the hot path. Rule 25 keeps its wording.
- T3, span names and kinds (breaking renames): `messaging consume` (Consumer), `messaging consume_batch` (Consumer, new, see D-03), `messaging publish` (`IMessageBus`, Producer), `messaging publish_event` (`IEventPublisher`, Producer), `messaging send` (Producer). Previously `Consumer.Consume`, `MessageBus.Publish`, `EventPublisher.Publish`, `MessageBus.Send`, all Internal kind.
- T4, tag keys from `MessagingTagKeys` (made public, documented): `messaging.message_type` and `messaging.event_type` stay; `messaging.destination` becomes the OpenTelemetry semantic-convention key `messaging.destination.name`; the batch span carries the semantic-convention `messaging.batch.message_count`; `outcome` comes from `WellKnownTagKeys.Outcome`. No raw string tag literal remains (SK0022 shape 5 from P-583 is clean).
- T5, failure recording through the shared helpers, never by hand: a recognised transport fault → `activity.AddExceptionEvents(ex)` then `activity.RecordFailure(error)` (status description = code, `error.code`, `error.type` = `ErrorType`, the full exception event, outcome `failure`); a `Result` failure from validation (contract violation, invalid message, endpoint not found) → `activity.RecordResult(result)`; an unrecognised exception → `activity.RecordException(ex)` then rethrow (outcome `exception`); `OperationCanceledException` → recorded as canceled, never an error. Consume: `RecordException` for a faulting `ConsumeAsync` (outcome `exception`, or `canceled`).
- T6, instruments renamed `sharedkernel.messaging.*` (breaking): `.publish.count`, `.send.count`, `.consume.count` (unit `{message}`), `.retry.count` (`{retry}`), `.fault.count` (`{fault}`), `.consume.duration` (histogram, unit **`s`**, recorded from `Stopwatch.GetElapsedTime(...).TotalSeconds`; the bucket view is the one `SharedKernel.*` seconds view from `SK.13.WildcardTelemetry`, none here). `publish.count`, `send.count` and `consume.count` gain the `outcome` tag (`success`, `failure`, `exception`, `canceled`) and now count every attempt, not only successes (filter `outcome=success` for the old meaning); `consume.duration` gains `outcome` too. The existing `.count` units already match the P-entry's `{message}` requirement; only the duration unit changes.
- T8, publish-side propagation only through `RequestContextPropagation`: `PublishContextPipe` hand-rolls `pipe.Headers.Set(WellKnownHeaders.CorrelationId, …)` and `…TenantId` (`PublishContextPipe.cs:68,73`). It writes through `RequestContextPropagation.WriteHeaders(new PropagatedRequestContext(ctx.TenantId, null, ActorKind.Anonymous, null, correlationId), pipe, setter, correlationId)`, so the header names and formats come from the one mapping. Consequence ratified in D-06: an `x-sk-actor-kind: Anonymous` header is now always present on an outgoing message that no `RequestContextHeaderPropagator` has already stamped (readers treat an absent kind as `Anonymous`, so no consumer behaviour changes; the caller-supplied headers still win and overwrite it, the explicit-wins rule is unchanged). `DispatchContextParityTests` gains the header case (rule 10). The consume side already uses `RequestContextPropagation.ReadHeaders`.

**Exceptions and error codes (E1-E4, C1-C3).**
- C1: `MessagingErrorCodes` is already public and all eight codes (six today, two from `SK.07.MessagingErrorSafety`) are lowercase `messaging.{snake}`; verified by a total test. C2: the public `MessagingErrors` factory in `.Abstractions` moves to the core's internal `MassTransitErrors` (D-02) because every producer is in the core; `MessagingErrorCodes` stays public. C3: types per code reviewed in D-02 (`messaging.unavailable` Unavailable stays).
- E3: `MessagingErrors.InvalidMessage(messageType, reason)` embeds `ArgumentException.Message` from `EventEnvelope.Wrap`; replaced by a closed internal reason (the publisher derives it from the `ArgumentException.ParamName`, verified on disk against `EventEnvelope.Wrap`; unknown → a fixed generic sentence) so no inner text reaches an `Error`. `PayloadTransformMessageDeserializer` stops doing `throw new InvalidOperationException(decrypted.Error.Message)` (and the decompress twin): the failure `Result` is turned straight into the mismatch exception with its canonical `Error`. Sweep of every other `throw` in non-test code (`MessagingBusBuilder.Build()` guards, `IdempotentConsumerBehavior`, `AzureServiceBusMessagingTransport`, `EntityFrameworkOutboxMessagingBusBuilderExtensions`, the `InMemory*` doubles): sentences ending in a period, values quoted, remedy named ("{X} requires {Y}. Call {Y} first."), no internal rule numbers, no `ArgumentOutOfRangeException` texts quoting data.
- E4: the scheduler's remaining catch narrows to recognised transport faults (`MessagingExceptionClassifier.TryClassify`) plus a 7014 log; an unrecognised exception rethrows (consistent with rule 5). `MassTransitMessageBus`/`MassTransitEventPublisher` already classify-or-rethrow.
