### SK.05.PipelineTelemetryGaps — Close the pipeline's telemetry and outage gaps `○`

**Work order:** WO-087 / P-586 · **Depends on:** SK.01.ObservabilityHelpers (P-580: `RecordResult`/`RecordException`/`AddExceptionEvents`, `WellKnownOutcomes`, `WellKnownTagKeys.Outcome`), SK.16.TelemetryCapture (P-581: every test asserts through `ActivityRecorder`/`MetricRecorder`/`LoggerAssertions`), and one additive constant in `SharedKernel.Primitives`, `ErrorCodes.Idempotency.StoreUnavailable` = `idempotency.store_unavailable` (not yet assigned to any P-entry, see Blocked)

Closes four gaps found by the WO-087 audit (item 12 and the idempotency half of item 10). (1) **Stream queries** register only `StreamAuthorizationBehavior`, so an `IStreamQuery<T>` has no span, log or metric. One new internal `StreamObservabilityBehavior<TRequest,TResponse>` is registered first in the `IStreamPipelineBehavior<,>` chain (outermost, so an authorization denial is observed too). Because an `IAsyncEnumerable` is lazy, the span, timer and log start at the first `MoveNextAsync`, not when `Handle` returns, and end exactly once at completion, fault or `DisposeAsync`; a stream that is never enumerated records nothing. Outcome: ran to the end `success`; the caller's token cancelled, an `OperationCanceledException`, or the consumer disposing before exhaustion `canceled` (span status stays Unset, no event, no `Error` log); any other throw `exception` (full recorder shape). One duration measurement goes to the existing `sharedkernel.application.request.duration` with `request.kind` = `stream`, and a new counter `sharedkernel.application.stream.items` (`{item}`) counts items yielded, including those yielded before a fault. No slow-threshold warning: a stream's duration is consumer-paced. (2) **`DomainEventDispatcher`** gets a span `application dispatch_events` per non-empty dispatch (tag event count) and one child span `application handle_event` per event type that has at least one handler (tags event type; handlers still run serially in registration order, rule 21 unchanged). A handler fault is logged once with the event type and handler type (the one fact the surrounding request log cannot name), recorded on both spans, and rethrown unchanged (`throw;`, same instance). (3) **`TransactionBehavior`** gets a span `application transaction` around `ExecuteInTransactionAsync` for the outermost transaction and for a joined one (tag `application.transaction_joined`), counts how often the unit of work ran the delegate (tag `application.attempts`; more than one logs the replay), and logs a rollback caused by a failed `Result` (Warning) or an exception (Error, exception passed). A nested command with no active transaction still calls `next()` directly, with no span. (4) **`IdempotencyBehavior`** treats every exception thrown by `IIdempotencyStore` as a store fault, because `.Pipeline` cannot reference Redis or Npgsql (rule 3) and `IIdempotencyStore` documents that an unreachable store throws: an exception from `TryBeginAsync` fails closed with a failed `Result` of `Error.Unavailable(ErrorCodes.Idempotency.StoreUnavailable)` and the handler does not run; a `SharedKernelException` from the store (what 18.Idempotency P-615 will throw) passes its own `Error` through unchanged; the caller's own cancellation still propagates. A fault in `CompleteAsync` (the work already committed) or `ReleaseAsync` (today it replaces the handler's own exception, because it runs in the `catch` block) is logged and swallowed, like a failed audit write (rule 16); the reservation expires on its own lease. **Stored/wire formats:** none touched (rule 14's key layout is unchanged); the new error code is a wire string, pinned literally. **Behavior change for the release notes:** a store outage that used to surface as a raw Redis or Npgsql exception (HTTP 500) now returns a failed `Result` (HTTP 503 through 14.Presentation).

**Design (file-level).** All internal, no public API. In `SharedKernel.Application.Pipeline`: new `Streaming/StreamObservabilityBehavior.cs`; `Tracing/ApplicationTagKeys.cs` (new, internal; `RequestType`/`RequestKind` keep today's literal values `request.type`/`request.kind` so the shared metric dimension does not split between stream and unary records until SK.05.ApplicationConformance changes them in one place; the new keys are final: `application.event_type`, `application.event_count`, `application.handler_type`, `application.transaction_joined`, `application.attempts`; the outcome tag is `WellKnownTagKeys.Outcome`); `Shared/RequestKind.cs` gains `Stream`; `Metrics/ApplicationMetrics.cs` gains the items counter; `DomainEvents/DomainEventDispatcher.cs`, `Transaction/TransactionBehavior.cs`, `Idempotency/IdempotencyBehavior.cs`; `ApplicationPipelineBuilder.Register` adds the stream behavior before `StreamAuthorizationBehavior<,>`; new `Diagnostics/PipelineLog.cs` (an `internal static partial class` with plain static methods, root rule L2) holds the new events while the existing ones stay in their behaviors until SK.05.ApplicationConformance moves them. Span names are final and follow T3: `application stream`, `application dispatch_events`, `application handle_event`, `application transaction`, all `ActivityKind.Internal`, started on the existing `ApplicationDiagnostics.ActivitySource`.

### SK.05.ApplicationConformance — Conform Application to the observability gold standard `○`

**Work order:** WO-087 / P-603 · **Depends on:** SK.05.PipelineTelemetryGaps (P-586), SK.01.ObservabilityHelpers (P-580), SK.16.TelemetryCapture (P-581), SK.00.ObservabilityReportOnly (P-583); soft: SK.13.WildcardTelemetry (P-582, only for the doc wording of the deleted `WithApplicationTelemetry`)

Applies root `CLAUDE.md` "Observability, exceptions and error codes" (L1-L8, T1-T8, E1-E4, C1-C3) to the four Application packages, on top of the new code of SK.05.PipelineTelemetryGaps. Measured state: the domain already owns one 100-wide sub-block per package (5000 Application with no logging, 5100 Pipeline, 5200 Pipeline.Caching, 5300 MediatR with no logging) and builds every EventId from `LoggingEventIdRanges.Application + n`; the `[LoggerMessage]` methods sit inside each behavior class with sentence-less templates; `LoggingBehavior` uses `ILogger<TRequest>` (a consumer category) and logs a successful request at Information; `TracingBehavior` hand-writes `SetStatus`/`error.*`/`AddException` and gives the exception message as the status description, and records cancellation as an error; `MetricsBehavior` and `TracingBehavior` use the raw literals `request.type`, `request.kind`, `outcome`, `error.type`; `ResponseOutcome` declares its own `success`/`failure`/`exception` strings; cache telemetry uses the keys `sharedkernel.query.type`, `sharedkernel.cache.scope`, `sharedkernel.cache.outcome`, `sharedkernel.command.type`, `sharedkernel.cache.target` (raw `"key"`/`"tag"`), `sharedkernel.cache.evicted`, tags values from `Enum.ToString()` (PascalCase), and the meter name `"SharedKernel.Application"` is declared as a literal in two packages (and a third time in `ApplicationPipelineTestHarness`); the `ActivitySource` and `Meter` carry no version; four swallowed failures leave no trace on any span. Caching instruments already declare units (`{query}`, `{entry}`); what is wrong is their names, tag keys and tag values. **Breaking, wire-visible, pre-GA, no aliases (WO-087 decision 2):** span name, tag keys, tag values, cache instrument names, the exception status description, the success log level, log categories and templates. **Stored/wire formats:** the idempotency key layout label (rule 14) and the cache key format (rule 18) are untouched.

**Blast radius.** The meter and source names do not change (`SharedKernel.Application`), so `AddServiceDefaults`' wildcard (P-582) needs nothing from this phase. Dashboards or alerts keyed on `request.type`/`request.kind`, the cache instrument names or tags, a log filter configured per request-type category, and a trace query on the old span name need the new names. `ApplicationPipelineTestHarness` (same domain) changes its capture implementation; its public members are kept. 13.ServiceDefaults' `ApplicationTelemetryExtensions` is deleted by P-582, not here.
