# Proposal: kernel 1.1.0, feedback from the service template

> Input for `/arch`. The source is building and releasing `platform-service-template` (the `sk-service` `dotnet
> new` template, now `1.0.0` on kernel `1.0.0`). That work included an AI acceptance run (four headless tasks on a
> generated service) and a real service repository through CI and release. Every item below was observed there; the
> evidence says where.
>
> Two parts: **A** is bookkeeping for the 1.0.0 release, and **B** is the 1.1.0 work. All of B targets **1.1.0**:
> additive or fixes, with no breaking change to a public API.

## Part B: work for 1.1.0

Each item: the problem, the evidence, and the outcome wanted. The domain planners decide the design.

### B1. A non-throwing business-rule check (`SharedKernel.Domain`, 03)

- **Problem:** `CheckRule(rule)` throws `BusinessRuleViolationException`, and there is no non-throwing form.
  Constructors are fine, because `TryCreate` turns the throw into a result. A **behavior method that returns
  `Result`** has two options today:
  - catch the exception (`ResultTry.Try` with an `onException` mapping, about 10 lines per method), or
  - hand-write `if (rule.IsBroken()) return Result.Failure(Error.BusinessRule(rule.Code, rule.Message));`
- **Evidence:** the template's `TemplateItem.Archive()` first shipped the `ResultTry` form, the only README-backed way
  to stay in `Result`. It was then rewritten by hand to the `IsBroken()` form. Every service copies this pattern from
  the template.
- **Wanted:** a non-throwing check on `AggregateRoot<TId>`, `ValueObject` and `DomainService` (alongside
  `CheckRule`) that returns `Result` carrying the rule's own error, documented in the Domain README next to
  `CheckRule`, with the rule of thumb: constructors and factories use `CheckRule`; behavior methods use the new check.

### B2. `PagedList<T>` and source-generated JSON (`SharedKernel.Contracts`, 04)

- **Problem:** `PagedList<T>` validates itself through a constructor the System.Text.Json source generator cannot
  call, so it cannot be deserialized with a `JsonSerializerContext`.
- **Evidence:** the template's published client (`{Service}.Client`) reads `ListAsync` results with reflection-based
  JSON (`JsonSerializerOptions.Web`), while every other call is source-generated. Every service's client inherits
  this exception to the AOT preference.
- **Wanted:** `PagedList<T>` (and `CursorPagedList<T>`, if it has the same issue) deserializable through a source-generated
  context, with validation kept. Check against the public-API baseline; this must not break 1.0.0 consumers.

### B3. Service-shape and placement rules as a package (`SharedKernel.ArchitectureTests`, 00)

- **Problem:** the rules that check a *consuming service's* project shape live only in
  `samples/Shop/Shop.TestSupport/ServiceShape.cs` (with `DependencyGraph`, `KernelPackageIndex`), which is not
  shipped.
- **Evidence:** the template copies `DependencyGraph.cs`, `KernelPackageIndex.cs` and `ServiceShape.cs` into every
  generated service, adapted to six projects (Domain, Contracts, Application, Infrastructure, Api, Client). It also
  copies `PlacementRules.cs`, nine folder/namespace rules: handlers under `*.Commands.{UseCase}` / `*.Queries.{UseCase}`,
  `IBusinessRule` under `*.Rules`, EF configurations under `*.Persistence.Configurations`, consumers under
  `*.Messaging.Consumers`, endpoints under `*.Api.Endpoints`, no `Managers`/`Helpers`/`Utils`/`Extensions`/`Exceptions`
  namespace segments, and no custom `Exception` types. Copies never update. The template's "Known gaps" section lists
  this.
- **Wanted:**
  - Ship the shape rules (four-project and six-project variants, with Contracts and Client) and the placement rules
    as reusable rule factories in `SharedKernel.ArchitectureTests`. Make the Shop's `ServiceShape` use them.
  - The kernel package index the rules need (which tier a `SharedKernel.*` package is) comes with the package, so it
    updates by version.
  - The template then drops its copies (template follow-up, not this work).

### B4. Skill: publishing and consuming a service's Contracts and Client (consumer skill)

- **Problem:** no recipe covers the pattern every service uses:
  - publish `{Service}.Contracts` (events and DTOs, additive changes only, versioned events) and `{Service}.Client`
    (a typed REST client over `Communication.Rest`)
  - consume another service's client **behind the consumer's own port**, registered in Infrastructure, never
    referenced from Application
- **Evidence:** the template's Client README is the only place this is written. Acceptance task 3 (consuming
  `ordering.order_placed`) had no guidance for "another service's event type"; the template's "Where things go" table
  got a row for it afterwards.
- **Also:** the recipes copy Shop's file placement (for example `OrderCommands.cs` grouping several use cases),
  which conflicts with the template's one-folder-per-use-case layout. The service `CLAUDE.md` tells the AI that its
  table wins over a recipe's placement. The skill should say the same thing from its side: **recipes decide packages
  and APIs; the service's `CLAUDE.md` decides folders.** Put it as one line in `SKILL.md` and in `recipes/new-service.md`.
- **Wanted:** a recipe (for example `publish-and-consume-a-service.md`) plus needs-table rows; `proven-by` from Shop
  where Shop does it, or declared `unproven`.

### B5. Vulnerable-package check as a kernel CI gate (devops)

- **Problem:** a vulnerable transitive dependency in a packed kernel package reaches every consumer, and nothing in
  kernel CI catches it.
- **Evidence:**
  - SSH.NET (through `Persistence.Testing` → Testcontainers) was found only by the consumer-skill greenfield eval,
    then fixed in #44. The fix was proven by restoring each of the 104 packed packages alone outside the repo with
    `NuGetAuditMode=all`, a check done once by hand.
  - A new MessagePack advisory later broke the template's main overnight without any code change. Template and
    services now run CI weekly for that reason.
- **Wanted:** a kernel CI gate, on pull requests and on a schedule, that restores every packed package **as a
  consumer would** (outside the repo, `NuGetAuditMode=all`) and fails on any NU190x. Record it in `eng/README.md`.

### B6. `add-caching.md`: required `ServiceName` (consumer skill, 02)

- **Evidence:** acceptance task 2 ("cache `GetShipmentQuery` for five minutes per tenant") wired caching without the
  `ServiceName` setting the package README marks required. The host then failed to start. The recipe does not
  mention it.
- **Wanted:** the recipe names every required setting of the packages it wires, and says that a missing one stops the
  host at startup.

### B7. Idempotency.EfCore migrations under the database role split (18, 06)

- **Evidence:** in acceptance task 3 (consumer deduplication), the AI hand-wrote a startup migration for
  `IdempotencyDbContext` and ran it on the runtime connection (`app_runtime`): `42501 permission denied for schema
  public`. `SharedKernel.Idempotency.EfCore` ships no migrations, and neither its README nor `add-idempotency.md` says
  how to create and apply them when migrations run as the migrator role and the service runs as the runtime role.
- **Wanted:** the documented way, and ideally a supported mechanism (shipped migrations or a `MigrateOnStartup`-style
  hook on the migrator connection, consistent with `Persistence.EfCore`). Update the README and the recipe.

### B8. "One replica" must route to the distributed lock (consumer skill, 19, 02)

- **Evidence:** acceptance task 4 ("run a job every night at 02:00 **on one replica**") used `SharedKernel.Scheduling`
  correctly but skipped the Redis distributed lock the job recipe calls for. The lock is mentioned in the recipe but
  not prominent enough to be followed.
- **Wanted:** make single execution across replicas a first-class line in `add-background-job.md` and its own
  needs-table row ("Run on one replica only" → `Scheduling` + `Caching.Redis.DistributedLocking`). If the scheduler can
  enforce or warn about a missing lock at startup, consider it.

### B9. OTLP exporter only when an endpoint is configured (`SharedKernel.ServiceDefaults`, 13)

- **Problem:** `AddServiceDefaults` always enables the OTLP exporter. With no endpoint configured it exports to the
  default `localhost:4317`.
- **Evidence:** in the template's composition test and integration test host, shutdown waited out the exporter's
  timeout, adding 8–9 s per run, until `OTEL_SDK_DISABLED=true` was set. In production, a pod without
  `OTEL_EXPORTER_OTLP_ENDPOINT` would keep retrying a collector that does not exist.
- **Wanted:** register the OTLP exporter only when `OTEL_EXPORTER_OTLP_ENDPOINT` (or the kernel's equivalent setting)
  is configured, as Aspire's own service defaults do. Aspire sets it locally, so local development is unchanged.
- **Weigh:** a deployment that relies on the implicit `localhost:4317` (a collector sidecar or node agent without the
  variable set) would stop exporting. Decide whether that is a release-note item, a deprecation warning, or an
  explicit opt-in to keep the old default.

### B10. Every published package must be public (devops)

- **Problem:** a new package on GitHub Packages starts **private**. Consumers' CI now reads the feed with
  `GITHUB_TOKEN`, which only sees public packages. A new kernel package left private would break every service's
  restore with a 401/404.
- **Evidence:** all 104 packages had to be switched by hand. GitHub has no API to change package visibility; it can
  only be **read** through `GET /orgs/{org}/packages/nuget/{name}` (`.visibility`).
- **Wanted:**
  - A release-time check (after publish in `release.yml`, and on the schedule) that every packable package exists on
    the feed and is `public`. It fails the run otherwise, naming the package and the manual step.
  - "Make it public (Package settings → Change visibility)" added to the new-package checklist in `CONTRIBUTING.md`.

## Out of scope

- Template changes. After 1.1.0, the template bumps through its documented procedure:
  - drop its copied shape and placement rules (B3)
  - use the non-throwing rule check (B1)
  - read `PagedList<T>` source-generated (B2)
  - keep or drop `OTEL_SDK_DISABLED` in its test hosts (B9)
- A smart-enum base type. It was discussed and not requested; services use plain enums.
- A second "thin service" template.
