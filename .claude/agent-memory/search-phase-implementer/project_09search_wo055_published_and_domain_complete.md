**Why this matters:** demonstrates how to handle two version-bump tasks (one PATCH-shaped, one MINOR-shaped) landing in the same delivery/session — a scenario the phase spec explicitly required a deliberate, recorded decision on rather than silent handling either way.

**Version-bump-folding decision (reusable pattern):** P-09 asked for a PATCH bump on the two provider packages (P-353's internal-only fixes); P-10 asked for a MINOR bump on all three packages (P-354's additive `SearchBulkWriteOptions` overloads). Both land in the same WO-055 delivery with no intervening published release. Packing a real `1.0.1` immediately followed by `1.1.0` in the same session would produce a PATCH artifact no consumer could ever depend on (1.1.0 supersedes it before anyone could reference it) — so both bumps were **folded into one MINOR pack per package**. All three packages went straight `1.0.0` → `1.1.0`. The decision was recorded in THREE places, never silently: (1) the state-map P-09 task row's explicit Decision note, (2) a dedicated XML comment block wrapping `<Version>`/`<PackageVersion>` in both provider `.csproj` files, (3) the CLAUDE.md/state-map changelog entries. **Reusable rule:** when two version-bump-worthy phases land in the same session with zero intervening publish, fold into one pack at the higher SemVer level and say so explicitly in at least the csproj comment + state-map — never silently skip the lower bump without a written rationale, and never actually publish two nupkgs where the first is unconsumable.
