09.Search Docs phase (SK.09.Docs, 8/8 tasks, 2026-07-20) completed: `GenerateDocumentationFile`+`TreatWarningsAsErrors`+full NuGet metadata (incl. `PackageReadmeFile`+packed `README.md`) on all three production `.csproj`; zero CS1591/CS1574; three `README.md` files written; DO-08 drift check. All 345 tests still green (155 Abstractions + 92 Meilisearch + 98 ElasticSearch). See [[project_09search_t26_and_completion]] for the prior Tests-phase state this builds on.

**The CS8509/CS8524 resolution (the load-bearing finding of this phase):** Core-phase left 2 (Meilisearch)/3 (ElasticSearch) "intentional" CS8509 (`SearchFilter`/`AggregationRequest` closed-hierarchy switches) and CS8524 (`SearchValueKind` enum switches) warnings, flagged as "to become a hard error once Docs-phase `TreatWarningsAsErrors` lands." That premise was WRONG and I proved it wrong with a scratch repro before trusting it:
- A switch over an `abstract record` base with every sealed subtype covered by a type-pattern arm still emits CS8509 ("the pattern `_` is not covered").
- Adding an explicit `null => throw ...` arm does **not** clear it — the reported gap just shifts from `_` to `not null`. This proves the diagnostic has nothing to do with nullability: **the C# compiler does not perform closed-world exhaustiveness analysis over a sealed-subtype class hierarchy, ever, regardless of constructor accessibility or how many subtypes are covered.** This is a permanent language limitation, not a fixable gap in how these switches are written.
- CS8524 on `SearchValueKind` (a 5-member enum, all covered) is the structurally identical enum analogue — an enum's underlying integral representation always permits an unnamed value, so full named-member coverage can never read as exhaustive to the compiler.

**Resolution applied:** both provider `.csproj` files (never Abstractions — it owns no translation switch) got `<WarningsNotAsErrors>CS8509;CS8524</WarningsNotAsErrors>`, narrowly scoped to exactly these two codes. Deliberately NOT `<NoWarn>` and NOT `#pragma warning disable` — `WarningsNotAsErrors` keeps both diagnostics **visible** in every build log while only these two stop failing the build; everything else stays fatal under `TreatWarningsAsErrors`. A discard arm was never added (still a hard violation). Each of the five affected switch sites (`MeilisearchFilterCompiler.Compile`/`.FormatValue`, `ElasticSearchFilterCompiler.Compile`/`.ToFieldValue`, `ElasticSearchAnalytics<TDocument>.GetName`) carries an inline `// ` comment cross-referencing `09.Search/CLAUDE.md`'s new "Reconciling switch exhaustiveness with `TreatWarningsAsErrors`" section (under Implementation Rules).

**What actually backstops a future 9th node (corrects the Core-phase premise on record):** never a compile-time catch — that assumption was untested and false. It's the runtime `SwitchExpressionException` every switch expression throws automatically on an unmatched value. A 9th `SearchFilter`/`AggregationRequest` subtype, or an out-of-range `SearchValueKind`, added without updating the switch fails loud at first execution — never silently. This is why a `_ => throw new NotSupportedException(...)` discard arm remains prohibited even though it "throws loudly" too: it's behaviourally identical to the implicit exception at runtime, but it erases the compiler's own honest "not provably exhaustive" signal for zero benefit — `WarningsNotAsErrors` preserves that signal.

**If a future domain (e.g. 16.Testing's `InMemorySearchIndex`/`InMemorySearchProviderDescriptor`, which have the identical CS8509 pattern on their own `SearchFilter` walkers, confirmed present via `dotnet test` warnings during this session) ever turns on `TreatWarningsAsErrors`, apply the same `WarningsNotAsErrors` resolution — do not rediscover this from scratch.**

**Two genuine XML-doc defects found only once `TreatWarningsAsErrors` was flipped on** (both were latent since Core phase, invisible without the doc-warning-as-error gate):
1. `MeilisearchResultMapper` (a non-generic `internal static class`) had a class-level `<remarks>` with `<typeparamref name="TDocument"/>` — but `TDocument` belongs to its `Map<TDocument>` method, not the class → CS1735. Fixed: replaced with plain `<c>TDocument</c>`.
2. `ElasticSearchResultMapper`'s doc had `<see cref="SearchResponse{TDocument}.IsValidResponse"/>` — `IsValidResponse` is inherited from a non-generic base type, not declared on `SearchResponse<T>` itself, and Roslyn's cref resolver fails to resolve an inherited member through an open generic type reference this way → CS1574. Fixed: replaced with plain `<c>response.IsValidResponse</c>` prose — don't fight the resolver over a link that isn't essential.

**Lesson for future sessions:** when `cref`/`typeparamref` doesn't resolve on an SDK type you don't own (especially inherited members through generics), don't spend time reflecting the SDK to find the "correct" cref syntax — just drop to plain `<c>` prose. It's faster and equally clear to a reader.

**DO-01's specific content requirement was NOT fully met by Core/Tests phases despite CLAUDE.md prose covering it**: `SearchFilter`'s own XML `<remarks>` never actually contained the "what nodes are deliberately absent, and why" + "the mandated flattening technique for object-array data" paragraphs — that content only ever lived in `09.Search/CLAUDE.md`'s prose (D-12), never in the type's own doc comment. Docs-phase closed this real gap. **Lesson:** when a phase spec calls out specific doc content by name (not just "add docs"), grep the actual type's doc comment for that content — don't assume brain-prose coverage implies source-doc coverage.
