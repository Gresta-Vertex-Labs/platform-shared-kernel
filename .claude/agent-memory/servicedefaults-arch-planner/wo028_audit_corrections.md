On 2026-06-19 a gold-standard audit of already-shipped `13.ServiceDefaults` Core code (C-01–C-19, landed under WO-027) surfaced three defects, dispatched as WO-028 (P-175/P-176/P-177). Key lesson: **this domain's own `CLAUDE.md` had previously documented a real defect as an "accepted test limitation."** Specifically, `TenantResolutionMiddleware.InvokeAsync` mapped strategies to `"Header"`/`"Claim"`/`"Database"` by switching on `s.GetType().Name` — and the test suite's `RecordingStrategy` double was deliberately built to be unreachable by that switch, with a doc comment admitting as much. The brain file treated this as a documented limitation rather than escalating it as a defect. **Do not repeat this pattern** — if a future audit finds a workaround masking a real defect, classify it as the defect it is, not as accepted behavior, even if a prior pass already wrote it down as "known."

Corrections landed in planning (state-map C-20–C-28, T-15–T-22; not yet implemented as of this writing):
- **P-175**: `ITenantResolutionStrategy.StrategyName` (explicit contract, not reflection) + `TenantResolutionStrategyNames` constants class + lookup computed once (not rebuilt per-request). This is the platform's only explicit extensibility point for `13.ServiceDefaults` (a consuming team's custom 4th strategy) — reflection-based identification silently defeats it.
- **P-176**: `DatabaseTenantResolutionStrategy.TryResolveAsync` was sync-over-async (`IDbCommand.ExecuteScalar()` inside an `async Task<Guid?>` method, `CancellationToken` accepted but never used). Fixed to genuine async ADO.NET with the token threaded through. **Pattern to watch for in future audits**: any method with an `async`/`CancellationToken` signature in this domain should be checked for whether the implementation actually awaits an async I/O call — a hot-path package (every multi-tenant request) cannot afford sync-over-async thread-pool blocking.
- **P-177**: `HealthCheckNames` constants class added (mirrors the already-correct `HealthCheckTags` pattern) — five literals (`database`/`redis`/`rabbitmq`/`azure-service-bus`/`cache`/`startup`) consolidated. Also closed a real **planning gap, not just a style issue**: `AddDatabaseReadinessCheck<TContext>` and `AddDapperDatabaseReadinessCheck` had been fully specified in `CLAUDE.md`'s Interface Contracts since P-150, but no Core task row ever existed for them and no code was ever written — the documentation outran the implementation silently. Lesson: when refreshing `CLAUDE.md`, periodically cross-check that every documented Interface Contract has a corresponding `state-map.md` Core task in a completed or pending state — a contract documented with no task row is a silent gap.

See [[health_check_tag_calibration]] for the tag/status table the two new DB readiness adapters slot into (`"ready"`+`"db"`, `Unhealthy` on failure — no fail-safe layer in front of a raw DB connectivity probe, so no `Degraded` calibration applies here, unlike cache readiness).
