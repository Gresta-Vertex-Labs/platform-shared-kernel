**SK0023 `NonSingletonAmazonS3ClientRegistrationAnalyzer`** — structural inverse of SK0703 (`MessageBusSingletonRegistrationAnalyzer`): flags `AddScoped`/`AddTransient` registration of a type whose first generic type argument's simple name is `"IAmazonS3"` (one- and two-argument forms), because `IAmazonS3` must always be Singleton (SK0703 flags `AddSingleton<IMessageBus>` because that must be Scoped). Syntax-only, no SemanticModel, fires globally, lives in `SharedKernel.Analyzers/Diagnostics/SK0023_NonSingletonAmazonS3ClientRegistrationAnalyzer.cs` (not the `Analyzers/` path some phase specs guess — every SK00NN analyzer lives in `Diagnostics/`, a discrepancy every recent phase spec has repeated and every closeout has resolved in favor of the on-disk convention).

**`StorageTopologyRules`** (`SharedKernel.ArchitectureTests/Rules/StorageTopologyRules.cs`) — mirrors `RedisTopologyRules` but scoped to `08.Storage`'s two provider packages (`.S3`, `.Obs`) instead of Redis's five. Three pure NetArchTest `.Should().NotHaveDependencyOn(...)` predicates, zero Mono.Cecil:
- `AbstractionsHasNoThirdPartyDependencies(Assembly)` — four forbidden terms: `"Amazon"` (bare prefix, catches all AWSSDK.S3 namespaces), `"SharedKernel.Storage.S3"`, `"SharedKernel.Storage.Obs"`, `"SharedKernel.Configuration"`.
- `ProviderPackagesNeverReferenceEachOther(Assembly s3, Assembly obs)` → `ConditionList[2]` — TWO NAMED parameters (not `params`), mirroring `UnitOfWorkSeamRules`'s two-named-parameter convention; no lookup table needed since only two packages exist and neither namespace prefixes the other.
- `OnlyProviderPackagesMayReferenceAmazonS3(params Assembly[])` — single `NotHaveDependencyOn("Amazon.S3")` check; caller-controlled exclusion (never pass `.S3`/`.Obs` themselves), same convention as `PresentationLayeringRules`/`CompositionRootExclusivityRules` — no internal namespace guard.

**Fixture pitfall — `const int` const-folds too, not just `const string`:** the fire-path fixtures for `ProviderPackagesNeverReferenceEachOther` initially had the "other" provider's stub type expose a `const int` field; the C# compiler const-folds `const` primitives of ANY type into a bare IL literal at the call site (no `Ldsfld`, no assembly metadata reference emitted), so NetArchTest's dependency-namespace scan never observed the cross-reference and the fire-path test passed for the wrong reason (or rather, silently failed to prove what it claimed). Fixed by switching the fixture to constructor-inject an *interface type* instead — a genuine metadata reference that NetArchTest can see. This confirms the const-folding class of pitfall already recorded in [[ref_string_constants_detector_pattern]] for `const string` vs `static readonly string` applies identically to `const int`/any const primitive — when building a fire-path dependency fixture, always use a reference-type/interface member, never a `const` field of any type, to guarantee a real IL/metadata reference exists.

**Third confirmed "phase spec's blocking-dependency premise went stale before implementation" incident** (after SK.00.MagicStringGuard's 01.Core dependency and an earlier one): the phase spec (authored 2026-07-16) mandated contrived-fixtures-only design because `08.Storage` was pre-implementation at authoring time. By the 2026-07-18 implementation session, `08.Storage` had independently reached Published (P-265/P-266/P-267 all shipped) — confirmed via `dotnet build --configuration Release` (0 warnings/errors on all three projects) rather than trusted from prose. Real-assembly wiring was implemented in the same session rather than deferred: three test-only `ProjectReference`s (`PrivateAssets="all"`) added to `SharedKernel.ArchitectureTests.Tests.csproj`, plus three `Real*`-suffixed tests. Contrived fixtures (T-194–T-199) were kept as the primary red/green proof per the phase spec's own instruction, with real-assembly tests as an addition, not a replacement. Always re-check a phase spec's stated blocking dependency against the ACTUAL current state of the other domain (build it, check its real state-map) before assuming the spec's "still blocked" framing is current — see [[feedback_verify_root_propagation]] for the same discipline applied to state-map bookkeeping itself.

Baseline test counts after this phase: 144/144 `SharedKernel.Analyzers.Tests`, 145/145 `SharedKernel.ArchitectureTests.Tests`. This closed the last `○` phase key in `00.Governance/state-map.md` — every phase key is now `●`.
