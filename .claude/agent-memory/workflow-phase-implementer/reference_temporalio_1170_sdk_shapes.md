Verified 2026-07-23 by reflecting the real compiled `Temporalio`/`Temporalio.Extensions.Hosting`/`.OpenTelemetry`/`.DiagnosticSource` 1.17.0 assemblies via a scratch console project (NuGet cache path: `~/.nuget/packages/temporalio/1.17.0/`). These are load-bearing corrections — re-verify against the assembly again if the pinned version ever changes, don't assume they still hold.

**Enum locations** — `Temporalio.Api.Enums.V1.WorkflowIdReusePolicy` (Unspecified/AllowDuplicate/AllowDuplicateFailedOnly/RejectDuplicate/TerminateIfRunning) and `.WorkflowIdConflictPolicy` (Unspecified/Fail/UseExisting/TerminateExisting) — NOT `Temporalio.Client` as a naive guess would place them.

**ActivityOptions split** — the type used inside `Workflow.ExecuteActivityAsync` is `Temporalio.Workflows.ActivityOptions` (StartToCloseTimeout/ScheduleToCloseTimeout/ScheduleToStartTimeout/HeartbeatTimeout/RetryPolicy, all nullable, genuinely no default). `Temporalio.Activities.ActivityOptions` does not exist — that namespace holds `ActivityAttribute`/`ActivityExecutionContext`/`ActivityInfo`. A separate `Temporalio.Client.StartActivityOptions` exists for client-side direct-activity-start (unused by [[17-workflows-core-implementation]]).

**ApplicationFailureException ctor** — `(string message, string? errorType = null, bool nonRetryable = false, IReadOnlyCollection<object?>? details = null, TimeSpan? nextRetryDelay = null, ApplicationErrorCategory category = Unspecified)`. Every parameter but `message` is optional/defaulted. `Details` is read back via `IFailureDetails.ElementAt<T>(int)` (generic, lazily decoded through the payload converter).

**Activity naming collision (critical, verified empirically)** — Temporal names an `[Activity]`-attributed method by the METHOD's own name (stripping an `Async` suffix) when no explicit name is given, never by the declaring/concrete class name. Proved via `ActivityDefinition.CreateAll(type, instance)`: two sibling classes both inheriting an unchanged `[Activity] Task<int> ExecuteAsync(int)` from a shared base BOTH registered as `"Execute"`. Consequence: any shared base method meant to be reused by multiple concrete activity types (e.g. `CommandActivity<TCommand>.ExecuteAsync`) must NOT carry `[Activity]` on the base — the concrete sealed subclass supplies its own explicitly-named override, e.g. `[Activity(nameof(ApproveOrderActivity))] public override Task ExecuteAsync(...) => base.ExecuteAsync(...);`.

**Workflow naming has no such collision** — `WorkflowDefinition.Create(Type)` defaults to the CLASS name, not a method name. Verified directly.

**String-keyed activity dispatch** — `Workflow.ExecuteActivityAsync<TResult>(string activity, IReadOnlyCollection<object?> args, ActivityOptions options)` exists alongside the expression-based overloads. This is what a generic `WorkflowBase.ExecuteAsync<TActivity,TArgs,TResult>` helper should use, keyed on `typeof(TActivity).Name` — which is exactly why the activity-naming-collision finding above matters.

**Header carriers** — `Temporalio.Workflows.WorkflowInfo.Headers` is `IReadOnlyDictionary<string, Payload>`, readable directly and deterministically inside workflow code (no interceptor needed to read it back). `Temporalio.Activities.ActivityInfo` has **no** `Headers` member at all — only the interceptor-level `ExecuteActivityInput.Headers` carries them, which is why an `AsyncLocal`-backed ambient bridge is the only way to get header-derived values (tenant scope, correlation id) into activity-side code. Client-side `StartWorkflowInput`/`SignalWorkflowInput`/`QueryWorkflowInput.Headers` are mutable `IDictionary<string, Payload>` — writable in place before calling `next.XAsync(input with { Headers = headers })`.

**Interceptor shapes** — `IClientInterceptor.InterceptClient(ClientOutboundInterceptor next) -> ClientOutboundInterceptor`; `IWorkerInterceptor.InterceptWorkflow(WorkflowInboundInterceptor next) -> WorkflowInboundInterceptor` and `.InterceptActivity(ActivityInboundInterceptor next) -> ActivityInboundInterceptor`. Override `ClientOutboundInterceptor.StartWorkflowAsync<TWorkflow,TResult>` (two generic params, not one — easy to get wrong), `.SignalWorkflowAsync`, `.QueryWorkflowAsync<TResult>`; override `WorkflowInboundInterceptor.ExecuteWorkflowAsync` and `ActivityInboundInterceptor.ExecuteActivityAsync` (both return `Task<object?>`).

**Health/probe primitives** — `ITemporalConnection.CheckHealthAsync(RpcService service = default, RpcOptions options = default) -> Task<bool>` is a genuine built-in health ping (both params optional; pass `client.Connection.WorkflowService` as the `RpcService`, since `WorkflowService` derives from the abstract `RpcService`). `WorkflowService.DescribeNamespaceAsync(DescribeNamespaceRequest{Namespace}, RpcOptions)` confirms namespace addressability. `Temporalio.Extensions.Hosting.TemporalWorkerService` extends `Microsoft.Extensions.Hosting.BackgroundService` and exposes a public `Task? ExecuteTask` — non-null and `!IsCompleted` is the honest "pollers still running" signal, resolved via `IEnumerable<IHostedService>` from DI.

**Obsolete overload** — `AddHostedTemporalWorker(services, taskQueue, buildId)` is `[Obsolete]` in 1.17.0 in favor of a `WorkerDeploymentOptions`-based overload (Temporal's worker-versioning/deployment feature — a distinct SDK concept). The obsolete overload still works; suppress CS0618 narrowly at the one call site with a documented comment rather than adopting the unplanned newer concept without a design pass.

**Native RID list (S-07, confirmed via the extracted package's `runtimes/` folder)** — exactly 8: `linux-arm64`, `linux-musl-arm64`, `linux-musl-x64`, `linux-x64`, `osx-arm64`, `osx-x64`, `win-arm64`, `win-x64`.

**`WorkflowEnvironment.StartTimeSkippingAsync()` dev-server binary cache path** — `%LOCALAPPDATA%\Temp\temporal-test-server-sdk-dotnet-{version}.exe` (version-suffixed, so an SDK bump fetches a fresh binary rather than silently reusing a stale one). Confirmed genuinely time-skips: a 30-day `env.DelayAsync` completed in ~11ms wall-clock. No network restriction encountered on this machine.

**`AddWorkflow(Type)` on the HOSTING builder does not validate eagerly (verified Tests-phase, T-08)** — `Temporalio.Extensions.Hosting.ITemporalWorkerServiceOptionsBuilder.AddWorkflow(Type)` silently accepts a non-`[Workflow]`-attributed type; the failure is deferred to worker startup. The CORE SDK's `Temporalio.Workflows.WorkflowDefinition.Create(Type)` (and `Temporalio.Worker.TemporalWorkerOptions.AddWorkflow(Type)`) DO throw `ArgumentException` immediately for the same input — call `WorkflowDefinition.Create(type)` yourself first if you need eager validation through the hosting builder.

**`WorkflowInboundInterceptor.Init(WorkflowOutboundInterceptor outbound)` is the hook for a workflow's OWN outbound calls** — `Temporalio.Worker.Interceptors.WorkflowOutboundInterceptor` has virtual `ScheduleActivityAsync<TResult>(ScheduleActivityInput)`, `ScheduleLocalActivityAsync<TResult>(...)`, `StartChildWorkflowAsync<TWorkflow,TResult>(StartChildWorkflowInput)`, `SignalChildWorkflowAsync`, `SignalExternalWorkflowAsync`, `CancelExternalWorkflowAsync`, `DelayAsync(DelayAsyncInput)`, `CreateContinueAsNewException`, `ScheduleNexusOperationAsync`. Its ctor is `protected WorkflowOutboundInterceptor(WorkflowOutboundInterceptor next)` (non-public, same pattern as `ClientOutboundInterceptor`/`ActivityInboundInterceptor`). `ScheduleActivityInput`/`StartChildWorkflowInput` both carry their OWN mutable `IDictionary<string, Payload> Headers` — **verified empirically these start EMPTY and are NOT auto-populated from `Workflow.Info.Headers`** — a workflow's own inbound headers do not automatically forward to activities/child workflows it schedules; an interceptor must copy them explicitly inside an `Init`-installed `WorkflowOutboundInterceptor` override.

**`ActivityOptions.CancellationToken` / `DelayOptions.CancellationToken` both default to the ambient `Workflow.CancellationToken`** (verified Tests-phase, T-11) — both are nullable `CancellationToken?` properties on `Temporalio.Workflows.ActivityOptions`/`DelayOptions`. Left unset, an activity/timer call observes the SAME workflow-level cancellation token — including for a call issued AFTER that token was already cancelled. A compensation activity dispatched from inside a `catch` block after cancellation must explicitly pass `CancellationToken.None` (or another non-cancelled token) or it is itself immediately cancelled before it can run.

**`Temporalio.Exceptions.CanceledFailureException` does NOT derive from `System.OperationCanceledException`** (verified type hierarchy: `CanceledFailureException` → `FailureException` → `TemporalException` → `Exception`). This is what `Workflow.DelayAsync`/activity calls throw when the observed cancellation token is cancelled — a workflow catching `OperationCanceledException` to run compensation logic will never enter that catch block; catch `Temporalio.Exceptions.CanceledFailureException` explicitly (or both, via an `is X or Y` pattern).

**Exception public-constructor availability, confirmed via reflection** — usable directly in unit tests: `WorkflowFailedException(Exception inner)`; `ApplicationFailureException(string message, string? errorType = null, bool nonRetryable = false, IReadOnlyCollection<object?>? details = null, TimeSpan? nextRetryDelay = null, ApplicationErrorCategory category = Unspecified)` (also an overload taking an inner `Exception`); `WorkflowAlreadyStartedException(string message, string workflowId, string workflowType, string runId)` (the 3-arg `(message, workflowId, runId)` overload is `[Obsolete]`); `RpcException(RpcException.StatusCode code, string message, byte[]? rawStatus)`; `WorkflowQueryRejectedException(WorkflowExecutionStatus workflowStatus)` (lives in `Temporalio.Exceptions`, not `Temporalio.Client` despite what the name suggests). **NOT publicly constructible** (internal-only ctors, requiring the internal `Failure` proto type) — cannot be unit-tested via direct construction, only via a real `WorkflowEnvironment` round trip: `ActivityFailureException`, `ChildWorkflowFailureException`, `CanceledFailureException`, `TerminatedFailureException`, `TimeoutFailureException`.

**`ApplicationFailureException.Details` (`IFailureDetails`) behavior when constructed with a raw `object?[]`** — `.Count` reflects the array length; `.ElementAt<T>(int)` does a direct runtime cast (throws `InvalidCastException` for a type mismatch, e.g. requesting `<int>` from a `string` element) — this is a genuine, catchable exception, not silently coerced, so a defensive `catch (Exception)` around a best-effort decode of this optional round-trip metadata is legitimate (not a "swallowed Result.Failure" violation).

**Genuine auto-time-skipping is coordinated through the specific `ITemporalClient` instance `WorkflowEnvironment.Client` vends — NOT purely server-side** (verified via an isolated repro before touching the real test suite: identical target host/namespace, a SEPARATELY-connected client via `Temporalio.Extensions.Hosting.AddTemporalClient(targetHost, ns)` never observes a real timer completing — the call hangs indefinitely). Any test needing a workflow's natural timer to actually elapse (not a cancel/terminate/signal-driven completion) MUST start/await through `env.Client` directly. The WORKER processing those executions can still be built via the normal production DI composition (`AddSharedKernelTemporalWorkflows` + `AddHostedTemporalWorker`) — task-queue-based routing does not care which client instance started the execution, only the CLIENT-SIDE await/skip coordination is client-instance-specific.

**`WorkflowEnvironment.Client.Connection.Options.TargetHost`** and **`WorkflowEnvironment.Client.Options.Namespace`** are the two values needed to point a separately-built DI composition (e.g. via `TemporalOptions`) at the SAME running time-skipping test server — confirmed working (`ITemporalClient` resolves in ~100ms without an active server, only fails/hangs on an actual RPC attempt against an unreachable target).

See also [[17-workflows-core-implementation]] and [[project_17_workflows_tests_phase]] for how these shapes were applied.
