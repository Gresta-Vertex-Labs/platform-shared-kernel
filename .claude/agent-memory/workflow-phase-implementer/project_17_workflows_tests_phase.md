**SK.17.Tests (T-01–T-16) reached `●` on 2026-07-23 — 68/81 total tasks. 158/158 tests passing** (134 pure-unit + 24 real-`WorkflowEnvironment`), confirmed stable across three consecutive clean `dotnet test` runs. `SK.17.Docs` and `SK.17.Published` remain pending.

**Three genuine production defects found by testing and fixed in the shipped package** (not routed around in test code — see [[reference_temporalio_1170_sdk_shapes]] for the Core-phase findings this session built on):

1. **`Temporalio.Extensions.Hosting`'s `AddWorkflow(Type)` does not eagerly validate `[Workflow]`.** Confirmed empirically: `ITemporalWorkerServiceOptionsBuilder.AddWorkflow(Type)` silently accepts a non-`[Workflow]`-attributed type at registration time (unlike the core SDK's own `WorkflowDefinition.Create(Type)`/`TemporalWorkerOptions.AddWorkflow(Type)`, which throw `ArgumentException` immediately). Fix: `TemporalWorkflowsBuilder.BuildWorkerHosting()` now calls `WorkflowDefinition.Create(workflowType)` itself as an eager pre-check before delegating to the hosting builder.
2. **Headers do not auto-propagate from a workflow's own inbound headers to activities/child workflows it schedules.** `ScheduleActivityInput.Headers`/`StartChildWorkflowInput.Headers` (`Temporalio.Worker.Interceptors`) start empty unless something populates them — there is no automatic "inherit the parent's headers" behavior. Fix: `WorkflowPropagationInterceptor`'s inbound interceptor now overrides `Init(WorkflowOutboundInterceptor outbound)` to wrap it in a `PropagatingWorkflowOutboundInterceptor` that merges `Workflow.Info.Headers` onto every `ScheduleActivityAsync`/`StartChildWorkflowAsync` call. Caught only because the propagation test (T-15) asserted the ACTIVITY's own observed tenant scope, not just the workflow's — a test that only checked the workflow-level header would have missed this entirely.
3. **No way to give an activity a cancellation token independent of the ambient `Workflow.CancellationToken`.** Both `ActivityOptions.CancellationToken` and `DelayOptions.CancellationToken` default to the ambient workflow token when unset — including for a call issued AFTER that token was already cancelled. This makes a "cancel → run compensation activity" pattern silently impossible with the base authoring surface, since the compensation activity is itself immediately cancelled. Fix: added `ActivityDispatchOptions.CancellationToken` (nullable), wired through `WorkflowBase.ExecuteAsync`. Pass `CancellationToken.None` explicitly for any compensation-activity call.

**Two behavioral findings, not defects (test-design/authoring-pattern only):**
- `Workflow.DelayAsync` cancellation surfaces as `Temporalio.Exceptions.CanceledFailureException`, which does **not** derive from `System.OperationCanceledException` (verified type hierarchy: `CanceledFailureException` → `FailureException` → `TemporalException` → `Exception`). A workflow's compensation `catch` clause must name the Temporal type explicitly, e.g. `catch (Exception ex) when (ex is OperationCanceledException or Temporalio.Exceptions.CanceledFailureException)`.
- **Genuine auto-time-skipping is coordinated through the exact `ITemporalClient` instance `WorkflowEnvironment.Client` vends.** A separately-connected client to the identical target host/namespace (i.e. `IWorkflowDispatcher`'s own client, built via `Temporalio.Extensions.Hosting.AddTemporalClient`) does **not** participate in the auto-skip protocol — a workflow awaiting a real timer through it never progresses (confirmed via an isolated repro before touching the real test suite). Fix (test-only): `TimeSkippingTests` starts/awaits directly through `fixture.Environment.Client`; the WORKER processing those executions is still the one built by the production `AddSharedKernelTemporalWorkflows` composition, since task-queue routing is client-agnostic. Tests that only need cancel/terminate/signal-driven completions (no natural timer elapsing) are unaffected and use the full `IWorkflowDispatcher` pipeline normally.

**How to apply:** Before touching `17.Workflows` real-environment tests again, remember: (a) any new sample workflow that needs a "run this even if I've been cancelled" step must pass `CancellationToken.None` explicitly; (b) any new propagation-hop test must assert the ACTIVITY/CHILD's own observed state, not just the immediate workflow's; (c) any new time-dependent (natural-timer) test must go through `fixture.Environment.Client`, not the DI-resolved dispatcher.

**Process lesson (session-management, not code):** running back-to-back `dotnet test` invocations against this suite without an explicit process-cleanup step in between (`taskkill` on leftover `testhost.exe`/`temporal-test-server-sdk-*.exe`) causes intermittent hangs — almost certainly port/resource contention between the just-torn-down and freshly-starting `WorkflowEnvironment` dev-server processes. Always kill lingering `testhost`/`temporal-test-server-sdk-*` processes before re-running this suite, and always run `dotnet test` as a single synchronous foreground call with a generous explicit timeout (five-plus minutes) — never chain it with a trailing shell `&` under `run_in_background: true` (that backgrounds only the wrapper shell, not the actual test process, and produces a false-positive "completed" notification while the real run is still in progress).
