> WO-086 (2026-09): the first two conventions below are rewritten for the 20-package split. Later entries still name the old single-package paths (`SharedKernel.Testing.SelfTests`, `Cryptography/…`, `Caching/…` inside `SharedKernel.Testing`) — those fakes now live in `SharedKernel.{Capability}.Testing`; the `HotChocolate`/`GreenDonut` ambiguity now only affects `SharedKernel.Presentation.Testing` (the only testing package referencing HotChocolate).

Recurring conventions in `16.Testing` worth knowing before starting any phase there.

**Testing packages depend only on what they fake (WO-086 package split).** The former capability folders of one `SharedKernel.Testing` package are now 20 packable Testing-tier packages — the core `SharedKernel.Testing` (Foundation + Model references only: `Clocks/`, `Logging/`, `Execution/` `TestRequestContext`/`FakeRequestContext`, `Fakers/`, `Domain/`, `Contracts/`, …; locked by `CoreTestingPackage_DependsOnlyOnFoundationAndModelPackages`) and 19 `SharedKernel.{Capability}.Testing` packages — plus the non-packable `SharedKernel.Testing.Internal` (`Containers/` Testcontainers fixtures, EF Core/Npgsql/audit helpers, MassTransit `TestHarnessFactory`). Each per-capability package references only the capability it fakes (+ core where needed). Even when two need near-identical plumbing (e.g. core `SharedKernel.Testing`'s `Communication/ActivityRecorder` and `SharedKernel.Application.Testing`'s `ApplicationPipelineTestHarness` both need an `ActivityListener`), the rule forces independent, duplicated implementations rather than a new cross-testing-package edge. Don't "fix" this by punching a hole in the isolation rule — it's load-bearing.

**Tests routing decision rule** (the testing package's own nested `.Tests` project vs. "prove it in the owning domain's suite"; the old `SharedKernel.Testing.SelfTests` no longer exists): does the type implement an interface owned by another domain, AND does that domain's own `.Tests` project actually (not theoretically) consume the fake today? Both must be true to route there. In practice almost every fake in this domain's history has routed to its own testing package's suite first, because the owning domain's suite never actually referenced the new fake yet, even when a live `ProjectReference` existed. Re-check this at implementation time every single time; don't assume from a prior session's routing decision for a similar-looking type.

**`⚑` Blocked vs `○` Pending is a load-bearing distinction unique to hard cross-domain compile-time blockers**, first needed at P-269/WO-043. Soft "design ahead of schedule" (a fake needs only a literal name string from an undesigned upstream, e.g. P-226/WO-036's `ActivityRecorder`) never blocks — Core proceeds unblocked, marked `○`. Hard blockers (a fake must `: IInterfaceName` against a package that is a genuinely empty placeholder `.csproj`, verified on disk) get `⚑` in Core/Tests/Docs task tables, with a Cross-Domain Dependencies row citing the exact upstream phase key that must land first (e.g. `08.Storage`'s `SK.08.Core`). **Once the upstream phase ships, the corrected action is to flip those tasks straight back to `○` Pending as a pure state-correction** — not to `●`, since flipping to `⚑`→`○` only means "no longer blocked," not "implemented." Actually writing the code remains a separate Core/Tests/Docs-phase task.

**Design phase can be a pure re-verification pass with zero `.cs` changes.** When a Design phase's tasks are all "Design"/"Confirm"/"Scope-lock" against an already-fully-drafted target shape (drafted by testing-arch-planner in a prior session), the implementer's job is to re-read the owning domain's live source and either confirm zero drift or correct it — never to write `InMemoryFileStorage.cs` etc. during Design. Confirmed this against a 96-task Design phase (D-79–D-96, WO-043) where the entire phase closed via documentation-only edits + one `dotnet build` verification (no code changes possible to break).

**Historical changelog entries are corrected via annotation, not silent rewrite.** When a later pass finds a prior changelog entry stated something now known to be wrong (e.g. "IFileStorage has ten members" when it actually has nine), the established pattern (confirmed against `08.Storage`'s own precedent, 2026-07-16 entry) is to append a parenthetical note to the stale entry pointing at the corrected entry below it, and add a new changelog entry with the correction — never delete or rewrite the historical line outright.

**All `Containers/` fixtures (now in `SharedKernel.Testing.Internal`) validate Docker connectivity eagerly in their own constructor, not lazily at `InitializeAsync`.** `MinioBuilder`/`PostgreSqlBuilder`/`RedisBuilder`/`RabbitMqBuilder.Build()` all throw `System.ArgumentException` immediately if no Docker daemon is reachable — confirmed identically across all four fixtures (2026-07-18). Practical consequence when writing/running `Containers/` tests without Docker available: even the "property throws `InvalidOperationException` before `InitializeAsync`" tests fail (with the Docker exception, not the expected one) — it isn't only the full-lifecycle test that needs Docker. When Docker isn't available in the working environment, run `dotnet test --filter "FullyQualifiedName!~Containers"` to get a clean signal on everything else, and say so explicitly rather than silently skipping verification.

**When checking whether the `HotChocolate.Data`/`GreenDonut.Result<T>` ambiguity (see `feedback_greendonut_result_ambiguity`) applies to a new file, check that specific project's own package references — it does not propagate through `ProjectReference`.** `SharedKernel.Testing.SelfTests.csproj` referencing `SharedKernel.Testing.csproj` does NOT inherit the latter's `HotChocolate.Data`-driven global usings; bare `Result<T>` is safe in `SelfTests` even though it isn't inside the production package.

**A "Docs" phase in this domain is usually a diff, not a from-scratch write.** Implementers here write substantial XML doc comments inline while implementing the Core phase, not deferred. When picking up a Docs-phase task (e.g. DO-17/DO-18), first read the actual current `.cs` files and check each bullet in the phase spec against what's already there — expect most bullets to already be satisfied, and the real work to be finding the 1-2 specific missing details (confirmed 2026-07-18: DO-17/DO-18 needed only two small additions — the `InitializeAsync` bootstrap-mechanism walkthrough and the "first `Storage/` folder" fact — everything else was already accurate from the Core-phase pass).

**`state-map-phase`'s root-mode Phase Backlog auto-close (Step S8a) has a "Case 3: skip entirely" rule for any phase key whose `Maps to Root Phase` is a plain lifecycle name (Design/Scaffold/Core/Tests/Docs/Published) with no `Root Backlog ID` column** — which is every phase key `16.Testing` has (`SK.16.Design`…`SK.16.Published`, no 4th column). Taken literally this would mean a WO's root `### P-NNN` Phase Backlog entries (e.g. P-268/P-269) never auto-close when the sub-domain finishes. **But the established, repeated precedent in this exact domain's own root changelog is to manually flip them to `● Complete` anyway** — confirmed for P-226 (WO-036), P-244/P-245 (WO-040), P-258 (WO-041), and now P-268/P-269 (WO-043), each accompanied by a `Phase Backlog P-NNN → ● Complete` changelog line. Don't follow Case 3 literally when closing out a WO that fully completes `16.Testing` — check the root changelog for how the same phase-key shape was handled last time and match it. **Only do this at FULL domain completion (Published), not at a single mid-way phase promotion** (e.g. Core finishing while Tests/Docs are still pending) — confirmed 2026-07-28 closing WO-049's `SK.16.Core`: the root Phase Backlog entry for P-300 was correctly left untouched (still `◐ Dispatched`) since Tests/Docs remained pending; only the Domain Summary Board row and root changelog got the `Core`/`●` update.

**The Phase Backlog auto-close precedent (line above) also applies to this domain's own DEPENDENT WO-specific fake-update phases** (`16.Testing`'s own P-306/WO-050, P-335/WO-053, P-352/WO-054, P-355/WO-055 — phases dispatched TO `16.Testing` to keep a fake in sync with another domain's newly-shipped capability, not phases FOR `16.Testing`'s own net-new folders). Confirmed a fourth time closing P-355/WO-055's DO-37 (2026-08-11): root `### P-355` was manually flipped to `● Complete` with every acceptance criterion checked and cited, exactly mirroring P-306/P-335/P-352's own entries (all found already `● Complete` with `[x]` boxes when checked). Do this at the SAME session that finishes the domain's last task for that WO, never left dangling — even though these phase keys map to a plain lifecycle name (`Docs`) with no `Root Backlog ID` column and Step S8a's literal Case 3 text says to skip.

**A DO-task's own carried-forward "remains a future session's task" note can itself be stale by the time that future session actually runs — always re-verify the live file, never trust the note at face value.** Confirmed 2026-08-11 on DO-37/P-355: the task row said the `CLAUDE.md` marker removal "remains a future `SK.16.Docs` session's own task," written during the Core-phase (C-108–C-110) pass — but that same Core-phase pass's OWN changelog entry (written moments later, same session) already recorded doing the marker removal. The task-row note was never updated to match. Grep for the literal marker text across the live file before assuming a "remains outstanding" note is still true — it may already be done.

**Root `state-map.md`'s Domain Summary Board can silently drift from what its own changelog claims.** Confirmed 2026-07-28: a prior session's changelog entry read "16 → Scaffold (●) — promoted from SK.16.Scaffold (41/41)" but the actual Domain Summary Board row 16 still read "Published" (the stale text from the *previous* full-domain-completion pass, WO-046) — the row edit apparently never landed even though the changelog claimed it did. Always read the ACTUAL current row content before trusting a changelog line that says a promotion already happened; fix the row in place (with a note in the new changelog entry) rather than assuming it's already correct. Also remember to recalculate the root `## Overall Progress` table's per-phase-name counts (e.g. `● Published` / `● Core`) when a domain's Current Phase changes — these must stay in sync with the Domain Summary Board's 18 rows.

**`FakeContentHasher` (C-92/P-300/WO-049) needed one deviation from the literal design draft**: the draft said it "mirrors `Sha256ContentHasher` exactly (real `SHA256.HashData(byte[])`/`.HashData(Stream)`/`.HashDataAsync(Stream,...)`)" — but a fake that also wants a `.HashedContent` introspection list (recording every payload ever hashed) cannot call the BCL's `Stream`-based overloads directly, since they never expose the raw bytes they read. Resolved by fully buffering the `Stream`/async-`Stream` input into a `byte[]` first, then hashing that buffer via the `byte[]` overload — same real `SHA256` algorithm, same output, but not literally "streaming" the way production is. This mirrors `InMemoryFileStorage`'s own `ReadAllBytesAsync` buffering pattern for the identical "need to record content for introspection" reason. General lesson: when a design says "mirrors X exactly" but also demands introspection over a `Stream`-based member, expect the two goals to conflict and buffer instead of calling the `Stream` overload verbatim — document the deviation explicitly in both `CLAUDE.md` and `state-map.md` rather than silently doing it.

**Reusable technique: proving a fake's `Dispose()` genuinely disposes cached resources, without reflection.** When a fake caches `IDisposable` resources per key (e.g. `Cryptography/FakeAsymmetricKeyProvider` caching `RSA`/`ECDsa` instances in a `Dictionary`) and `Dispose()` disposes every cached original but doesn't clear the dictionary, the cleanest proof that disposal really happened is behavioral, not reflective: call `Dispose()`, then call the same accessor again for an already-cached key — the cached-branch code path (e.g. `existing.ExportParameters(true)`) throws `ObjectDisposedException` because the cached original really is gone. This beats reflecting into the private cache and checking some disposed-flag (many BCL disposable types, including `RSA`/`ECDsa`, expose no public `IsDisposed`-shaped property at all) — confirmed while writing `Cryptography/FakeAsymmetricKeyProviderTests.cs` (T-56/P-300/WO-049).

**Before starting any phase, check `git status`/`git diff` for uncommitted work that already matches the phase brief — a dispatch prompt can be stale relative to the actual working tree.** Confirmed 2026-07-29 picking up `SK.16.Docs` (DO-27–DO-29, P-300/WO-049): the phase brief said "26/29 done, DO-27–29 pending," but `git status` showed five `Cryptography/` `.cs` files plus both `state-map.md` files already modified and uncommitted, with the exact DO-27 `<remarks>` additions already written and the state-map already marked all 29/29 `●` (root Domain Summary Board row and Phase Backlog P-300 already flipped too) — a prior session had done the real work but never committed or reported. The correct move was NOT to redo the edits, but to independently re-verify each claim against live source (grep for the `TEST-ONLY` string across all 7 fakes; read `FakeContentHasher.cs`/`FakeFeatureManager.cs`/both `Add*` extension classes directly), confirm `dotnet build` was clean, do the one genuinely-missing step (`16.Testing/CLAUDE.md` brain sync — the Interface Contracts blocks and changelog had NOT been touched even though state-map.md had), and then commit everything as one phase-closing commit. This is a stronger version of `feedback_check_already_done_before_working.md`'s lesson: it isn't just the state-map's task table that can be stale relative to reality — the whole working tree can already contain a finished-but-uncommitted phase.

**A "design-ahead" phase's Docs task can be a genuine zero-diff audit-and-close, not just a small diff.** Confirmed 2026-08-24 closing DO-46/P-438/WO-065: `testing-arch-planner` had already written the FULL target-shape documentation into `16.Testing/CLAUDE.md` at the same Design-phase dispatch pass that added D-209–D-212 — the `Caching/` Interface Contracts block (with `[STATUS: Planned]` marker), the D-211 audit-finding blockquote, the `## DI Registration` code sample plus narrative justification, and the Folder/Namespace Map row were all already present, word-for-word matching the Docs task's own listed sub-requirements. This goes one step further than the existing "Docs phase is usually a diff, not a from-scratch write" lesson above — here there was no diff at all, only a changelog entry. Always grep/read the target section of `CLAUDE.md` FIRST before assuming a Docs task needs new prose; this domain's arch-planner increasingly front-loads design-ahead documentation at dispatch time rather than deferring it to the Docs phase.

**Cryptography fakes reusing a REAL production DI-key constant (e.g. `CryptographyServiceCollectionExtensions.RsaSignatureServiceKey`/`EcdsaSignatureServiceKey`) is safe and expected** — it's the same abstraction package the fake already depends on (`SharedKernel.Cryptography`), not a sibling-folder or cross-domain reference. Only the wrapping DI-extension *class name* needs to differ (`FakeCryptographyServiceCollectionExtensions` vs. the real `CryptographyServiceCollectionExtensions`) to avoid a static-member ambiguity — the constants themselves are reused verbatim, never redeclared.

**The `SharedKernel.Testing.csproj` `GreenDonut`/`HotChocolate.Error` ambiguity (see `feedback_greendonut_result_ambiguity`) extends to bare `Error` too, confirmed again in `Cryptography/FakeSymmetricEncryptionService.cs` (P-300/WO-049)** — any fake in this project that constructs a new `Error.Xxx(...)` directly (not merely receiving one from an existing `XxxErrors` factory class) must fully qualify as `SharedKernel.Primitives.Errors.Error.Xxx(...)`. This was the first fake in the package's history to need this specific pattern (prior fakes always got their `Error` from an existing `StorageErrors`/`SearchErrors`/`WorkflowErrors`-style factory, never constructed one directly) — `SharedKernel.Cryptography`'s own `CryptographyErrorCodes` is only an error-*code*-string constants class, not an `Error`-factory class, so the fake had to build the `Error` itself.
