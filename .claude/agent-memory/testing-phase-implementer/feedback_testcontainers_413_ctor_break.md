> WO-086 (2026-09): `SharedKernel.Testing` was split into 20 packable Testing-tier packages (core `SharedKernel.Testing` + 19 `SharedKernel.{Capability}.Testing`) plus the non-packable `SharedKernel.Testing.Internal` (containers, EF/Npgsql/audit helpers, MassTransit harness); `SharedKernel.Testing.SelfTests` became each package's own nested `.Tests` project. Paths and project names below are pre-split history; the technique/lesson still applies.

Confirmed 2026-07-19 (16.Testing SK.16.Scaffold, S-27, WO-044): bumping `Testcontainers.PostgreSql`/`.Redis`/`.RabbitMq`/`.Minio` from `4.1.0` to `4.13.0` was flagged by the dispatching brief as "the riskiest task" and told to actually verify rather than assume a drop-in — that caution was justified. The bump obsoleted each builder type's parameterless constructor (`RedisBuilder()`, `MinioBuilder()`, `RabbitMqBuilder()`, `PostgreSqlBuilder()`) in favor of a `ctor(string image)` overload, surfacing 4 new `CS0618` warnings in the four existing `Containers/*ContainerFixture.cs` files (each of which used `new XBuilder().WithImage("...")`).

**How this was diagnosed and fixed, in order:**
1. Ran `dotnet build -c Release` immediately after the version bump — did not just edit the `.csproj` and move on. The warning list is the ground truth for "did this break anything," not the release notes or an assumption.
2. Located the new package version's own shipped XML doc comments at `~/.nuget/packages/{package}/{version}/lib/net10.0/{Package}.xml` (Bash/Glob against the local NuGet cache — no internet access needed) to confirm the exact new constructor signature (`ctor(string image)`) existed and took the same "repository:tag" string, before writing any fix.
3. Rewrote `new XBuilder().WithImage("image:tag")` → `new XBuilder("image:tag")` in all four affected files — same pinned image, zero behavioral change.
4. Verified with a REAL Docker-backed test run (Docker was available in this environment) — `SharedKernel.Testing.SelfTests`' `Containers/` suite, 12/12 passing — not just a compile check, since a constructor swap on a container-builder type is exactly the kind of thing that could silently change runtime behavior even if it compiles.
5. Also did downstream compile-only checks on two other domains' `.Tests` projects that directly consume these fixtures (`SharedKernel.Storage.S3.Tests`, `SharedKernel.Presentation.SignalR.Tests`) since the public contract (`ConnectionString`/`ServiceUrl` etc.) was unchanged but a genuine consumer existed.
6. Independently checked whether the SAME obsolete-constructor pattern would apply to two NOT-YET-IMPLEMENTED fixtures in the same package (`Testcontainers.Elasticsearch`'s `ElasticsearchBuilder`, and the base `Testcontainers` package's own `ContainerBuilder`) by reading their 4.13.0 XML docs before any code for them was written — found the identical `ctor(string image)` pattern, and corrected the not-yet-implemented design prose in `CLAUDE.md` so a future Core-phase session doesn't write code that's obsolete on day one.

**How to apply:** whenever a phase spec says "bump this package pin" — even phrased as routine Scaffold/metadata work — always `dotnet build` immediately after and actually read the warning diff, don't trust that a version bump within a task described as "explicit version-alignment, no functional change" is risk-free. If Docker (or the equivalent real backend) is available in the environment, prefer a real runtime verification over a compile-only one for anything that constructs infrastructure objects, since a constructor-signature swap is exactly the class of change a compile-only check can miss behaviorally. When the bump affects a shared package used by not-yet-implemented sibling code in the same file/folder, check whether the same class of break will hit that unwritten code too, and pre-correct the design documentation — cheaper to fix once in the docs now than to have a future session rediscover the same CS0618 independently.
