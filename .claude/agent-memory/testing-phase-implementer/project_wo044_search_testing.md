**Status as of 2026-07-20: SK.16.Design (121/121), SK.16.Scaffold (28/28), and SK.16.Core (69/69) are all `●`, promoted to root.** SK.16.Tests (T-48-T-51) and SK.16.Docs (DO-19-DO-22) remain to fully close WO-044.

**Core-phase implementation (C-64-C-69) landed 2026-07-20** -- see [[feedback_greendonut_result_ambiguity]] and [[feedback_testcontainers_413_ctor_break]] for cross-cutting gotchas hit again in this pass. Key decisions:

- **Meilisearch image**: `getmeili/meilisearch:v1.20.0`. **Elasticsearch image**: `docker.elastic.co/elasticsearch/elasticsearch:9.4.2` -- chosen to exactly match the platform's pinned `Elastic.Clients.Elasticsearch` 9.4.2 NuGet client (same-version client/server lockstep). Both confirmed to exist via `docker manifest inspect <image>` run directly against the real registry (no web browsing tool was available in the implementation environment, so this is the verification method to reach for whenever a phase spec says "pick a real tag, don't guess").
- **ElasticsearchContainerFixture credential sourcing**: the `Testcontainers.Elasticsearch` module (4.13.0) exposes a public `WithPassword(string)` fluent method and public static constants `ElasticsearchBuilder.DefaultUsername`/`.DefaultPassword` (both literally `"elastic"`), but NO `WithUsername` method and `ElasticsearchContainer` exposes NO `GetPassword()`/`GetUsername()` accessor. Since the fixture never calls `WithPassword`, the module's own default is both what gets configured and the only observable value -- so `.Username`/`.Password` just return the module's own public constants directly, never queried from the running container. Confirmed via a custom .NET `System.Reflection.Metadata` PE-reader inspector (see below) since `Assembly.LoadFrom` + `GetTypes()` throws `ReflectionTypeLoadException` on a Testcontainers assembly outside a full app context.
- **Real Elasticsearch startup takes ~18-20s** even after the container reports "ready" per Testcontainers' own wait strategy -- this is the documented `testcontainers-dotnet#955` race (HTTP listener up != cluster bootstrap done). `ElasticsearchContainerFixture.InitializeAsync` closes this with an explicit post-`StartAsync` poll loop against `GET /_cluster/health?wait_for_status=yellow&timeout=1s` (Basic auth, `ServerCertificateCustomValidationCallback = (_, _, _, _) => true` for the self-signed cert), using `Task.Delay` only as the retry interval inside a real poll loop -- confirmed NECESSARY (not just theoretical) by a real-Docker smoke test where the loop actually ran for ~18s before observing `status:"green"`.
- **GreenDonut.Result<T> ambiguity hit hard in `InMemorySearchIndex.cs`/`InMemorySearchIndexProvisioner.cs`/`InMemorySearchProviderDescriptor.cs`**: every `ISearchIndex<TDocument>`/`ISearchIndexProvisioner`/`ISearchProviderDescriptor` method returns a generic `Result<T>`, so ALL of them needed `SharedKernel.Primitives.Results.Result<T>` fully qualified. Also newly discovered: bare `Error` (not just `Result<T>`) is ALSO ambiguous in this same csproj, against `HotChocolate.Error` -- any method returning `Error?`/`Error` needs `SharedKernel.Primitives.Errors.Error` fully qualified too. Plain non-generic `Result` remains unambiguous, as previously documented.
- **PowerShell `Get-Content -Raw` / `Set-Content -Encoding utf8` mangles UTF-8 em-dashes into mojibake** (`—` becomes `â€”`) when used for bulk regex find/replace on a UTF-8-with-BOM `.cs` file in Windows PowerShell 5.1 -- the default encoding assumption during the read is wrong. Fixed with `perl -CSD -i -pe 's/\x{00e2}\x{20ac}\x{201d}/--/g'` (perl IS available in this Windows environment, unlike python3). Lesson: never bulk-edit a C# file's `Result<T>` qualification via a blind PowerShell regex across the WHOLE file including doc comments -- the naive pattern `Result<` also matches `Result</c>` inside XML doc-comment closing tags (`</c>` starts with `<`), producing an incorrect qualification inside prose text, not just code. Prefer the `Edit` tool's per-site replacement, or write the file correctly from the start via `Write`.
- **The closed-8-node `SearchFilter` switch expression (no discard arm, per the interface's own documented "no discard" convention) produces a `CS8509` "not exhaustive" Roslyn warning** -- and this is NOT unique to the fake. A clean rebuild (`rm -rf obj bin && dotnet build`) of `SharedKernel.Search.Meilisearch` reproduces the IDENTICAL warning on `MeilisearchFilterCompiler.Compile`, normally hidden by incremental-build caching (a `dotnet build` with nothing changed skips re-emitting warnings for unchanged files). This is a pre-existing, unaddressed characteristic of the shipped `09.Search` codebase, confirmed empirically rather than assumed. Also confirmed: **`TreatWarningsAsErrors` is NOT actually wired into any `.csproj` in this repo** (no `Directory.Build.props` exists at all) despite root `CLAUDE.md`'s aspirational framing referenced by a prior session's memory note about the Testcontainers CS0618 bump -- warnings do not currently fail any build in this repo. Don't assume this claim from a prior memory note without re-verifying; it turned out to be aspirational, not actually enforced.
- **Tenant-scope-missing check extended to `CountAsync`/`DeleteByFilterAsync`/`EnumerateAsync`**, beyond D-108's literal text (which scoped the 5-step fail-loud pipeline to `SearchAsync` only) -- justified by reading the REAL `MeilisearchIndex<TDocument>` source directly (`09.Search/SharedKernel.Search.Meilisearch/Index/MeilisearchIndex.cs`) and finding all four operations (Search/Count/DeleteByFilter/Enumerate) share one `CompileWithTenantScope`-equivalent helper that fails closed on `TenantScope.None` against a tenanted index -- but `GetAsync` does NOT get this upfront check, even in the real adapter (it does its own separate, simpler tenant-field-mismatch-after-fetch handling). This is a good example of: when a design spec (D-97-D-121) is silent/ambiguous on a specific method's behavior, go read the ACTUAL shipped implementation of the interface the fake is imitating, not just the abstract interface contract -- the real adapter's own internal consistency is often the best tiebreaker.
- **No `System.Reflection.Metadata`/`PEReader` available directly in Windows PowerShell 5.1** (not in the default assembly search path) -- when needing to inspect a NuGet package DLL's exact public API surface (method signatures, public const field values) without loading/executing the assembly, spin up a tiny scratch `dotnet run` console app referencing `System.Reflection.Metadata`/`System.Reflection.PortableExecutable` (both ship in the .NET 10 SDK) and read the PE metadata directly -- far more reliable than `Assembly.LoadFrom` (throws on missing transitive deps) or grepping raw bytes for UTF-16 string literals.
- Verified via: (a) real-Docker smoke test for both `Containers/` fixtures (health checks, authenticated calls, pre-init `InvalidOperationException` guards -- all passed); (b) a 65-assertion throwaway functional smoke harness for all three `Search/` fakes + both DI extensions, covering every write/read/tenant-scope/field-role-validation/facet/sort/paging/pagination-ceiling/`SimulateFailure`/`Seed`/`Reset`/provisioner/descriptor/DI-resolution path -- all passed; (c) full `SharedKernel.Testing.SelfTests` regression, 344/344 passing, zero regressions. Both throwaway harnesses were deleted after use, per the "never leave a throwaway test file behind" rule.
- No consuming-domain regression check applied -- net-new capability, zero existing reference anywhere in `09.Search` as of this session (confirmed via `grep`). `09.Search`'s own `SK.09.Tests` T-13-T-17/T-21-T-26 (blocked on these exact two fixtures) are now unblocked for a future `09.Search` session to pick up -- not this domain's job to write those tests.
