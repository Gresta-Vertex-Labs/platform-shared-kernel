> WO-086 (2026-09): `SharedKernel.Testing` was split into 20 packable Testing-tier packages (core `SharedKernel.Testing` + 19 `SharedKernel.{Capability}.Testing`) plus the non-packable `SharedKernel.Testing.Internal` (containers, EF/Npgsql/audit helpers, MassTransit harness); `SharedKernel.Testing.SelfTests` became each package's own nested `.Tests` project. Paths and project names below are pre-split history; the technique/lesson still applies.

Rule: for any new BCL-cryptography-heavy test-fixture builder in `16.Testing` (DPoP proofs, X.509 certs, CRLs, JWS/JWT-shaped output), write and RUN a throwaway smoke-test console app (reference the real `SharedKernel.Testing.csproj`, exercise every new type, assert real invariants — signature verification, chain validation, ASN.1 parsing) in the scratchpad, then delete it, BEFORE marking the Core-phase task done. A clean `dotnet build` proves the code compiles against the assumed API shape; it proves nothing about whether that shape is actually correct or whether the crypto is genuinely valid.

**Why:** `MtlsTestCertificateBuilder`'s `.AsRevoked()` path (16.Testing, WO-060/P-391, C-120, 2026-08-17) compiled cleanly on the first attempt against a guessed `CertificateRevocationListBuilder.Build(X509Certificate2, BigInteger, DateTimeOffset, HashAlgorithmName, X509SignatureGenerator, DateTimeOffset?)` signature — plausible-looking, wrong. Reflecting the real type (`typeof(CertificateRevocationListBuilder).GetMethods()`, printed as a throwaway console app) showed only two real overloads exist:
1. `Build(X509Certificate2 issuerCertificate, BigInteger crlNumber, DateTimeOffset nextUpdate, HashAlgorithmName hashAlgorithm, RSASignaturePadding? rsaSignaturePadding = null, DateTimeOffset? thisUpdate = null)` — RSA-only; cannot sign an ECDsa-keyed CA at all (`RSASignaturePadding` has no ECDsa equivalent).
2. `Build(X500DistinguishedName issuerName, X509SignatureGenerator generator, BigInteger crlNumber, DateTimeOffset nextUpdate, HashAlgorithmName hashAlgorithm, X509AuthorityKeyIdentifierExtension authorityKeyIdentifier, DateTimeOffset? thisUpdate = null)` — the ECDsa-capable one, via `X509SignatureGenerator.CreateForECDsa(ecdsaPrivateKey)`.

Overload 2 additionally throws `CryptographicException: The provided certificate does not have a Subject Key Identifier extension.` from `X509AuthorityKeyIdentifierExtension.CreateFromCertificate(issuerCert, includeKeyIdentifier: true, includeIssuerAndSerial: true)` unless the issuer certificate itself carries an `X509SubjectKeyIdentifierExtension` — a fact undiscoverable by reading the `Build` signature alone; only running the code against a real self-signed ECDsa CA surfaced it. Fix: add `new X509SubjectKeyIdentifierExtension(request.PublicKey, critical: false)` to the CA's own `CertificateRequest` before `CreateSelfSigned`.

**Discovery 3 (surfaced during the T-83 Tests-phase pass, writing the CONSUMING test that parses `.RevocationList`, not the Core-phase builder itself):** `CertificateRevocationListBuilder.AddEntry(byte[] serialNumber, ...)` does NOT re-apply the DER sign-safety zero-pad byte that `X509Certificate2.GetSerialNumber()`'s own certificate-embedding path applies. Concretely: `X509Certificate2.GetSerialNumber()` returns bytes in little-endian order and appends a trailing `0x00` pad byte when the value's most-significant (last-in-LE) byte has its high bit set, to keep the DER `INTEGER`'s big-endian encoding non-negative. `AddEntry` just reverses the caller's raw LE bytes into the entry's DER content — with NO equivalent pad-byte insertion. Net effect: a revoked entry's serial number can legitimately be encoded as a strictly-invalid-per-ASN.1-signed-semantics `INTEGER` (leading content byte's high bit set, no `0x00` pad), so `AsnReader.ReadInteger()`'s signed `BigInteger` conversion throws `OverflowException` when later trying `.ToByteArray(isUnsigned: true, isBigEndian: true)` on it (a negative `BigInteger` has no unsigned representation). This is a real, reproducible quirk of `AddEntry` itself — not a bug in the consuming code that built the CA/leaf. Fix (test-side only, never touch the production builder): read the entry's raw `INTEGER` content bytes directly by manually parsing the DER tag+length (skip `AsnReader.ReadInteger()`'s `BigInteger` conversion entirely), and compare raw bytes against `reverse(strip-trailing-pad-if-present(GetSerialNumber()))` rather than going through any signed/unsigned `BigInteger` round-trip.

**How to apply:**
1. Before writing crypto-fixture code from a design doc's prose description of an API, reflect the REAL type in a 5-line throwaway console app (`typeof(X).GetMethods()`, print signatures) rather than trusting memory or the design doc's assumed shape — this caught the wrong `Build` overload before any production code was written.
2. After writing the fixture builder, write a second throwaway program that actually exercises it end-to-end with real assertions (ECDsa `VerifyData` against the embedded JWK; `X509Chain.Build()` with `CustomTrustStore`/`ExtraStore` for a chained cert; `AsnReader.ReadSequence()` on CRL bytes) — a clean compile is not evidence the crypto is correct, only that the types line up.
3. Delete both throwaway programs before finishing (this domain's own container-fixture-smoke-test discipline — "never leave a throwaway test file behind" — extends naturally to any complex fixture builder, not just `Containers/`).
4. Record the real, corrected API shape in the CLAUDE.md NOTE block for the type (not just "it works now") — a future implementer reading the design doc alone would hit the identical wrong-overload mistake otherwise.
5. This discipline applies just as much at Tests-phase (proving a Core-phase builder) as it does at Core-phase (building it) — Discovery 3 above was found only when a LATER session wrote the consuming test's own DER-parsing code, not when the original builder shipped. Never assume a clean Core-phase smoke-test run means every possible consumer-side interaction (e.g., parsing the builder's byte-array output with a strict, spec-compliant parser) is also safe — write and run the actual proof.
