**Trigger:** Direct user request, 2026-08-13 — "Analys the @12.Security/ packages... so important for us... Do we need more packages. Do we need more features. Need to refactor anything. We need gold standard developer friendly packages on security." Explicitly asked to take time and add as many phases as warranted.

**Context that made this notable:** `12.Security` was the platform's *only* domain that had never had a WO-050-through-WO-056-style deep-dive review since its original 2026-06-02 build-out. Its Domain Summary Board row 12 "Summary: Done" ("Both packages packed... 46 tests passing") was the thinnest, least-detailed entry of any `●` Published domain — a signal worth noticing before even reading the code.

**The critical finding (P-366):** `SecurityClaimTypes.Email`/`.Role` and `OidcUserContext.Username` resolve claims via legacy `ClaimTypes.*` long-form URIs. Since .NET 8, `JwtBearerHandler` defaults to `JsonWebTokenHandler` with `MapInboundClaims = false` — real tokens from Entra ID v2.0, Auth0, Okta, Keycloak all carry short claim names (`email`, `name`, `roles`) by default. This means `Email`/`Username`/`Roles` silently resolve to null/empty against the realistic default token shape, with zero exception and zero log line. The existing `12.Security.Oidc.Tests` suite's fixtures construct `ClaimsPrincipal` using the long-form `ClaimTypes.*` shape directly — the one shape that still works — which is exactly why this had never been caught. `TokenValidationParameters.NameClaimType`/`RoleClaimType` were also never set, so ASP.NET Core's own `[Authorize(Roles=...)]` attribute (if any consuming service reaches for it instead of `IUserContext.HasRole`) is equally broken by the same root cause. `UserId`/`"sub"` was unaffected only because `"sub"` already happens to be a short name — luck, not design.

**The second architecturally significant finding (P-367):** `OidcUserContext` forces `IsAuthenticated = false` on any token lacking a human `Guid`-parseable subject claim — which silently rejects legitimate OAuth2 client-credentials (service-to-service/M2M) tokens, a routine call shape `11.Communication`'s typed clients exist to make in a "hundreds of microservices" platform. No prior domain had ever addressed machine-to-machine identity at all. Fixed by introducing a single coherent `IdentityKind` discriminator (`Anonymous`/`User`/`ServicePrincipal`/`System`) on `IUserContext` rather than scattering ad hoc booleans — `P-369`'s `SystemUserContext` (for Temporal/MassTransit/Hangfire background execution, previously indistinguishable from `AnonymousUserContext`) reuses the same enum. This is a deliberate design consolidation: three separate capability gaps (service-principal recognition, permission/scope authorization, system-context distinction) could have each proposed their own new `IUserContext` boolean; instead `IdentityKind` was designed once as shared infrastructure and `Permissions`/`HasPermission` (P-368) was kept as a separate additive member since it isn't a discriminator.

**Full phase list (WO-057, P-366–P-374), all `12.Security` unless noted:**
- P-366 — claim-mapping fix (configurable per-IdP, `TokenValidationParameters` wiring, defensive roles-claim parsing). Foundational, no deps.
- P-367 — `IdentityKind` + service-principal recognition. Depends on P-366.
- P-368 — `Permissions`/`HasPermission` scope-based authorization (OAuth2 `scope`/`scp`). Depends on P-366.
- P-369 — `SystemUserContext` sentinel using `IdentityKind.System`. Depends on P-367.
- P-370 — new `SharedKernel.Security.ApiKey` sibling provider package (pre-shared-key auth, composes alongside JWT Bearer, built on `01.Core/SharedKernel.Cryptography`'s constant-time comparison — kept as its own package rather than folded into `.Oidc` since API-key auth isn't an OIDC concept, per the platform's `.Abstractions`+`.{Provider}` split discipline). No deps.
- P-371 — structured `[LoggerMessage]` security audit logging, EventId range 12000-12999 — this domain had adopted zero logging despite WO-041's platform-wide mandate. Depends on P-366, P-367, P-369.
- P-372 — docs refresh (domain-root README was literally empty; cross-domain recipes into 05.Application/06.Persistence/07.Messaging/13.ServiceDefaults.MultiTenancy/17.Workflows). Depends on P-366-370.
- P-373 (00.Governance) — mechanize three hard rules documented since inception but never enforced: `03.Domain` must never reference `ITenantProvider`; no raw `IHttpContextAccessor`/`ClaimsPrincipal`/`HttpContext` injection outside Oidc/ApiKey; `IUserContext`/`ITenantProvider` never singleton. No deps.
- P-374 (16.Testing) — update `FakeUserContext`/`FakeTenantProvider` (confirmed already implementing the REAL `SharedKernel.Security.Abstractions` interfaces, not a local seam) for the expanded surface. Depends on P-367, P-368, P-369.

**Important cross-domain relationship confirmed during investigation (not a finding, but worth remembering):** `13.ServiceDefaults/SharedKernel.MultiTenancy`'s `ClaimTenantResolutionStrategy` deliberately *delegates* to `12.Security.Oidc`'s `OidcTenantProvider` rather than reimplementing claim parsing — no duplication exists there. `16.Testing` already had `FakeUserContext`/`FakeTenantProvider` in a `Security/` folder before this review (confirmed via file read, not assumed) — ruled out a redundant "add testing fakes" phase, only an "update existing fakes" one (P-374).

**Deliberately NOT dispatched (considered and cut):** OTel `Activity` tag/baggage for user identity (no precedent exists in `WellKnownTagKeys`/`WellKnownBaggageKeys`, and `14.Presentation`'s correlation-id middleware could already do this today by injecting `IUserContext` if it wanted to — not a `12.Security` gap); per-vendor convenience wrappers beyond Azure B2C (Auth0/Okta/Keycloak already work via the generic `AddSharedKernelSecurity`, Authority/Audience-driven); `RequireHttpsMetadata` (ASP.NET Core's own default is already secure, not a bug); refresh-token/token-issuance concerns (out of scope — this is a resource-server validation library, not an STS).

**Breaking-change posture:** `IUserContext` gains `IdentityKind` and `Permissions`/`HasPermission` — both explicitly flagged as intentional breaking interface changes in the phase text, justified by the same reasoning `04.Contracts`'s WO-052 `Envelope` rename used (still early in adoption — 46 tests, two packages, first review pass ever — cheaper to break now than after wider downstream uptake).
