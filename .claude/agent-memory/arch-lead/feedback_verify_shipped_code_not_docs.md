When asked to review a domain for quality/gaps/over-engineering — especially one that already looks polished (multiple closed work orders, extensive `CLAUDE.md` prose, all-green test counts, `●` on the Domain Summary Board) — do not evaluate from the documentation alone. Read the actual `.cs` source files for the behaviors/classes in question, and read the test suite's helper methods and inline comments, not just the assertions.

**Why:** In [[project_wo039_application_review]], `05.Application` had three prior work orders (WO-035/036/038), thorough XML docs, and 120 passing tests — and still shipped a load-bearing bug (`AddFireAndForgetDispatch()`'s guard behavior unconditionally blocks its own background consumer's dispatch, so fire-and-forget commands silently never execute when wired exactly as documented). The bug was findable in under five minutes by reading `FireAndForgetGuardBehavior.cs` next to `FireAndForgetBackgroundConsumer.cs` and noticing they both go through the same `IPipelineBehavior<,>` registration with no way to distinguish caller context. The test suite's own `BuildConsumerDirectProvider` helper contains a comment admitting it avoids registering the guard specifically to route around this — i.e., the bug's shadow was already visible in the tests, but nobody connected it to the "Complete" status three work orders later.

Separately, an acceptance criterion from a prior "Complete" phase (P-232: "`FailureResponseFactory` relies on `IResultOfT<T>` constraint instead" of reflection) was checked off but not actually true when the code was read — the shipped version still uses `Type.GetInterfaces()`/`MakeGenericType()`/`GetMethod()`/`Invoke()`, just a different reflection API than the one the platform's own governance rule (SK0012) checks for, so it slipped through both the acceptance review and the mechanical enforcement.

**How to apply:** For any domain review request — especially "is this gold-standard," "find bad practices," "check for gaps" — budget time to actually open and read the implementation files for the core mechanisms (pipeline behaviors, dispatchers, builders), not just the domain's own `CLAUDE.md`/`state-map.md`. Cross-check acceptance criteria phrased as absolutes ("eliminates X," "zero Y") against the actual diff, not the checkbox. Also check whether a domain's own test helpers contain workaround comments (`"we wire it this way to avoid Z"`) — those are often a confession that a real bug exists but was routed around rather than fixed.
