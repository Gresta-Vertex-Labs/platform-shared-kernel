> WO-086 (2026-09): the three idempotency contracts became one `SharedKernel.Idempotency.Abstractions.IIdempotencyStore` (purpose-keyed); `SharedKernel.Application.Behaviors` is now `.Application.Pipeline`; `ISchedulerServiceProbe`, the 13→19 grant and `SharedKernel.ServiceDefaults.Scheduling` were deleted (`IReadinessProbe` named `scheduler`); numbered layering is replaced by tiers.

WO-070–WO-073 (2026-08-26): batch 2 of a 3-batch architectural review of missing SharedKernel packages. P-454–P-467 queued in root `state-map.md`. First batch in this review series to introduce brand-new numbered capability domains (18 and 19) rather than folding new work into existing ones.

**Capability 5 (WO-070) — Idempotency stores, new domain `18.Idempotency`.** The user posed a genuine layering puzzle: `05.Application.Behaviors` declares `IIdempotencyKeyStore`/`IIdempotencyResponseStore`, `07.Messaging.Abstractions` declares `IIdempotencyStore`, and nothing implements any of them. Neither owning domain can host a concrete Redis/EF store itself (`05.Application` may never reference concrete infra; `07.Messaging` is hard-barred from `SharedKernel.Caching.*` and capped at `01–04`), and WO-054 had already explicitly declined shipping one inside `07.Messaging` for exactly that reason. **Resolution: a brand-new domain numbered above both (18) can legally reference down into both `05.Application.Behaviors` and `07.Messaging.Abstractions` under the plain downward-reference rule — no grant needed.** Considered and rejected hosting it in `13.ServiceDefaults` instead (which already has a `01–12` ceiling covering both, and real precedent — the Key Vault provider — for shipping a concrete infra implementation there): rejected because idempotency storage is a substantial, freestanding capability comparable in engineering weight to `08.Storage`/`02.Caching.Redis.DistributedLocking`, and folding it into ServiceDefaults would blur that domain's "host composition wiring" identity. Two provider packages shipped (`.Redis`, `.EfCore`), each implementing all three cross-owned interfaces — a package implementing contracts owned by two *different* lower domains simultaneously is a legitimate, if novel, shape. No `.Abstractions` package of its own (it implements others' contracts). No new `13.ServiceDefaults` readiness-probe grant needed — store health is already covered by the existing Redis/DB connectivity probes, so this domain needed zero grant machinery at all, unlike domain 19 below. Key design requirement: the public `HasProcessedAsync`/`MarkProcessedAsync` shape is check-then-act at the interface level, so true atomicity must be closed *inside* the store implementation (atomic conditional reservation via Redis `SET NX PX` or Postgres `INSERT ... ON CONFLICT DO NOTHING`, with an in-flight TTL that expires on crash to preserve the platform's existing fault-vs-failure key-consumption semantics). Fail-closed on store unavailability by default, mirroring the platform's conservative-default convention.

**Capability 6 (WO-071) — Audit trail, sibling packages in `06.Persistence` + `05.Application`, no new domain.** Unlike idempotency, `06.Persistence`'s layering ceiling (`01–05`) already legally covers everything needed. Shipped: `IAuditTrailWriter`/`IAuditQueryService` in `.Abstractions` (structurally immutable — no update/delete member exists on the contract at all), `.EfCore` implementation with a `SaveChanges`-time guard rejecting any `Modified`/`Deleted` `AuditRecord` plus hash-chain tamper-evidence via `01.Core`'s already-shipped `IContentHasher` (accepted as in-scope specifically because it was nearly free — the primitive already existed for this exact purpose), and an opt-in `05.Application` `IAuditableRequest`/`AuditingBehavior` mirroring `IRequiresDualApproval`'s exact shape with its own local `IAuditTrailWriter` seam (never a compiled reference to `06.Persistence`, same bridge pattern as `IAuthorizationContext`/`IUnitOfWork`). **Explicitly declined: feeding audit records automatically off the existing `AuditInterceptor`** — would make every `SaveChanges` silently produce a compliance record with no application-layer visibility into what "before/after" means; the platform's established convention (WO-045 Domain Invariant #5) is opt-in for consequential side effects. **Explicitly declined: retention/archival policy** — deferred as a real, separate capability with per-jurisdiction variance.

**Capability 7 (WO-072) — Human notifications, sibling package in `15.Integration`, no new domain.** Extended rather than spun off into a new domain because the domain's real identity — "outbound delivery to a destination outside our control, with resilience/signing/retry/observer discipline" — is shared by webhooks and notifications even though payloads differ. Folder Map row 15's description was broadened accordingly. First providers: **SendGrid (email) and Twilio (SMS), deliberately chosen over AWS SES/Azure Communication Services** — reasoned that the platform's existing Azure-leaning (`12.Security.Oidc`→B2C) and AWS-leaning (`08.Storage.S3`) choices are each justified by a vertical-specific or technical-standard argument that notifications lack, so committing to either cloud's native service would entangle this domain in the platform's cloud politics for no reason; cloud-neutral REST SaaS providers sidestep that. Attachments routed through `08.Storage.Abstractions` object references (a new, ordinary downward reference added to 15.Integration's layering line, since `08 < 15` — not a grant, just a previously-unused legal reference). **Explicitly declined for this phase: push notifications** (device-token/platform-payload scope is materially larger than text delivery) **and bounce/complaint handling** (requires an *inbound* webhook receiver, a capability that doesn't exist anywhere on the platform yet).

**Capability 8 (WO-073) — Scheduling, new domain `19.Scheduling`.** Distinguished from `17.Workflows` on a clean boundary: scheduling answers "did it fire, exactly once, across replicas" (no determinism/replay needed); workflows answer "did this multi-step process complete, surviving crashes/deploys mid-step." Reuses Quartz's standalone `CronExpression` class only (already a transitive dependency via pinned `MassTransit.Quartz`) for parsing — deliberately never adopts Quartz's full `IScheduler`/clustered `JobStore`, which would stand up a second persistence story competing with `06.Persistence`. Cross-replica exclusivity via the already-shipped `IFencedLock` (`02.Caching.Redis.DistributedLocking`), optional with a startup `Warning` if omitted. Single package, no `.Abstractions` split — explicitly using the same "one provider today" reasoning already established for `SharedKernel.Cryptography`/`.Compression`/`.Guards`. `TenantScope` on job definitions is **nullable**, a deliberate documented deviation from the platform's mandatory-non-defaulted-tenant-scope convention (Search/Intelligence/Workflows/Idempotency all make it mandatory) — reasoned that a cron registration is a system-level startup act, and genuine per-tenant fan-out belongs inside the job body iterating its own tenant directory, not the scheduler spawning N tenant executions. **Needed its own new, separately-named `13→19` readiness-probe grant** (P-466), independent of and never widening the WO-047 `17.Workflows` grant — the second time this exact grant pattern has been earned independently rather than reused by analogy, exactly as root `CLAUDE.md` demands. Distinguished the *telemetry* wiring (`WithSchedulingTelemetry`, P-465) from the *readiness-probe* wiring (P-466) as two separate phases specifically because `AddSource`/`AddMeter` take a bare string and need no compiled reference/grant at all, while the probe requires calling a real interface method and does need one — this same string-vs-compiled-reference distinction silently applies to the already-shipped `WithIntegrationTelemetry`/`WithWorkflowTelemetry` and is worth checking before assuming any higher-numbered-domain wiring needs a grant.

**Governance phases declined across all four capabilities**, each with the same reasoning: the invariants needing enforcement (atomic dedup, structural audit immutability, no raw Quartz client leak) are either not mechanically detectable via Roslyn (hand-rolled dedup/cron-loop patterns have no clean syntactic signature) or are better enforced as a runtime guard inside the implementing package itself (the `SaveChanges` immutability guard) than as a static analyzer. Consistent with [[project_wo054_messaging_goldstandard_review]]'s precedent of declining unenforceable rules rather than adding weak ones.

**Tooling limitation discovered:** the `state-map-phase` skill is hardcoded to "always exactly 18 rows" and a `domain: 00–17` parse range in its own format contract — it cannot register a genuinely new domain. Domains 18 and 19's Domain Summary Board rows, Active Work, and Overall Progress counts were added/updated directly by hand instead of via the skill, with an explicit note left in `state-map.md` flagging that the skill needs a one-time update before it can promote rows 18–19 through their phase lifecycle via the normal `/dispatch-phase`/sub-map-mode flow. Future sessions creating domain 20+ will hit the same wall until that skill is patched.
