> WO-086 (2026-09): `IEncryptionKeyProviderProbe`, `IMessageBusProbe` and the other probe primitives became `IReadinessProbe`; the named layering grants and their enforcement rules (`ServiceDefaultsWorkflowLayeringRules`/`ServiceDefaultsSchedulingLayeringRules`) were deleted — no grants exist any more; `Application.Behaviors` is now `Application.Pipeline`.

**Finding 1 — 01.Core Azure Key Vault provider ships no readiness-probe primitive, half-blocking P-449.**
`AzureKeyVaultEncryptionKeyProvider` (`01.Core/SharedKernel.Cryptography.KeyVault.Azure`, shipped P-447/WO-068) exposes only `GetCurrentKeyAsync`/`GetKeyAsync`/`GenerateDataKeyAsync`/`UnwrapDataKeyAsync` — no `ProbeAsync`-shaped member, unlike every other infra-provider domain (`06.Persistence`/`08.Storage`/`09.Search`/`10.Intelligence`/`07.Messaging`/`17.Workflows`/`19.Scheduling`). Decision: **ACCEPT**, new phase **P-487** (01.Core) — add an optional probe companion contract in `SharedKernel.Cryptography` (mirrors `07.Messaging`'s `IMessageBusProbe`/`MessageBusHealth` split), implemented by the Azure provider via a cheap, non-cryptographic Key Vault reachability check (key metadata, never wrap/unwrap/sign/verify). Explicitly reasoned this is **not** analogous to [[project_wo045_intelligence_buildout]]/WO-047's LLM-orchestration probe retraction — that retraction turned on the only honest LLM reachability signal being a real *billed, rate-limited generative call*, forbidden as hidden/automatic behavior; a Key Vault metadata read is cheap and non-generative, same class as `06.Persistence`'s DB round-trip probe. P-449 (13.ServiceDefaults, already-existing phase, left `◐` Dispatched by the implementer pass) had its `Depends on` updated to add P-487.

**Finding 2 — `CacheInvalidationBehavior` evicts BEFORE the transaction commits (real defect in shipped WO-036 code).**
`ApplicationBehaviorsBuilder` registers `TransactionBehavior` (1st/outermost) → `AuditingBehavior` (2nd) → `CacheInvalidationBehavior` (3rd/innermost). MediatR makes first-registered outermost, so `CacheInvalidationBehavior`'s post-`next()` eviction runs *before* `TransactionBehavior`'s post-`next()` `SaveChangesAsync` — contradicting the behavior's own XML doc ("a confirmed commit, never a speculative one"). Hazard: a concurrent read repopulating the cache from pre-commit state between eviction and commit leaves the cache stale forever. Note `AuditingBehavior`'s inside-Transaction position is *correct* as-is (staged writes must land in the same atomic `SaveChangesAsync`) — this is not a "flip all three" fix, only `CacheInvalidationBehavior` needs to move outside `TransactionBehavior`. Decision: **ACCEPT**, **P-488** (05.Application) fixes the registration order + adds a real-composed-pipeline regression test; **P-489** (00.Governance) mechanically locks the corrected ordering via a real-executed-pipeline test, mirroring `SK.00.CacheEncryptionAndRedisValidationLock`'s technique. Same defect *class* (design-doc step numbering ≠ DI registration order) had already bitten `AuditingBehavior` once during P-458 — worth locking mechanically now that it's recurred.

**Finding 3 — `13.ServiceDefaults`→`17.Workflows` readiness-probe layering grant (WO-047) has zero mechanical enforcement.**
The sibling `19.Scheduling` grant is enforced (`ServiceDefaultsSchedulingLayeringRules.OnlyReachesSchedulerProbeTypes`, shipped same pass); the older `17.Workflows` grant never was — `SharedKernelLayeringRules.WorkflowsReferencesOnlyCoreContractsAndApplication` constrains the wrong direction (17→down, not 13→17-upward), and `WorkflowTopologyRules.cs` only mentions the grant in a doc comment. Decision: **ACCEPT** verbatim per the reporter's own design constraints — **P-490** (00.Governance), a deliberately **separate** rule (root CLAUDE.md explicitly forbids reasoning about the two grants by analogy or merging them into a shared/parameterized helper). Implementation note carried into the phase: likely needs both an exact-type-name predicate (not namespace ban — permitted probe types may share a namespace with an internal impl type, as the Scheduling case did) and a walk of compiler-generated nested/state-machine types (since the real consumption site is `async`).
