> WO-086 (2026-09): `SharedKernel.Application.Behaviors` is now `SharedKernel.Application.Pipeline`; `MediatRDomainEventDispatcher` was deleted (native `DomainEventDispatcher` via `AddSharedKernelDomainEvents()`); MediatR is referenced only by `SharedKernel.Application.Mediator.MediatR`.

WO-039 (2026-07-03): user asked for a full gold-standard review of `05.Application` (SharedKernel.Application + SharedKernel.Application.Behaviors) — bad practices, over-engineering, refactor candidates, missing features. This domain had already been through three work orders (WO-035/036/038) and looked "done" (Core+Tests ● on the board). Reading the actual shipped `.cs` files (not just `CLAUDE.md`/`state-map.md` prose) surfaced four real, previously-undetected issues that documentation alone had missed:

1. **Confirmed functional bug**: `ApplicationBehaviorsBuilder.AddFireAndForgetDispatch()` registers `FireAndForgetGuardBehavior<,>` globally against the open-generic `IPipelineBehavior<,>` in the same call that registers `FireAndForgetBackgroundConsumer`, which dispatches via `ISender.Send(...)`. The guard can't distinguish the consumer's own internal dispatch from external misuse — it always throws, the consumer's catch-all swallows it and logs `Error`. Net effect: fire-and-forget commands never execute when wired exactly as documented. The test suite's own `BuildConsumerDirectProvider` helper has a comment admitting it wires the consumer *without* the guard specifically to avoid this — i.e., the bug was known at the code level but never surfaced as an issue.
2. **Acceptance-criteria theater**: P-232 (WO-038) claimed `FailureResponseFactory` eliminated reflection via an `IResultOfT<T>` constraint. The shipped `ResultOfTDispatcher.BuildFactory` still uses `Type.GetInterfaces()`/`MakeGenericType()`/`GetMethod()`/`Invoke()` — real reflection, just invisible to governance's SK0012 rule because that rule matches `MethodInfo.MakeGenericMethod` by exact IL call-target name, and this code calls `Type.MakeGenericType` instead (a different API). No `[RequiresUnreferencedCode]` annotation either, despite being trimming-unsafe. **Lesson: when a phase's acceptance criteria say "reflection eliminated," read the diff — don't trust the box being checked.**
3. **Governance/domain handoff gap**: `00.Governance`'s WO-036 (P-225) and WO-038 (P-235) built `ReflectionGuardRules`, `ApplicationPipelineRules`, `PipelineOrderAssertion`, and `MetricsInstrumentationRules` *specifically* for 05.Application, explicitly documented as "05.Application's responsibility to invoke against its own real assembly" — but 05.Application never did. Confirmed via `grep` returning zero hits for these type names anywhere under `05.Application/`. The root Domain Summary Board's own "Summary: Next" for row 00 was already pointing at this exact gap (outcome tag retrofit) — the platform had already flagged its own gap and nobody had picked it up.
4. **Design gap, not a bug**: `IdempotentCommandBehavior` always returns `Error.Conflict` on a duplicate key, even when the original attempt succeeded — meaning it cannot serve the actual real-world purpose of idempotency keys (safe retry after an ambiguous network outcome, à la Stripe/AWS). Documented in-code as "a deliberate scope boundary," which is defensible for an MVP but not gold-standard. Proposed an opt-in, backward-compatible response-replay extension to the local seam rather than changing default behavior.

**Why this matters for future reviews**: this domain had 3 prior work orders, passing tests, and extremely thorough prose documentation — and still had a load-bearing bug (#1) that would silently break in production for any consumer who used the feature exactly as documented. High documentation density does not correlate with correctness; only reading the actual shipped code (plus the test suite's own workarounds/comments, which often confess the bug) reliably catches this class of issue. See [[feedback_verify_shipped_code_not_docs]].
