WO-061 (2026-08-19, direct user request): gold-standard/big-fintech architecture review of `13.ServiceDefaults` (`SharedKernel.ServiceDefaults` + `SharedKernel.MultiTenancy`). Verdict: UPGRADE. Dispatched P-393 through P-401 (WO-061), all `○` Pending — none implemented yet as of this entry.

**Why this matters:** this is the fourth domain this review cycle (after `12.Security` WO-057/058/060, `02.Caching` WO-050, `06.Persistence` WO-051/053) where a domain whose own `CLAUDE.md`/`state-map.md` reads as fully "Published"/gold-standard turned out to have a real, source-verified security defect once someone actually read the `.cs` files instead of trusting the brain's prose. [[feedback_verify_shipped_code_not_docs]] applies here as strongly as anywhere in the repo.

**The two real security bugs found (both source-verified line-by-line, not inferred):**
1. `TenantResolutionOptions.StrategyOrder` defaults to `[Header, Claim, Database]` (`13.ServiceDefaults/SharedKernel.MultiTenancy/Resolution/TenantResolutionOptions.cs`). `TenantResolutionMiddleware` takes the first strategy that resolves and stops. `HeaderTenantResolutionStrategy` trusts a raw, unsigned `X-Tenant-Id` header via bare `Guid.TryParse` — no auth check, no restriction to unauthenticated/API-key callers. Net effect: an authenticated JWT request carrying a legitimate tenant claim can have its tenant silently overridden by an unsigned header for a *different* tenant — a default-on cross-tenant impersonation vector, present since the domain's original Core phase (WO-027) with no prior review catching it. Fix dispatched as P-393: reorder default to `[Claim, Header, Database]` — safe because `ClaimTenantResolutionStrategy` returns `null` for unauthenticated/no-claim requests, so the B2B/API-key use case (Header's documented intended audience) is unaffected.
2. `MtlsForwardedHeaderMiddleware` (`13.ServiceDefaults/SharedKernel.ServiceDefaults/Security/MtlsForwardedHeaderMiddleware.cs`) decodes and validates a forwarded mTLS client-certificate header with **no trusted-proxy/network restriction** — unlike ASP.NET Core's own `ForwardedHeadersOptions` (`KnownProxies`/`KnownNetworks`), there is nothing stopping a caller who can reach Kestrel by any path other than the intended ingress from forging the header directly. Same defect class as `12.Security.Mtls`'s WO-060-fixed default-posture bug. Fix dispatched as P-394: opt-in `TrustedProxies`/`TrustedNetworks` allowlist + startup `Warning` when unconfigured.

**Other six phases dispatched (hardening, not confirmed exploits):** P-395 zero `[LoggerMessage]` audit logging anywhere in this domain (confirmed by grep — a real gap given it composes tenant/mTLS decisions); P-396 `TenantResolutionOptions` has no `ValidateOnStart()`, so a typo'd `StrategyOrder` entry silently degrades to "always resolves `Guid.Empty`"; P-397 zero rate-limiting anywhere in the platform — new opt-in `AddSharedKernelRateLimiting()` wrapping BCL `Microsoft.AspNetCore.RateLimiting`, landing in 13 specifically because `14.Presentation` declined this in WO-058; P-398 zero secrets-manager integration anywhere — new opt-in `AddSharedKernelKeyVaultConfiguration()` (Azure Key Vault first, since `12.Security.Oidc` already targets B2C; AWS Secrets Manager/Vault as documented future providers); P-399 health endpoints unauthenticated with no network-exposure guidance (low actual risk today — no custom `ResponseWriter` wired, confirmed by reading `HealthCheckExtensions.cs` — but a latent regression risk); P-400 opt-in `ITenantStatusValidator` seam so Header/Claim-resolved tenants get an existence/active-status cross-check (today only `DatabaseTenantResolutionStrategy` has this, by construction).

**Governance companion:** P-401 mechanically locks the corrected P-393/P-394 defaults against silent regression, mirroring `SecurityContextGuard`/`SecureDefaultsAssertion` (P-373/P-390) — this is now a well-established platform pattern: harden a default, then immediately add a real-assembly-verified architecture test pinning it, in the same work order.
