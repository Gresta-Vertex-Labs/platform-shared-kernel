User is running a three-batch architectural review of missing SharedKernel packages, delivered as separate prompts. This is batch 1/3, covering four capabilities, each given its own Work Order per explicit instruction (WO-066–WO-069, not one shared WO) — matches this repo's established practice of theme-scoped WOs.

**All four verdicts, briefly:**

1. **Money → UPGRADE, lands in `03.Domain/SharedKernel.Domain`, NOT `01.Core`.** The user's prompt asked me to choose between `01.Core/SharedKernel.Primitives`, a new `01.Core` sibling, or `03.Domain`. Reasoned by direct analogy to [[project_wo034_cryptography_generalization]]: WO-034 renamed `IPasswordHasher` specifically to keep auth-domain vocabulary OUT of `01.Core`. `Money` is business/domain vocabulary the same way — it belongs where `ValueObject`/`SingleValueObject<TValue>` already live. No `.Abstractions` split (single concrete type, no infra-provider axis — same reasoning WO-034 used to decline splitting Cryptography). `IExchangeRateProvider` ships as a pure zero-I/O domain-owned port, implementation bridged by the consuming service. Percentage/interest helpers explicitly ruled OUT of scope. P-439 (03.Domain) → P-440 (06.Persistence EF conversion) → P-441 (16.Testing faker) → P-442 (00.Governance advisory-only, warning-severity analyzer for raw decimal+string currency pairs — deliberately NOT error-severity, since the detection is heuristic).

2. **Format validators → ACCEPT with upgrade, new `01.Core/SharedKernel.Validation` + `.FluentValidation` sibling.** Declined folding into `SharedKernel.Guards` (explicitly asked) — Guards' value is minimalism, a country-algorithm catalog would bloat it. Split into a FluentValidation-free core plus a thin adapter package, mirroring the "keep the core dependency-free, split the framework adapter" instinct already visible in this repo (Cryptography/Compression zero-dep posture). National ID validation is a pluggable per-country registry (TCKN as built-in default, given Turkey is the platform's primary market) — never hardcode one country as the only option. P-443 → P-444 (adapter) → P-445 (16.Testing checksum-correct sample generators).

3. **KMS key management → UPGRADE via a SOURCE CORRECTION, not a straightforward accept.** This is the important one to remember. The user's prompt claimed (with a specific file:line citation) that `IEncryptionKeyProvider` lives `internal sealed` inside `06.Persistence.EfCore`. **I verified this against actual source and it is FALSE.** `IEncryptionKeyProvider` is already a PUBLIC interface at `01.Core/SharedKernel.Cryptography/Symmetric/IEncryptionKeyProvider.cs`, and is already the shared seam consumed across `06.Persistence.EfCore` (`EncryptionOptionsKeyProvider`/`NullEncryptionKeyProvider` — just two implementations of it, not the interface's home), `15.Integration.Webhooks`, `16.Testing` (`FakeEncryptionKeyProvider` already exists), and `17.Workflows.Temporal`'s payload codec. The "extract it from 06.Persistence into 01.Core" framing the user proposed is simply wrong and must never be repeated in a future pass.
   - **The REAL gap, found by reading `IEncryptionKeyProvider.cs`/`CryptographicKey.cs` directly:** both interface members (`GetCurrentKey()`/`GetKey(string)`) are SYNCHRONOUS, and `CryptographicKey.Material` exposes raw key bytes only (direct-retrieval-only, no envelope-encryption mode). A real KMS/HSM (Azure Key Vault, AWS KMS) needs genuine network I/O — a synchronous contract structurally blocks any correct implementation (forces blocking-on-async). This is the actual, narrower, source-verified defect.
   - P-446 (01.Core, BREAKING): converts the interface to async/`CancellationToken`-aware, adds an additive envelope-encryption contract, adds a bounded-TTL caching decorator with tested fail-closed behavior. P-447 (01.Core): new sibling package `SharedKernel.Cryptography.KeyVault.Azure` (first vendor, given the platform's existing Azure Key Vault *configuration*-source precedent at `13.ServiceDefaults` P-398 and Azure B2C at `12.Security.Oidc` — explicitly NOT the same helper as P-398, which is an `IConfiguration` source, not a key provider). P-448 (06.Persistence): migrates EF Core's consumers onto the async contract, flagging the one real wrinkle — EF Core's `ValueConverter` pipeline is itself synchronous by EF Core's own design, so the phase needs a resolved-key-cache mechanism, never a blocking-on-async call inside that pipeline. P-449 (13.ServiceDefaults): new composition-root helper + readiness probe. P-450 (16.Testing): migrate the existing fake.
   - **Lesson reinforced:** this is exactly the [[feedback_verify_shipped_code_not_docs]] pattern — a user-supplied "gap analysis" with file:line citations still needs independent source verification before phases get written on top of it. The citation was real (the file exists) but the *conclusion drawn from it* (interface is internal/needs extraction) was wrong because the citation only showed one CONSUMER's implementation, not the interface's actual declaration site.

4. **TOTP/HOTP → ACCEPT the user's own suggested split, ratified as proposed.** Algorithm/generation/replay-guard half → additive to existing `01.Core/SharedKernel.Cryptography` (zero identity-stack dependency, same reasoning that already keeps password hashing and AES-GCM there rather than in `12.Security`). ASP.NET-facing enrollment/challenge/step-up-wiring half → new fifth `12.Security` sibling provider package `SharedKernel.Security.Totp` (alongside `.Oidc`/`.ApiKey`/`.Mtls`). The replay-guard contract stays with the generator (not split into Security) because the verifier needs it internally — splitting would create a circular dependency between the two packages. P-451 (01.Core) → P-452 (12.Security, depends on P-451) → P-453 (16.Testing, depends on both). Explicitly verified no new `14.Presentation` phase is needed — the existing `[RequireAuthenticationMethod]` attribute (WO-062/P-406) already matches on a generic AMR string, so a TOTP AMR value works with zero changes there; said so explicitly in the acceptance criteria rather than silently assuming it.
