name: feedback_split_phase_on_missing_upstream_fixture
description: How to handle a Tests-phase dispatch when a cross-domain test fixture (e.g. 16.Testing's MinioContainerFixture) the phase spec assumes exists has not actually been built yet
type: feedback
---

When a phase spec (or the storage-phase-implementer dispatch brief) says a set of tasks "depend on [some other domain]'s fixture," never trust that framing at face value — verify the fixture's actual existence on disk before planning work. In this session, the `SK.08.Tests` phase spec's own intro sentence said "Provider round-trip tests (T-05–T-16) depend on `16.Testing`'s MinIO Testcontainers fixture" — but the fixture (`Containers/MinioContainerFixture.cs`) genuinely did not exist yet: no `.cs` file, no `Testcontainers.Minio`/`AWSSDK.S3` package reference in `SharedKernel.Testing.csproj`, and `16.Testing/state-map.md`'s own `SK.16.Core` task `C-60` was still `○`. `16.Testing`'s own state-map explicitly anticipates this exact scenario and tells you how to verify it (grep `Containers/*.cs`, check the specific Core-phase task ID, don't just read the domain's `CLAUDE.md` prose).

**Why this matters:** the phase brief's task-range grouping ("T-05–T-16 are the container-backed tasks") is a summary, not a per-task spec. The individual task rows in `state-map.md` are the authoritative, more granular source — some tasks lumped into that range (DI-registration tests, options-validation tests) genuinely need no container at all, because they only exercise `ServiceCollection`/`BuildServiceProvider()` or a synchronous local operation (presign clamping). Blindly deferring every task in the stated range would have left 6 of 17 tasks (T-09/T-10/T-11/T-15/T-16 plus the never-container-gated T-17) undone for no real reason. Read each task's own literal description before deciding it's blocked — don't inherit the summary sentence's scope uncritically.

**How to apply:**
1. Verify the upstream fixture's existence directly on disk (`Glob`/`Grep` the actual `.cs` files and `.csproj` package references) — never trust a domain's own prose ("this is fully unblocked") without checking the concrete Core-phase task state too. A fixture can be fully *designed* (Design/Scaffold phases `●`) while its *implementation* (Core phase) is still `○` — these are different facts.
2. Re-read each individual task's own description in the phase's task table, not just the phase's intro summary — some tasks in a "container-gated" range may not actually need the container (DI/options tests; anything the domain's own Test Rules already sanctions mocking for, e.g. status-code-mapping tests where 403/500 are "hard to induce" against a real backend).
3. Implement everything genuinely unblocked to completion, including tests explicitly sanctioned to use mocking (check the domain's own `CLAUDE.md` Test Rules for phrases like "mock only for narrow error-mapping" — that's a deliberate, pre-approved exception, not scope creep).
4. Never hand-roll a competing ad-hoc version of the missing fixture inside the dependent domain's own test project — that duplication is exactly what centralizing the fixture in `16.Testing` (or whichever domain owns it) exists to prevent.
5. Mark only the tasks that truly need the missing piece as `⚑` Blocked (not `○`, which reads as "not started by choice" rather than "cannot start by necessity") — add a `Blocked` section entry naming the exact missing file/package/task-ID so a future session can re-check it precisely, and leave the phase key's overall state as `◐` (add a `⚑ Blocked` column to the Overall Progress table if the domain's table doesn't already have one — `16.Testing`'s own state-map already established this column format as precedent). Do **not** call `/state-map-phase` to promote the phase to root when it's only partially done.

See [[project_08storage_status]] for the concrete outcome this produced (10/17 done, 7/17 blocked) and the exact blocked task IDs.
