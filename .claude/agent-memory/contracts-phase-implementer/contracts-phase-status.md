## CRITICAL: breaking renames in 04.Contracts cascade into 16.Testing (platform-wide blast radius)
`16.Testing/SharedKernel.Testing` is referenced by literally every `.Tests` project in the repo (root CLAUDE.md Test Project Rules). It has its own `Contracts/EnvelopeAssertions.cs`(+`EnvelopeAssertionsTests.cs` in `.SelfTests`) that mirrored the exact same `using EnvelopeNs = SharedKernel.Contracts.Envelope;` alias workaround this package used to carry. **The moment C-08 landed, `SharedKernel.Testing` failed to build — which transitively fails every single domain's `.Tests` project**, not just this one's.

**Why this was in-scope to fix here, not deferred:** `16.Testing`'s own `CLAUDE.md`/`state-map.md` had ALREADY pre-planned this exact fix as its own task (C-101/T-65/DO-32, `⚑` Blocked "pending P-328 landing in code") — testing-arch-planner anticipated this transition during a prior WO-052/P-330 planning pass. The fix is purely mechanical (drop the alias, use `SharedKernel.Contracts.Envelopes` directly, unqualify `Envelope`/`Envelope<T>` everywhere in those two files) — no new capability, no judgment call. Applied it directly to unblock `dotnet test` for this session's own mandatory testing gate, since leaving it broken isn't a "different domain's problem to fix later" when it prevents verifying this domain's own Core-phase deliverables.

**What was NOT done:** `16.Testing/CLAUDE.md`/`state-map.md` were left untouched — formally closing C-101/T-65/DO-32 there is testing-phase-implementer's job, not this domain's. Only the two `.cs` files were edited (`16.Testing/SharedKernel.Testing/Contracts/EnvelopeAssertions.cs`, `16.Testing/SharedKernel.Testing/SharedKernel.Testing.SelfTests/Contracts/EnvelopeAssertionsTests.cs`).

**Lesson for any future breaking-rename phase in this domain:** before declaring a Core phase done, grep the WHOLE repo (not just `04.Contracts`) for the old symbol/namespace being renamed — `16.Testing`, `11.Communication.Rest`, and `consumer-verify` are the three known external consumers of `Envelope`/`Envelope<T>` (per contracts-arch-planner's own WO-052/P-328 changelog note). `11.Communication.Rest` (P-329) and `consumer-verify` (P-06, Published phase) were deliberately left broken/unbumped since they're explicitly separately-dispatched follow-on phases in the same WO — only `16.Testing` was fixed because its breakage is a hard, immediate blocker to THIS session's own `dotnet test` gate (every `.Tests` project ProjectReferences it), not a matter of choice.

## STJ null-serialization gotcha (test-level JsonSerializerOptions)
The test-level `JsonSerializerOptions` used throughout this package's tests only sets `PropertyNamingPolicy = JsonNamingPolicy.CamelCase` — it does NOT set `DefaultIgnoreCondition = WhenWritingNull`, even though `ContractsJsonContext`'s own `[JsonSourceGenerationOptions]` attribute declares that condition. Per the existing memory note on `[JsonSourceGenerationOptions]` not auto-applying naming policy through `TypeInfoResolverChain`, the SAME non-propagation applies to `DefaultIgnoreCondition`: a null property (`TenantId`, `NextCursor`) round-trips as a literal JSON `null`, not an omitted key, in test code. Don't assume "the context declares WhenWritingNull" means test JSON omits nulls — assert `"\"propertyName\":null"` is present, not absent, unless the test's own `JsonSerializerOptions` explicitly sets `DefaultIgnoreCondition` too.
