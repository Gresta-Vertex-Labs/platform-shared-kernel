## The gap
`00.Governance/SharedKernel.ArchitectureTests/SharedKernel.ArchitectureTests.Tests/ContractsPurityRulesTests.cs` tests all four `ContractsPurityRules` factory methods (`ContractsAssembliesHaveNoNonTrivialMethods`, `ContractsAssembliesHaveNoDomainTypeOnPublicSurface`, `ContractsAssembliesHaveNoResultTypeOnPublicSurface`, `IntegrationEventImplementationsMustBeSealed`) using **only contrived in-memory fixtures** (`CompileInMemory`). As of 2026-07-31 it has never once pointed any of these rules at the real, compiled `SharedKernel.Contracts.dll`, at any shipped version (1.0.0 through 2.0.0). Confirmed by direct read of that test file, not assumed.

## What was found (discovered while closing 04.Contracts's Published phase for WO-052/v2.0.0, verifying whether the new `CursorPagedList<T>` needed a `ContractsPurityRules` exemption)
Built a throwaway console harness (never committed to the repo — lived in the session scratchpad only) referencing both the real `00.Governance/SharedKernel.ArchitectureTests/SharedKernel.ArchitectureTests.csproj` and `04.Contracts/SharedKernel.Contracts/SharedKernel.Contracts.csproj`, then called each rule factory method directly against `typeof(SharedKernel.Contracts.Pagination.CursorPagedList<>).Assembly` and printed `.GetResult()`.

Results:
- `ContractsAssembliesHaveNoDomainTypeOnPublicSurface` and `ContractsAssembliesHaveNoResultTypeOnPublicSurface`: `CursorPagedList<T>` passes cleanly — same shape as `PagedList<T>`, zero exemption needed.
- `ContractsAssembliesHaveNoNonTrivialMethods`: **fails for essentially every type in the package** — `PagedList<T>` (`.Create`), `Envelope`/`Envelope<T>` (`.Ok`/`.Fail`), `EventEnvelope`/`EventEnvelope<TEvent>` (`.Wrap`), `ResultEnvelopeExtensions` (all four extension methods), and `CursorPagedList<T>` (`.Create`). Root cause: `NoNonTrivialMethodsPredicate`'s "trivial" allowlist (constructor / getter / setter / `op_*` operator / `ToString` / `Equals` / `GetHashCode` — per `00.Governance/CLAUDE.md`'s own documented predicate logic) has never included static factory methods or extension methods. `04.Contracts/CLAUDE.md`'s own purity contract explicitly sanctions "factory methods and computed properties" as the sole permitted non-trivial members — the rule's allowlist just never matched that contract. This is not new: it has been true since `PagedList<T>.Create` first shipped in WO-011/WO-012 (1.0.0). `CursorPagedList<T>` merely inherits the pre-existing false positive.
- `ContractsAssembliesHaveNoDomainTypeOnPublicSurface`'s exemption list (`.DoNotHaveName("EventEnvelope\`1")`) only names the **generic record** `EventEnvelope<TEvent>` — the sibling **non-generic static** `EventEnvelope` class (which holds the `Wrap<TEvent>` factory, itself carrying a `where TEvent : IDomainEvent` constraint) is not exempted and independently fails the same rule. Also pre-existing since WO-011.

## Why this wasn't fixed here
Both are `00.Governance`'s rule/predicate implementation, not a `04.Contracts` defect — out of this agent's jurisdiction (never edit `00.Governance` files). Recorded as a candidate follow-up for governance-arch-planner/governance-phase-implementer in both `04.Contracts/CLAUDE.md`'s changelog and root `state-map.md`'s Domain Summary Board row 04 (2026-07-31 entries). No `00.Governance` file was touched.

## How to apply
If a future phase spec says "confirm `ContractsPurityRules` passes" (or similar), don't take it at face value — the existing governance test suite provides no such confirmation for the real assembly. Re-run the empirical check: a tiny scratchpad console project with `ProjectReference`s to `00.Governance/SharedKernel.ArchitectureTests/SharedKernel.ArchitectureTests.csproj` and `04.Contracts/SharedKernel.Contracts/SharedKernel.Contracts.csproj`, calling each rule factory method against `typeof(SomeNewType).Assembly` and printing `.GetResult().IsSuccessful`/`.FailingTypes`. Expect `ContractsAssembliesHaveNoNonTrivialMethods` to still fail platform-wide until `00.Governance` actually widens `NoNonTrivialMethodsPredicate`'s allowlist — that failure is not evidence your new type did something wrong; check whether your new type appears in the failing-types list for the *other* three rules (domain-type/Result-type/sealed-integration-event), which are the ones that actually gate a genuine purity violation for a DTO with only factory methods.
