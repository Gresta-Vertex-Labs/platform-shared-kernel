WO-051's SK.03.Tests phase (T-31..T-39, 9 tasks) arrived at `○` Not Started in the state-map, but on inspection every one of the 9 test files/regions already existed with full coverage — written during the *prior* Core-phase session (C-38..C-46) alongside the production code, presumably so the implementer could verify its own implementation as it went. The Core-phase session's changelog entry never mentioned writing these tests, and the Tests-phase task rows were never checked off, so the state-map looked like 9 tasks of net-new work when in fact it was ~0.9 tasks (one genuine gap) plus 8 tasks of pure verification.

**Discoverable convention:** test files in `03.Domain/SharedKernel.Domain.Tests/` mark which task they satisfy via an XML doc comment directly above the class or above the relevant region, e.g. `/// T-35: P-310/WO-051 — ValueObject.TryCreate<T>/CheckRule tests...` or an inline `// --- T-31: P-307/WO-051 — Includes/StringIncludes composite propagation ---` region comment inside a shared file (multiple task IDs can live in one file, e.g. `SpecificationCompositionTests.cs` carries T-13, T-15, T-31, and T-39 all in one file). Grep the test project for the task ID (`T-31`, `P-307`, etc.) before assuming a Tests-phase task needs new code.

**Why:** Saves duplicate work and avoids accidentally writing a second, slightly-divergent test class for the same scenario. Also surfaces genuine gaps precisely — cross-checking the task's exact wording against the found tests (not just "a test file with this name exists") caught one real miss: T-35 required a `SingleValueObject<TValue>` subclass to exercise *both* inherited `ValueObject` helpers (`TryCreate` and `CheckRule`) directly, but the existing `PercentageValueObject` only exercised `TryCreate`. Fixed by adding a `CheckRule`-enforced business rule to that same subclass rather than writing a whole new test class.

**How to apply:** When starting any 03.Domain Tests-phase session, before writing a single new test: (1) grep `SharedKernel.Domain.Tests/` for each task ID and its `P-NNN`/`WO-NNN` tag, (2) if found, read the actual test bodies and diff them line-by-line against the task's specific acceptance wording (not just its title) — partial coverage is the common failure mode, not zero coverage, (3) only write net-new tests for genuine gaps, (4) still run the full suite and update state-map/changelog to reflect what was verified vs. newly added. See also [[project_wo009_design_closure]] for the parallel pattern in the Design phase (arch-planner pre-writes content; implementer verifies).
