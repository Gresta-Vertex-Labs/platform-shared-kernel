WO-053 (2026-08-03) dispatched six independent gold-standard-completeness phases (P-333 structured logging + tracing gap, P-334 config-section binding, P-336 Testcontainers fixture consolidation, P-337 soft-delete restore + command timeout, P-338 read-replica routing, P-339 pgvector nearest-neighbor ordering), all `○` Pending as of dispatch. Key reusable design decisions from this session:

**EventId sub-block assignment skips packages that never log.** The platform's "100-wide sub-block per package, in declaration order" rule (root CLAUDE.md Logging Conventions) does not mean every package in the domain's Packages table gets a slot — a package with zero `ILogger` consumers (e.g. `SharedKernel.Persistence.Abstractions`, a pure interface library) reserves none at all. The first package that actually needs one claims the first slot. Applied: EfCore (not Abstractions) claims `6000-6099`.
**Why:** Abstractions has no DI container, no `ILogger<T>` injection site, ever — reserving it a slot would waste range and mislead future contributors into thinking Abstractions logs something.
**How to apply:** Before assigning "the Nth package in declaration order" an EventId sub-block, check whether that package will ever construct/inject `ILogger<T>` at all. If PostgreSQL/Dapper start logging later, they claim `6100-6199`/`6200-6299` at that time, never retroactively renumbering `6000-6099`.

**`DbContextOptionsBuilder.CommandTimeout` is provider-neutral relational, not Npgsql-specific.** It lives in `Microsoft.EntityFrameworkCore.Relational` (already referenced by `SharedKernel.Persistence.EfCore`), unlike `EnableRetryOnFailure` (genuinely Npgsql-only, must live in the PostgreSQL package per P-320's precedent). Designed `EfCorePersistenceBuilder.WithCommandTimeout(int)` in EfCore, not on `UsePostgreSQL(...)`.
**Why:** Not every "database connection/command knob" is Npgsql-specific just because it configures database behavior.
**How to apply:** When facing an EfCorePersistenceBuilder-vs-UsePostgreSQL placement decision, check which NuGet package actually declares the extension method — don't default to "it goes in PostgreSQL, like retry did" by analogy alone.

**`ActivatorUtilities.CreateInstance<TContext>` constructs a second DbContext instance while reusing scope-ambient DI state.** Used for read-replica routing (P-338): build a SECOND `TContext` pointed at a different `DbContextOptions<TContext>` while still resolving the SAME scope's already-DI-resolved `AuditInterceptor`/`SoftDeleteInterceptor`/`ConcurrencyInterceptor` (and their live `CurrentUserContext`, WO-051/P-322) — `ActivatorUtilities.CreateInstance<TContext>(serviceProvider, replicaOptions)`, never a second `AddDbContext<TContext>()` call (conflicts with the first) and never bare `Activator.CreateInstance` (loses DI constructor resolution). Requires `Microsoft.Extensions.DependencyInjection` — the CONCRETE package, not merely `.Abstractions` — as a new EfCore `PackageReference`.
**Why:** Closes "second DbContext instance, same interceptor identity" cleanly — audit-field consistency between primary/replica reads is then automatic, zero extra plumbing.
**How to apply:** Reach for this whenever a future need arises to construct a second instance of a DI-composed type with one overridden constructor argument while still wiring the rest from the ambient scope.

**`IRestorableRepository<TAggregate,TId>` — compile-time-loose interface + runtime-enforced narrower constraint, mirroring `BulkSpecificationGuard`.** When a capability (soft-delete restore, P-337) applies only to a SUBSET of `TAggregate` (those implementing `ISoftDeletable`), and the generic base class (`EfRepository<TAggregate,TId>`) can't conditionally implement a narrower interface per closed-generic instantiation: declare the interface with the SAME constraint as `IRepository<TAggregate,TId>` itself, implement it UNCONDITIONALLY on `EfRepository<TAggregate,TId>` (exactly like `IBulkMutationRepository` already is), and enforce the real constraint via a runtime `is ISoftDeletable` guard throwing `InvalidOperationException` — never a parallel base-class hierarchy alongside `TenantedRepository<TAggregate,TId>`.
**Why:** A parallel `EfSoftDeletableRepository<TAggregate,TId>` base class was considered and rejected — it would force every consumer with a soft-deletable aggregate to remember to extend a different base class purely to gain one method; the runtime-guard approach is purely additive with zero migration cost.
**How to apply:** Reach for this pattern whenever a new repository capability applies only to aggregates satisfying some marker interface beyond `IAggregateRoot<TId>`.

**Cross-package `Specification<T>`-populating helpers must return the expression, never call `AddOrderBy`/`ApplyOrderBy` themselves.** `Specification<T>.AddOrderBy` (03.Domain) is `protected` — a static helper in a DIFFERENT package (e.g. `SharedKernel.Persistence.PostgreSQL`'s `VectorOrderingExpressions`, P-339) cannot call it directly (extension methods only see public members, and protected access requires being an actual subclass). Resolved by having the helper return the boxed `Expression<Func<TAggregate,object>>` value — the CONSUMER's own `Specification<TAggregate>` subclass wires it into its own protected `AddOrderBy` call from within that subclass's constructor, exactly how `KeysetSpecification<T,TKey>`/`PagedSpecification<T>` already populate protected members. No new `Specification<T>` base class was needed for pgvector ordering.
**Why:** General C# access-modifier constraint, not pgvector-specific — any future cross-package helper wanting to contribute to a specification's `Criteria`/`OrderBy`/`Includes` hits the identical wall.
**How to apply:** Design such helpers to return the expression/value, never to call the protected setter — the consumer's own spec subclass is always the one with legitimate protected access.

**Zero-reflection `Expression.Call` via typed-delegate-cast `.Method`.** To reference a known static method's `MethodInfo` in a hand-built expression tree without `Type.GetMethod`/`MakeGenericMethod`, cast a delegate of the exact matching signature and read `.Method`: `((Func<Vector,Vector,double>)VectorExtensions.CosineDistance).Method` — resolved entirely by the C# compiler at compile time. Used in `VectorOrderingExpressions.ByDistance` (P-339); reusable for any future expression-tree builder needing to invoke a known static/instance method AOT-safely.

**Testcontainers fixture-drift severity must be verified by grepping actual instantiation sites, never trusted from a phase input's framing.** P-336's input described "one drifted copy" in `PostgreSQL.Tests`; direct source inspection found SIX independently-drifted copies (four inline `IAsyncLifetime` test classes each spinning up their own container + one dead, never-instantiated `Fixtures/PostgreSqlContainerFixture.cs` + one more inlined in `Dapper.Tests`), plus four pre-existing `[Collection("PostgreSQL")]` tags with no matching `[CollectionDefinition]` anywhere in the assembly (confirmed via repo-wide grep) — sharing clearly intended but never wired up.
**Why:** "Defined" and "actually instantiated/used" are different claims; a phase input's severity framing is a starting hypothesis, not a verified fact — this mirrors WO-051's own repeated "verified against real shipped source, not assumed" discipline.
**How to apply:** For any future "consolidate/fix drifted X" phase, grep for every instantiation site of the drifted type across the whole domain before writing the Design task's scope — do not stop at the first copy found.
