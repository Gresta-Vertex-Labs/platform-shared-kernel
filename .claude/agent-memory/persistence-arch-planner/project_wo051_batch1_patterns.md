> WO-086 (2026-09): `SharedKernel.Persistence.PostgreSQL` was merged into `.EfCore` (P-558), which now references `.Npgsql` through a declared Adapter edge — the "EfCore must never reference Npgsql (layering rule)" premise of Pattern 1 no longer holds; `ITransactionalUnitOfWork`/`BeginTransactionAsync` were deleted (retry-safe `IUnitOfWork.ExecuteInTransactionAsync` in `SharedKernel.Execution.Transactions` is the only transaction API).

WO-051 (dispatched 2026-07-30, batch 1 of 2: P-315-P-320; batch 2 P-321-P-325 follows in a separate call) established several reusable architectural patterns for `06.Persistence`, all `○` Pending in state-map.md as of this writing (design-only, not yet implemented).

**Pattern 1 — "provider-neutral marking in EfCore + provider-specific realization in PostgreSQL"** (used twice: P-315 xmin concurrency, P-320 retry-on-failure).
**Why:** `SharedKernel.Persistence.EfCore` must never reference `Npgsql` (hard layering rule), but some genuinely-correct PostgreSQL behavior (`.UseXminAsConcurrencyToken()`, `EnableRetryOnFailure`) can ONLY be configured via Npgsql-specific extension methods reachable only from `SharedKernel.Persistence.PostgreSQL`. The original P-315 design (D-05, dating to WO-008) assumed a single provider-branching convention could live in EfCore — this is architecturally impossible and was never built, leaving a doc-drift defect (XML doc claimed a `ConcurrencyTokenConvention` existed; it never did) that shipped undetected for months.
**How to apply:** Whenever a "make X provider-aware" requirement surfaces for this domain, check FIRST whether the provider-specific half requires an Npgsql-only API. If so, split the design as: EfCore does the provider-neutral marking/flagging (e.g. `.IsConcurrencyToken()`, a stored options POCO), and `SharedKernel.Persistence.PostgreSQL` does the actual Npgsql wiring inside `UsePostgreSQL()` (which already has the Npgsql reference and already runs `IModelFinalizingConvention`s like `SnakeCaseNamingConvention` at the right lifecycle point). Never propose a "provider-branching convention inside EfCore" — that shape cannot exist without breaking the layering rule.

**Pattern 2 — method-level generic parameters on `ISpecificationEvaluator<T>` to avoid `TKey`-erasure reflection.**
`GetKeysetQuery<TKey>(IQueryable<T>, KeysetSpecification<T,TKey> spec)` was added as a method with its OWN generic parameter beyond the interface's `T` — mirroring the existing `GetProjectedQuery<TResult>` precedent (P-097). This means the evaluator never needs runtime type-detection/reflection to discover `TKey` for a `KeysetSpecification<T,TKey>` passed as a plain `ISpecification<T>` — the caller (`EfReadRepository.ListKeysetAsync<TKey>`, itself generic in `TKey`) always knows it statically. Consequence: a `KeysetSpecification<T,TKey>` passed to the ORDINARY `GetQuery`/`ListAsync`/`GetBySpecAsync` silently ignores the cursor and returns page 1 every time — this is a deliberate, documented trade-off (type safety over foolproofing), not an oversight.
**How to apply:** whenever a future spec shape needs an erased-at-the-interface-level generic parameter (like `TKey`), reach for a dedicated method-level-generic evaluator method + dedicated repository method FIRST, before reaching for reflection-based type detection.

**Pattern 3 — `ActivitySource` naming convention discovered in shipped code, not documented in any brain until this phase.**
`02.Caching.FusionCache/Implementations/FusionCacheService.cs` already ships `new ActivitySource("SharedKernel.Caching", "1.0")` (predates WO-050's P-304, which extends tracing to more of `02.Caching`, not the first instance). The convention is `new ActivitySource("SharedKernel.{DomainPackagePrefix}", "1.0")`. `06.Persistence`'s new one is `new ActivitySource("SharedKernel.Persistence", "1.0")` — this exact string is the coordination point for `13.ServiceDefaults`' paired phase P-326 (`WithPersistenceTelemetry`-shaped wiring). If any future domain adds its first `ActivitySource`, grep `02.Caching`/`06.Persistence` for this naming pattern before inventing a new one.

**Pattern 4 — EF Core retrying execution strategies vs. held-open explicit transactions is a genuine, hard incompatibility.**
`ITransactionalUnitOfWork.BeginTransactionAsync()` → caller-held `IPersistenceTransaction` handle → `CommitAsync()` cannot be made retry-safe by patching — EF Core requires the WHOLE transactional unit inside one `IExecutionStrategy.ExecuteAsync(...)` delegate, and control returns to arbitrary caller code between begin and commit in the handle-based shape. The resolution shipped in P-320's design: add a NEW `ExecuteInTransactionAsync(Func<CancellationToken,Task> operation, ct)` API (wraps `Database.CreateExecutionStrategy().ExecuteAsync(...)`, reuses existing begin/commit machinery including the P-105 deferred-dispatch-until-commit rule) as the retry-safe alternative, and add an UNCONDITIONAL guard to the OLD `BeginTransactionAsync()` (checks `IExecutionStrategy.RetriesOnFailure` — a genuine public EF Core API) that fails fast with an actionable, platform-specific message BEFORE EF Core's own less-actionable native exception would fire. The guard is unconditional (queries live EF Core state) so it protects a consumer who enabled retry directly via `UsePostgreSQL(...)` without ever calling the EfCore-side `.WithTransientFaultRetry()` convenience method.
**How to apply:** any future "make X retry-safe" request in this domain should reach for this same shape — a new callback-based API for the retry-safe path, plus an unconditional live-state guard on the old API, rather than trying to retrofit retry-safety onto a held-open-handle API.

**Doc-drift discovery method that found P-315's defect:** reading the actual shipped `.cs` source (`EntityTypeConfigurationBase.cs`, `TenantedRepository.cs`, `ConcurrencyInterceptorTests.cs`) rather than trusting CLAUDE.md prose was what surfaced this — the XML doc's claim (`ConcurrencyTokenConvention` exists) was internally consistent and plausible-sounding but simply false. Grep the actual codebase for a claimed type/member name before trusting any brain's description of "what already exists," especially for concurrency/security-adjacent claims.
