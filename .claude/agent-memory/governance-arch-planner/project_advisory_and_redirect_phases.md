Four phases processed together 2026-08-26 (P-486/WO-079, P-442/WO-066, P-476/WO-076, P-469/WO-074, in that order per the dispatching instruction) established three reusable patterns not seen before in this domain. Full detail lives in the four new phase blocks in `00.Governance/state-map.md` and the diagnostic entries in `00.Governance/CLAUDE.md` — this memory is the "why," not a restatement of the design.

**1. First Advisory diagnostic category (SK0034, `AmountCurrencyPairCoupling`).** Every prior rule in this registry is either already-enforced-at-Warning-pending-Error-escalation (SK0006/SK0007) or a permanent Warning-severity platform-wide prohibition. SK0034 is neither — it is a permanently-Warning, heuristic NUDGE with no escalation path, ever. When a future phase input frames a rule as "inherently heuristic... ships as advisory," don't default to declining it outright (P-442 was flagged by the dispatching agent as the most likely decline candidate in that batch) — evaluate whether the detection technique has a genuinely narrow, low-false-positive surface (same-type co-occurrence of a closed suffix list, syntax-only, no cross-type/cross-file reasoning). If narrow enough, ship it as Advisory with a MANDATORY empirical false-positive validation task against the repo's own real sources before the Tests phase closes, and a documented narrowing contingency if a real false positive turns up — that's what keeps "I judged this narrow enough" honest rather than asserted. Never let an Advisory-category rule's severity drift toward Error without a fresh design review — its whole justification for existing was accepting a heuristic no Error-severity rule on this platform could tolerate.

**2. A "redirect, not accept" phase (SK0033, Mapper enforcement).** WO-079/P-486's own root state-map framing was explicit: `arch-lead` declined the proposed `SharedKernel.Mapping` package outright (wrapping a compile-time source generator behind a runtime interface defeats the point) and dispatched ONLY the platform-wide-prohibition mechanization half to this domain. This is a different shape from every prior "mechanize an already-designed guard" phase in the `SecureDefaultsAssertion`-lock family — there is no producing-domain package to eventually depend on, ever, because none will ship. When a phase input says "no new package" and names a declined alternative, treat the analyzer as the ENTIRE deliverable, not a placeholder pending a future package — and don't invent a Cross-Domain Dependencies entry for a package that was deliberately never approved.

**3. Confirm "ungated from the start," don't just assume the root's stated dependency.** Every phase in the `SecureDefaultsAssertion`-lock family (SenderConstrainedCredentialGuard through CacheEncryptionAndRedisValidationLock, nine occurrences) found its stated cross-domain dependency had ALREADY SHIPPED by implementation time — a recurring "stale, re-verify" correction. SK0036 (`RawRpcExceptionConstruction`, WO-074/P-469) is the first phase in this lineage where the *design-time* analysis itself found the phase was NEVER actually gated in the first place: the root state-map said "Depends on: P-468," but the analyzer only needs semantic-model resolution of `Grpc.Core.RpcException`/`Grpc.Core.Status`, which live in the standalone `Grpc.Core.Api` NuGet package — independently available, no relationship to whether `SharedKernel.Presentation.Grpc` (P-468) has shipped. **Reusable lesson:** before writing a Cross-Domain Dependencies entry just because the root state-map names one, ask what the analyzer/rule actually needs to compile and test — a namespace-string exemption match, or resolution of a THIRD-PARTY type via its own NuGet package, needs no compiled reference to the producing SharedKernel package at all. Only write the dependency entry when something genuinely can't be built/tested without the real package (as SK0035 genuinely needs `01.Core`'s `SharedKernel.DataPrivacy` for its real-assembly test, even though its contrived-fixture tests don't, via WO-040/P-248's fully-qualified-metadata-name technique).

**How to apply:** the next time a phase input frames something as "advisory only," don't default-decline — check the false-positive surface honestly and consider a new Advisory category if it's narrow enough, mirroring [[sk-diagnostic-registry]]'s SK0034 entry. The next time a phase input says "no new package, arch-lead declined X," write it as a pure-analyzer phase with no future-package Cross-Domain Dependencies row. Before writing ANY Cross-Domain Dependencies entry, verify what the rule's own detection technique actually needs — not what the root state-map's "Depends on" line implies.
