`SK.00.SenderConstrainedCredentialGuard` (WO-058 P-383, authored 2026-08-13) mechanizes locality rules for TWO new sender-constraining credential mechanisms `12.Security` has planned but not yet built: DPoP proof validation (`P-376`, extends `SharedKernel.Security.Oidc`) and mTLS client-certificate validation (`P-377`, new `SharedKernel.Security.Mtls` sibling provider package). Both P-376/P-377 were dispatched to `security-arch-planner` in the same run and are UNBUILT as of this phase's authoring — see [[project_sk_diagnostic_registry]] for the SK ID ledger this phase does NOT touch.

**Key design decision — extends the EXISTING `SecurityArchitectureRules` class, not a new class.** Unlike `SK.00.EventEnvelopeConstructionGuard` (P-350), which deliberately created a new `ContractsLayeringRules` class instead of reusing `ContractsPurityRules`, this phase's own input explicitly said "extending SecurityArchitectureRules" — so the two new methods (`DpopProofValidationNeverDuplicatedOutsideOidc`, `ClientCertificateAccessNeverDuplicatedOutsideMtls`) were added as new methods on the P-373 class. Zero new SK ID for either — both are `ICustomRule` architecture-test predicates per the phase's own acceptance criteria (explicitly NOT Roslyn analyzers), following the same "boundary/regression rule, no ID" convention `SecurityArchitectureRules`'s first two methods already established.

**Detection techniques (both reuse existing Mono.Cecil techniques, no new one introduced):**
- `NoDpopProofValidationDuplicationPredicate` — TWO-surface match in one predicate (mirrors `NoTenantProviderReferenceInDomainPredicate`'s multi-surface shape): (a) `Ldstr "DPoP"` literal (reuses `HealthCheckTagIntegrityRules`'s Ldstr literal-collection technique), OR (b) a type reference to `System.IdentityModel.Tokens.Jwt.JwtSecurityTokenHandler`/`Microsoft.IdentityModel.JsonWebTokens.JsonWebTokenHandler` (reuses SK0301's raw-cipher-type-reference technique, applied to JWT-parsing types). Single exemption: `SharedKernel.Security.Oidc` — deliberately NO second forward-looking exemption prefix (unlike SK0031's two-namespace shape), since DPoP is exclusively an OIDC/JWT-bearer-adjacent concern, not spread across every identity provider.
- `NoRawClientCertificateAccessOutsideMtlsPredicate` — single-surface match on `Call`/`Callvirt` to `Microsoft.AspNetCore.Http.ConnectionInfo.get_ClientCertificate` (the `HttpContext.Connection.ClientCertificate` getter). Deliberately did NOT add a second broad "any `X509Certificate2` type reference" surface — `01.Core/SharedKernel.Cryptography`'s `IAsymmetricSignatureService` legitimately handles X.509-adjacent material for unrelated signing/verification, so a bare type-reference check would false-positive there. The property-getter match alone satisfies the acceptance criterion's "ClientCertificate/X509Certificate2" phrasing since the property IS typed `X509Certificate2?`. Single exemption: `SharedKernel.Security.Mtls`.

**Real-assembly status: UNVERIFIABLE/non-gating on this phase's own completion** (contrast with `SK.00.SecurityContextGuard`/P-373, where both target assemblies already existed at authoring time). Contrived fixture tests (T-292–T-298) are the only proof at authoring time; two GATING-once-unblocked real-assembly tests (T-299 vs P-376, T-300 vs P-377) are tracked as a new Cross-Domain Dependencies block, dispatched deliberately last in WO-058's run for this reason — mirrors the `SK.00.MagicStringGuard`/`SK.00.EfPropertyUsageGuard` not-yet-implemented-dependency precedent.

**Reusable lesson — proactive mechanization pattern:** this is the first phase in this domain explicitly framed as applying a PRIOR phase's own retroactive lesson (`SK.00.SecurityContextGuard`'s "documented-but-unenforced hard rules accumulate silent violations") proactively, before either target mechanism ships, rather than waiting for a future gold-standard review to discover drift. Worth reusing this framing whenever a domain's arch-planner dispatches a governance phase in the SAME run as the capability phases it mechanizes, rather than after.
