> WO-086 (2026-09): historical — `ContractsLayeringRules` was deleted (commit 01847078): `EventEnvelope<TEvent>` has only internal constructors, so no construction path other than `EventEnvelope.Wrap` compiles and no rule is needed. The generic-arity `Newobj` technique below is still a valid reference. `NoDirectEncryptedValueConverterInstantiationPredicate`, cited below as a precedent, no longer exists.

`SK.00.EventEnvelopeConstructionGuard` (WO-054 P-350, 07.Messaging's gold-standard review) prohibits direct construction of `04.Contracts`'s `EventEnvelope<TEvent>` (namespace `SharedKernel.Contracts.Events`) outside its own mandated `EventEnvelope.Wrap<TEvent>()` factory. Motivated by a real, confirmed defect: `07.Messaging`'s shipped `MassTransitEventPublisher.PublishEnvelope<TEvent>` builds the envelope via a raw object initializer and never populates `TenantId` (WO-052/P-331), silently violating the type's own XML-doc-mandated construction contract.

**Design decisions (reusable precedent for any future "one correct construction path" rule on a generic record type):**

1. **No new SK ID.** Closest structural analog is `PresentationLayeringRules.NoDirectProblemDetailsConstructionOutsideWebApi` (WO-031 P-199) — a sealed/record wire-format type, exactly one legitimate construction site, no compiler-lowering ambiguity, `Newobj` IL-opcode detection, caller-controlled package exclusion — not SK0013/SK0020 (the phase input's own cited precedents), which are Roslyn analyzers for a different detection shape. Rule of thumb confirmed again: the phase input's own "mirrors X/Y/Z" framing does not dictate the technique — check which sibling is *structurally* closest, and prefer the NetArchTest/Mono.Cecil route whenever the acceptance criteria say "real compiled assemblies" (that phrase is this domain's own idiom for the IL technique, distinct from "real-source audit," which signals a Roslyn analyzer).

2. **New class, not a bolt-on.** Created `ContractsLayeringRules` (new static class) rather than adding a fifth predicate to the existing `ContractsPurityRules`. `ContractsPurityRules` governs `04.Contracts`'s own internal purity (self-referential); this rule governs how *other* assemblies must construct one of its types (boundary-protection) — the same direction `PresentationLayeringRules`/`CommunicationLayeringRules`/`MessagingArchitectureRules` already established under a `{Domain}LayeringRules` name. Don't conflate self-purity rules and boundary-misuse rules into one class just because they share a domain number.

3. **Generic-Newobj matching technique, refined.** For a `Newobj` targeting a generic type (`EventEnvelope<TEvent>`), Mono.Cecil's `TypeReference.Name` on the `GenericInstanceType` returns the simple name *undecorated* by the closed type argument (e.g. "EventEnvelope\`1", arity-suffixed but not `<OrderPlacedEvent>`-suffixed) — confirmed precedent already existed in `NoDirectEncryptedValueConverterInstantiationPredicate` (`DeclaringType.Name.Contains("EncryptedValueConverter")`), just not previously called out as "the generic-Newobj technique." This phase refined it to an exact `Namespace`+`Name` pair (not a bare `Name` substring) because "EventEnvelope" alone is a more collision-prone simple name than "EncryptedValueConverter."

4. **First constructor-arity discriminator on a generic-Newobj predicate.** `EventEnvelope<TEvent>` is a `sealed record` with only `required ... { get; init; }` properties (no positional parameter list) — it synthesizes a public **parameterless** constructor (used by object-initializer syntax, the fire condition) *and* a separate **one-parameter** copy constructor (used by `with` expressions on an already-`Wrap`-constructed instance). Added `MethodReference.Parameters.Count == 0` as a third condition specifically to exclude the copy-constructor path — a `with` expression mutates an existing legitimately-constructed envelope, it doesn't fabricate new envelope identity from scratch. **Reusable lesson:** before writing a Newobj-based construction-path predicate against any `sealed record` with only `init` properties (no positional params), check whether the record has legitimate `with`-expression usage anywhere downstream — if so, the parameterless-vs-copy-constructor parameter-count split is required, or the rule will false-positive on `with`.

5. **Structural (not policy) non-detection for the legitimate call path.** A caller that legitimately invokes `EventEnvelope.Wrap<TEvent>()` never needs an exemption at all — its own compiled IL contains only a `Call`/`Callvirt` to `EventEnvelope.Wrap`, never a `Newobj` targeting `EventEnvelope<TEvent>`; the actual `newobj` lives inside `SharedKernel.Contracts.dll`'s own `Wrap<TEvent>` method body, a different assembly. This is the same *class* of self-exemption as `NoDirectEfPropertyUsagePredicate`'s `Expression<TDelegate>`-lowering exclusion, but a different *mechanism* (cross-assembly IL locality vs. compiler expression-tree lowering) — document which mechanism applies, don't just cite the precedent by name.

6. **Split GATING status — a first for this file.** Every prior `*TopologyRules`/`*PackageHygiene` GATING dependency in this domain waited entirely on the dependency landing before real-assembly verification could run at all. Here, because the motivating defect is *already live* in shipped `07.Messaging` code (not a not-yet-built package), the **fire-path** real-assembly test (point the rule at the current, uncorrected `SharedKernel.Messaging.MassTransit.dll`) is non-gating and can run immediately — it's expected to fire, proving the rule catches the real defect. Only the **pass-path** re-verification (after `07.Messaging`'s P-340 ships `EventEnvelope.Wrap<TEvent>()`-based construction) is GATING. **Reusable pattern:** when a governance phase's motivating defect is already shipped (not merely a future risk), always check whether a real-assembly fire-path proof can run *before* the fix lands — it's strictly stronger evidence than a contrived fixture and doesn't need to wait on the dependency.
