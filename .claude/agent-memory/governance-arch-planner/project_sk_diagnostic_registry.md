## Block conventions

- **SK0001–SK0030**: general SharedKernel coding patterns (mix of Roslyn analyzers and NetArchTest ICustomRules, sequential)
- **SK0031–SK0199**: reserved for future sequential general-purpose rules; next is SK0031
- **SK0201–SK0299**: EF Core / multi-tenancy domain block; next is SK0203
- **SK0301–SK0399**: encryption subsystem block; next is SK0305
- **SK0701–SK0799**: messaging-domain block (domain 07); next is SK0709
- Never backfill gaps between blocks. Never reuse a published ID even if a rule is renamed.
- **Not every new rule consumes an ID.** A `NetArchTest`/`ICustomRule` predicate scoped to a single package's own "prevent this exact regression" concern (e.g. `EfCorePackageHygieneRules`'s four predicates, `RedisTopologyRules`, `StorageTopologyRules`, `WorkflowTopologyRules`) routinely ships with **zero** SK ID — this is an established, deliberate pattern in this domain, not an oversight. Only assign a new ID when the rule is either (a) a genuine Roslyn analyzer (source-level, per-compilation-unit), or (b) a platform-wide `ICustomRule` with no natural single-package home. When in doubt, check whether the rule's closest sibling in the same `*Rules` class already carries an ID — if the siblings carry none, don't mint one for consistency's sake alone.

**Why:** Tracking this prevents ID gaps, reuse, and block collisions. Block numbers follow the domain number (02xx = domain 02 EfCore/multi-tenancy, 03xx = encryption subsystem, 07xx = messaging domain). The 07xx block was introduced in WO-020 P-123; extended to SK0705–SK0708 in WO-021 P-133.

**How to apply:** Before assigning a new SK ID, verify this registry — and also grep the real `00.Governance/CLAUDE.md` diagnostic registry, since this memory file can lag a phase or two behind (it has, more than once: SK0024/SK0025 from WO-044 were never recorded here before WO-045 needed the next slot; SK0028–SK0030 from WO-046/WO-049 were likewise missing until this 2026-07-30 correction). Use SK0031 for the next general-purpose rule, SK0203 for the next multi-tenancy rule, SK0305 for the next encryption rule, SK0709 for the next messaging rule. Update this memory file whenever a new rule is assigned.

**WO-051 P-327 (`EfCorePackageHygieneRules.NoDirectEfPropertyUsageInEfCoreAssembly` — zero new SK ID):** Confirms the "not every new rule consumes an ID" pattern above with a concrete example. The phase input's own motivating comparison cited SK0013 (raw-`HttpClient`) and SK0020 (ad hoc-logging) — both platform-wide Roslyn analyzers — but the actual design chosen was a fourth `ICustomRule` predicate added to the existing `EfCorePackageHygieneRules` class (whose other three predicates all carry no SK ID), because the rule is scoped to a single package (`SharedKernel.Persistence.EfCore`) and its detection technique (Mono.Cecil `Call`/`Callvirt` opcode-presence on `Microsoft.EntityFrameworkCore.EF::Property`) naturally, structurally distinguishes the bug shape (direct executable-code invocation) from the platform's one legitimate usage (inside a `HasQueryFilter(Expression<Func<T,bool>>)` lambda, which the C# compiler lowers to `Expression`-builder calls with no `Call` opcode against `EF.Property` at all) — a distinction a Roslyn analyzer would have to reconstruct manually via `SemanticModel.GetTypeInfo(lambda).ConvertedType`. **Reusable lesson:** when a "prevent this exact regression" rule is scoped to one package AND the IL-opcode-presence technique can exploit a compiler-lowering distinction the source syntax alone doesn't expose, prefer the NetArchTest/Mono.Cecil route over a Roslyn analyzer, even when the motivating precedent cited in the phase input is itself a Roslyn analyzer. This phase is also the platform's second "identical defect class recurred despite a documented fix" escalation (first was SK0012/`ReflectionExemptionRegistry`, P-147/P-153/P-240) — first occurrence P-105 (`EfReadRepository.GetByIdsAsync`), second P-316 (`TenantedRepository`). **Key design decision (P-153):** SK0012 is a NetArchTest ICustomRule predicate, NOT a Roslyn analyzer. Reason: MethodInfo.MakeGenericMethod is called at runtime on a variable — there is no compile-time syntax pattern to detect reliably. IL inspection (Mono.Cecil Call/Callvirt opcode name match on "MakeGenericMethod") is the only reliable detection mechanism. This is the first sequential SK rule that is NOT a Roslyn analyzer — all prior SK0001–SK0011 were Roslyn analyzers.

**Key design decision (P-159):** SK0013 RawHttpClientConstructorInjection is Roslyn syntax-only (no SemanticModel) — "HttpClient" as a simple name is sufficiently unique within production code; the two exemptions (DelegatingHandler base class, SharedKernel.Communication.Rest namespace) are both syntax-checkable without semantic model. The hardcoded URI guard (assigned in the same P-159 phase spec) was deliberately kept as documentation-only: detecting URI assignment to typed-client BaseAddress or GrpcChannel config requires semantic model type resolution on the assignment target, with unacceptable false-positive risk across legitimate URI construction patterns.

**WO-039 P-240 (ReflectionExemptionRegistry's first real entry):** No new SK ID. `ReflectionExemptionRegistry` (SK0012's sole exception mechanism, introduced empty in WO-024 P-153) gained its first real registration — `SharedKernel.Application.DomainEvents.MediatRDomainEventDispatcher`'s `MakeGenericMethod` call site (inside `PublishSingle`'s `ConcurrentDictionary.GetOrAdd` factory delegate), registered pre-emptively so a future phase can safely point `ReflectionGuardRules.NoMakeGenericMethodReflection` at the real `SharedKernel.Application` assembly. **Key Mono.Cecil/Roslyn gotcha discovered here, reusable for every future SK0012 exemption request:** a closure-free `static` lambda (e.g. `dict.GetOrAdd(key, static t => {...})`) is compiled by Roslyn onto a compiler-generated `<>c` singleton cache class nested inside the declaring type — NOT onto the declaring type directly. The Mono.Cecil-observed `TypeDefinition.FullName`/`MethodDefinition.Name` the registry actually keys on is shaped like `"Namespace.DeclaringType/<>c"` / `"<ContainingMethodName>b__{token}_{ordinal}"`, not the literal declaring-type/method-name pair a source-level reading suggests. Never hand-guess the ordinal — derive it empirically (red-then-green: point the rule at the compiled assembly with the exemption absent, read the exact names out of the failure message, then register). **Confirmed open gap (not yet fixed, flagged as a candidate follow-up WO):** `07.Messaging`'s `MassTransitEventPublisher.BuildPublisher` (the exact same closure pattern — in fact the precedent `MediatRDomainEventDispatcher`'s own exemption cites) and `MessagingBusBuilder.AddActivity` (`GetMethods().Single(...).MakeGenericMethod(...)`) are BOTH still unregistered in `ReflectionExemptionRegistry` and unverified against SK0012 as of 2026-07-03. Also corrected a standing inaccuracy: SK0012's CLAUDE.md note previously claimed "all production assemblies pass this rule" — that was never actually verified by running the rule against every real assembly; true only in the narrow sense that P-147 fixed the one manually-discovered violation. Check this gap before assuming SK0012 is safe to wire into CI platform-wide.

**WO-040 P-248 (SK0017–SK0019, consumer-side marker-interface misuse):** Three new general-purpose IDs closing the LAST THREE "not mechanically enforced — code review must catch this" callouts in `05.Application/CLAUDE.md`'s Hard Violations section (the fourth callout from that same family, `typeof(TRequest).Name` short-name usage, was already closed by SK0016 in WO-038 P-235 — so this phase finishes what P-235 started). Key design decisions: (1) all three require `SemanticModel`-resolved `INamedTypeSymbol.AllInterfaces` — a `BaseList` simple-name check is insufficient because `ICommandBase`/`IQuery<TResponse>` are usually implemented transitively (e.g. `ICommand<TResponse> : ICommandBase`), not declared directly — making these the domain's 3rd/4th/5th semantic-model analyzers after SK0011 and SK0015; (2) interface matching uses `OriginalDefinition` + namespace-prefix (`"SharedKernel.Application"`) rather than exact assembly/type identity, specifically so analyzer test fixtures can declare their OWN fixture-local marker interfaces inside a matching-namespace code block in the same test compilation — no `ProjectReference` to the real `SharedKernel.Application`/`.Behaviors` assemblies needed, unlike SK0015 which needed the real MediatR NuGet package; (3) unlike SK0016 (trigger-IN scope), these three fire globally with NO namespace restriction — they are deliberately CONSUMER-side rules: the violation is a command/query type declaration, which only ever happens in a consuming microservice, never inside `SharedKernel.Application`/`.Behaviors` itself (which declares only generic pipeline-behavior classes, never concrete command/query types) — so the "zero false positive against 05.Application's own source" requirement is a structural/inspection argument, not a real-assembly architecture test; (4) abstract types are exempt (same as SK0009), so a generic abstract request base spanning multiple marker families behind a type parameter isn't prematurely flagged. Zero new `SharedKernel.ArchitectureTests` artifacts — pure Roslyn, `netstandard2.0`, no new NuGet dependency.

**WO-037 P-229 (CryptoIsolationRules / UnitOfWorkSeamRules):** No new SK ID assigned. First precedent in this domain for **narrowing an existing rule's exemption list in place** rather than minting a new ID when a platform-wide generalization is needed: SK0301 (DirectCryptoInDomainOrApplication)'s backing predicate `NoAesCipherInDomainOrApplicationPredicate` had its exemption narrowed from `{SharedKernel.Persistence, SharedKernel.Security}` to `{SharedKernel.Cryptography}` only — motivated by a hand-rolled `AesGcm` usage inside `SharedKernel.Persistence.*` (06.Persistence P-227's fix target) that SK0301 could never have caught because it was only ever invoked by the caller against `03.Domain`/`05.Application` assemblies, never against `06.Persistence` itself. The new platform-wide rule `CryptoIsolationRules.NoRawSymmetricCipherOutsideCryptography` shares identical exemption/trigger logic with the narrowed SK0301 predicate but is designed for invocation against every production assembly — SK0301 is a caller-scoped special case by construction, not a duplicate. Lesson for future phases: when a rule's exemption list turns out to be wider than the platform's actual single-legitimate-caller story, narrow the existing predicate's exemption rather than leaving stale wide exemptions that mask new violations in "exempt" namespaces. Also introduced `UnitOfWorkSeamRules.UnitOfWorkInterfacesRemainDistinct` — a negative-space/regression-guard `ICustomRule` (no fire-path precedent exists in the codebase; fixtures must be contrived) protecting the `IUnitOfWork` local-seam pattern between `05.Application.Behaviors` and `06.Persistence.Abstractions` from a future interface-merge or interface-inheritance "simplification". Depends on 06.Persistence P-227/P-228 (design-only as of 2026-06-30) for real-assembly verification only.
