> WO-086 (2026-09): `IRequestIdempotencyStore`/`IdempotencyBeginResult` (`05.Application.Behaviors`) and the messaging `IIdempotencyStore` were deleted; both are now `SharedKernel.Idempotency.Abstractions.IIdempotencyStore` keyed by `IdempotencyPurpose`, implemented by one `RedisIdempotencyStore` and one `EfCoreIdempotencyStore` (the message stores were merged in). The reservation-token lesson below still holds.

**What happened:** `05.Application.Behaviors` shipped a redesigned request-idempotency contract (`IRequestIdempotencyStore`: `TryBeginAsync(key, requestFingerprint, ct)` / `CompleteAsync(key, serializedResponse, ct)` / `ReleaseAsync(key, ct)`, returning an `IdempotencyBeginResult{Status, StoredResponse}` where `Status` is `Started`/`InProgress`/`Completed`/`FingerprintMismatch`) before either `05.Application.Behaviors` or `18.Idempotency`'s packages had published. This session migrated both `18.Idempotency` providers onto it as a clean rewrite — no shim, no `[Obsolete]`, since nothing downstream could be broken by a breaking change pre-publish.

**Why:** the old two-interface split (`IIdempotencyKeyStore.HasProcessedAsync`/`MarkProcessedAsync` + separate `IIdempotencyResponseStore`) exposed a check-then-act shape at the interface level and required response-replay detection via a runtime `is IIdempotencyResponseStore` pattern-match — awkward. The new single interface folds reservation, fingerprint-based reuse detection, and response replay into one atomic `TryBeginAsync` call.

**Scope of the rewrite (both providers):**
- `RedisIdempotencyKeyStore` → `RedisRequestIdempotencyStore`; `EfCoreIdempotencyKeyStore` → `EfCoreRequestIdempotencyStore`. Full protocol redesign — see [[reference_redis_reservation_protocol]] and [[reference_efcore_reservation_protocol]] for the exact commands/SQL.
- `RedisIdempotencyMessageStore`/`EfCoreIdempotencyMessageStore` (`IIdempotencyStore`, `07.Messaging.Abstractions`) — **untouched**. That contract never had a fingerprint/replay concept and the migration brief was explicit about leaving it alone.
- DI extensions (`Add*Idempotency`) simplified — no more double-registration trick (`services.AddScoped<RedisIdempotencyKeyStore>()` + two `AddScoped<Interface>(sp => sp.GetRequiredService<Concrete>())` calls) since there's only one interface now; a single `AddScoped<IRequestIdempotencyStore, Concrete>()` suffices.
- Both `README.md`s and `18.Idempotency/CLAUDE.md` updated (Domain Invariants 1/2/4/6/7 all touched by the contract change; Invariant 7's "two interfaces, one class" framing is now obsolete — replaced with "two contracts, two classes, unaffected by the interface count").

**A deliberate addition beyond the literal migration brief:** both rewritten stores added a **reservation-token guard** on `CompleteAsync`/`ReleaseAsync` — see [[reference_redis_reservation_protocol]] / [[reference_efcore_reservation_protocol]] for the mechanism. This closes a real race (a late confirm/release after the reservation already expired and a different caller reclaimed the key would otherwise corrupt that new caller's row) that this domain's own change history (the 2026-09-09 changelog entry in `18.Idempotency/state-map.md`, and `feedback_redis_test_ttl_must_not_borrow_shared_default.md`'s sibling investigation) had explicitly flagged against the *old* `MarkProcessedAsync` design but left unfixed as "worth a future look." Since the rewrite already touched every code path that gap lived in, fixing it now (rather than filing yet another follow-up) was the right call — confirmed correct via a dedicated concurrency test on each provider (`CompleteAsync_AfterReservationWasReclaimedByAnotherCaller_DoesNotCorruptTheNewOwner`).

**Test results:** `SharedKernel.Idempotency.Redis.Tests` 31/31 (up from 25/26 pre-migration — net-new: fingerprint-mismatch ×2, completed-replay, release ×2, stale-token-corruption), `SharedKernel.Idempotency.EfCore.Tests` 32/32, both against real Testcontainers Redis/PostgreSQL (Docker was available this session). Concurrency proofs (32-way parallel `TryBeginAsync`, tenant isolation, expiry reclaim, stale-token guard) all genuinely executed, not skipped.

**If you're implementing a similar "reserve → confirm-or-release with replay" contract for a future provider:** the reservation-token pattern (generate a fresh opaque token on the winning reserve, remember it per-scope, require it to match on every subsequent mutation) is the reusable technique here — it's what makes "did I actually win this row" a robust signal independent of clock resolution, and what makes late/stale confirm-or-release calls safe no-ops instead of silent corruption.
