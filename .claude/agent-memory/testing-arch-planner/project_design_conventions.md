**"Mock" requests get upgraded to deterministic in-memory fakes, never a mocking-framework substitute.**
Why: `SharedKernel.Testing` has a hard dependency-hygiene rule — zero NSubstitute/Moq/FluentAssertions/test-runner references in `SharedKernel.Testing.csproj` itself (only in the sibling `.SelfTests` project, which carries the Standard Test Package Set). Every fake implements the target interface directly in plain C#.
How to apply: if a phase input says "add a mock for X," design a `FakeX : IX` with settable properties/`SimulateFailure`-style toggles instead — this is the default translation, not a judgment call to re-litigate each time.

**Sibling capability folders (`Caching/`, `Domain/`, `Security/`, `Messaging/`, `Persistence/`, `Communication/`, `Application/`, etc.) never reference each other — even when two folders need functionally identical machinery.**
Concrete example (WO-040): `Application/ApplicationPipelineTestHarness` needed `ActivityListener`-based span capture, and `Communication/ActivityRecorder` already does exactly that. The rule still forbids the cross-reference — `ApplicationPipelineTestHarness` hand-rolls its own small `ActivityListener` wiring instead of depending on `ActivityRecorder`.
How to apply: when a new fake in folder A needs a capability another folder B already has, do NOT design a cross-folder reference "just this once" — either duplicate the small amount of logic locally (the standing precedent), or (only if the duplication would be large) flag it to arch-lead as a possible signal that the shared logic belongs in a lower, non-capability-specific location. For anything at the scale of a single helper class/listener, duplicate.

**A live `ProjectReference` from a consuming domain's `.Tests` project to `SharedKernel.Testing` does NOT by itself mean a net-new fake should be proven there.**
The domain's default rule is "prove a fake in the owning domain's `.Tests` suite where the interface's real implementation already has contract tests." But repeatedly across WO-029/WO-030/WO-040, the actual finding was: the reference exists in the `.csproj`, but zero `.cs` files in that project consume the new type (because it's net-new). In every such case the fake was routed to `SharedKernel.Testing.SelfTests` instead, with adoption into the owning domain's suite tracked as an explicit, undone cross-domain follow-up.
How to apply: always grep the actual `.cs` files of the candidate consuming `.Tests` project for real usage of the new type name — never assume routing from the mere existence of a `ProjectReference`. This has been true for `TestSharedKernelDbContext`/`AggregateRootFaker` (06.Persistence), `StaticTenantProvider`/`FakeUserContext`/`FakeTenantProvider` (12.Security), and `FakeUnitOfWork`/`FakeAuthorizationContext`/`FakeIdempotencyKeyStore`/`FakeIdempotencyResponseStore`/`ApplicationPipelineTestHarness` (05.Application, WO-040) — i.e. it is now the norm, not the exception, for a brand-new fake's first Tests-phase home to be `SelfTests` regardless of which domain "owns" the interface.

**When a real production interface can optionally implement a second capability interface, detected via a runtime `is`-check (e.g. `IIdempotencyKeyStore` optionally also `IIdempotencyResponseStore` in 05.Application.Behaviors, P-242), the fake MUST ship as two separate concrete types, never one type with a constructor flag.**
Why: C# interface implementation is a static, per-type fact — it can't be toggled at runtime, so a single flag-driven fake would make the `is`-check always pass or always fail regardless of the flag, silently breaking the test path the flag claimed to disable.
How to apply: whenever a phase input describes a fake for an interface with a documented "MAY additionally implement X for opt-in behavior" pattern, always design two fake types (base-only, and base+extension) rather than one configurable type. First applied to `FakeIdempotencyKeyStore`/`FakeIdempotencyResponseStore` (WO-040) — treat as the reference precedent for any future optional-capability interface.

**Before designing a new fake, always read the *owning* domain's live CLAUDE.md/source for the exact interface signature — including disambiguating same-named interfaces across domains.**
Concrete trap: `05.Application.Behaviors.IUnitOfWork` and `06.Persistence.Abstractions.IUnitOfWork` share a name but are unrelated single-member vs. multi-member interfaces; the root `CLAUDE.md` and `05.Application/CLAUDE.md` both explicitly call this out. A fake for one must never be assumed to satisfy the other, and its doc comment should say so explicitly.

**Before assuming a gap exists, audit this package's existing surface first.** Demonstrated repeatedly (P-226/WO-036's `CacheInvalidationBehavior` audit found `FakeCacheService` already fully sufficient with zero new code — only the `TracingBehavior` half was a genuine gap, closed by one small additive `ActivityRecorder` type). Grep existing types and their documented capabilities before designing something that looks new.

**"Design ahead of an upstream domain's schedule" has two distinct flavors — verify which one you're in by reading the actual `.cs` files on disk, not just the target domain's `CLAUDE.md`/`state-map.md` prose.** Soft flavor (P-226/WO-036's `ActivityRecorder`): the new fake needs only a literal value from the upstream domain (e.g. an `ActivitySource` name string), never a real compiled type — Core-phase implementation is NOT blocked even though the upstream capability is itself still design-only. Hard flavor (first hit at P-269/WO-043's `Storage/InMemoryFileStorage`): the new fake must `: IUpstreamInterface` against a real compiled type, and the upstream package (`08.Storage/SharedKernel.Storage.Abstractions.csproj`) turned out to have ZERO `.cs` files on disk despite a fully-authored `CLAUDE.md` describing its target interface. In the hard case: Design still proceeds fully (target shape sourced from the owning domain's `CLAUDE.md`, which remains authoritative regardless of code-shipped status); Scaffold may still add the `ProjectReference` (an empty-project reference always builds — it just resolves to nothing yet); but Core/Tests/Docs tasks needing the real type must be marked `⚑` Blocked (not `○` Pending) with an explicit Cross-Domain Dependencies row naming the upstream phase key that must land first (e.g. `08.Storage`'s `SK.08.Core`).
How to apply: whenever a new phase's fake needs `: ISomeUpstreamInterface`, always `Glob`/`Read` the actual upstream `.csproj` folder for real `.cs` files before assuming the interface exists in compiled form — a fully-written `CLAUDE.md` interface-contract block is not proof the code exists; that domain's own `state-map.md` Package Board phase label (`Design ○` vs `Core ●`) is a strong signal but verify the `.cs` files directly too, since prose can lag reality in either direction. Mark only the tasks that need the real type as `⚑`, not the whole phase.
Confirmed a SECOND time at P-276/WO-044 (`Search/InMemorySearchIndex<TDocument>` etc., against `09.Search/SharedKernel.Search.Abstractions`, also a genuinely empty `.csproj` at design time) — this is a recurring category for this domain, not a one-off. A useful tell that a whole domain is still Design-only: its own `state-map.md` Blocked/Cross-Domain-Dependencies section will often have ALREADY named the exact `16.Testing` fake/fixture it's waiting on (both `08.Storage` pre-WO-043 and `09.Search` pre-WO-044 did this) — read the upstream domain's own state-map first, it frequently does half the verification work for you, but still independently confirm the `.cs` file count yourself rather than trusting its prose alone.

**A container fixture (`Containers/`) almost never carries the hard blocker that an in-memory fake (any other folder) does, even for the exact same upstream domain in the exact same work order.** Why: every `Containers/` fixture in this domain's history (`PostgreSqlContainerFixture`, `RedisContainerFixture`, `RabbitMqContainerFixture`, `MinioContainerFixture`, and now `MeilisearchContainerFixture`/`ElasticsearchContainerFixture`) exposes only flat scalar connection properties (`ConnectionString`, or a small named set like `ServiceUrl`/`ApiKey`/`Nodes`) and takes NO `ProjectReference` to the domain whose real provider it stands in for — it doesn't need to `: ISomeInterface`, so it has nothing to compile against. An in-memory fake in a different folder (`Storage/InMemoryFileStorage`, `Search/InMemorySearchIndex<TDocument>`) DOES implement the real interface directly, so it DOES need the real compiled type. How to apply: when a work order bundles a container-fixture phase and an in-memory-fake phase for the SAME upstream domain (P-268+P-269 for `08.Storage`, P-275+P-276 for `09.Search`), expect the fixture half to be fully unblocked and the fake half to be hard-blocked if the upstream `.Abstractions` package is still empty — do not assume both halves share the same blocked/unblocked status just because they target the same domain.

**When three fakes in one new folder collectively cover a "primary generic interface + one or more secondary non-generic interfaces" shape (mirrors real production DI, where all three interfaces for one provider share internal state under a single root registration), the test-double versions should be designed as fully INDEPENDENT types with no constructor/type coupling between them, breaking from how the real production types are wired.** First applied at P-276/WO-044's `Search/` folder (`InMemorySearchIndex<TDocument>` generic-per-document-type vs. `InMemorySearchIndexProvisioner`/`InMemorySearchProviderDescriptor` non-generic). Why: the generic per-type fake is overwhelmingly the one most tests need in isolation (a handler test depending on just `ISearchIndex<TDocument>`); forcing it to take a non-generic collaborator dependency for a capability (rebuild-orchestration/pre-flight-validation) most of its callers never touch adds ceremony without adding real fidelity — even the real interfaces' own `RegisteredIndexes`/`Validate`/`ProbeAsync.DocumentCount` are definition-derived, not live-document-store-derived, so a shared backing registry wouldn't buy back the fidelity lost by the coupling anyway. How to apply: when a similar "one generic + N non-generic sibling interfaces from the same provider" shape appears again, default to three (or N+1) independent sealed fakes, each directly `new`-able/constructible on its own, with an explicit test-setup helper (e.g. `.RegisterIndex(name, definition)`) for a test that specifically wants two of them to agree on the same underlying data — never force the coupling by default.

**The "design-ahead-of-schedule hard blocker" has a THIRD flavor beyond soft/whole-folder-hard: PARTIAL blocking within one folder, and whether it's partial or whole-folder depends on WHERE in the upstream package the gap falls, not on how big the gap is.** First hit at P-300/WO-049 (`Cryptography/`+`FeatureManagement/`, both `01.Core`): `SharedKernel.Cryptography` was already fully `Published` with 7 of 8 target interfaces shipped, so only the ONE fake needing the missing 8th interface (`FakeContentHasher` → `IContentHasher`, not yet added) was blocked, plus anything that transitively references it (the composite `AddFakeCryptography()` DI bundle). But `FeatureManagement/`'s single fake (`FakeFeatureManager` → `IFeatureManager`) was blocked in its ENTIRETY even though the interface already ships 2 of its eventual 4 members (the boolean `IsEnabledAsync` pair) — because the fake must implement the interface in FULL to compile, and C# gives no partial-interface-implementation escape hatch.
Why this matters: don't assume "the upstream package is mostly done" implies "only the missing piece is blocked" — check whether the missing piece is (a) a whole separate interface a specific fake needs (→ only that fake + its transitive dependents block), or (b) a missing MEMBER on an interface some fake must implement completely (→ that whole fake blocks, full stop, regardless of how many sibling members already exist).
How to apply: when auditing an upstream package for a design-ahead-of-schedule fake, don't just check "does the package exist" or "is the domain's Design phase ratified" — check at the GRANULARITY of exactly which type/member each planned fake needs, then mark `⚑` Blocked at that same granularity. A folder with N fakes against N different interfaces from a partially-shipped package will likely be partially blocked; a folder with fakes against interfaces that must be implemented in full will be blocked or unblocked as whole units per fake.

**A fake's unconfigured/default return value must mirror the SPECIFIC target interface's own documented contract, not copy a sibling fake's precedent by reflex — even within the same fake, two methods can legitimately default in opposite directions.** First hit at P-431/WO-064's `InMemoryWebhookDispatcher`: `InMemoryMessageBus.RequestAsync` throws `InvalidOperationException` when no response handler is configured — an established, oft-cited precedent in this domain. But `IWebhookDispatcher.DispatchToSubscriptionAsync`'s own XML doc states a delivery failure is ALWAYS expressed as a returned `WebhookDeliveryResult` record, NEVER a thrown exception — copying `RequestAsync`'s throw-when-unconfigured shape onto this fake would violate the very interface contract the fake exists to satisfy. The fix was to default to a synthetic success result instead. Meanwhile the SAME fake's `DispatchAsync` (fan-out) defaults to an EMPTY result list — also non-throwing, but a different default value, because "zero configured subscriptions" is the honest empty-fan-out shape while "an unconfigured single delivery" reads more naturally as an assumed-successful no-op.
How to apply: before writing an unconfigured/default-return-value NOTE on a new fake, re-read the TARGET interface's own XML doc/remarks for an explicit statement about how failure/absence is expressed (return value vs. exception) — never assume the shape from another fake in this package, even a heavily-precedented one like `InMemoryMessageBus`. Two methods on the same new fake can legitimately default differently from each other if their own real contracts differ.

**When checking whether a new fake's target package is a "design-ahead-of-schedule" blocker, checking on the FIRST pass (before writing any task) can itself land on an already-mature, zero-blocker domain — this is now common enough to expect by default for any long-since-`●`-Published owning domain, not just a pleasant surprise found on a later confirmation pass.** Confirmed at P-431/WO-064 (`15.Integration`, first-ever check, zero blocker) following the same shape at P-335/WO-053 (`06.Persistence`) and P-391/WO-060 (`Security/`'s third extension) — three of the last four occurrences found no blocker at all on the very first on-disk check, versus the earlier P-269/P-276/P-284/P-288 run where every occurrence found at least a partial blocker that then had to clear over a subsequent pass.
How to apply: always `Glob`/`Read` the target `.csproj` folder's real `.cs` files before writing any Design task — do not assume a newly-requested capability implies the owning domain must be design-only just because this domain's history shows several hard-blocker examples; a domain that shipped its Core phase months ago (confirmed via its own `state-map.md` Package Board / Overall Progress, not merely its `CLAUDE.md` prose) is very likely to be a zero-blocker case on the first check.

**When a real production interface has multiple keyed DI registrations sharing one interface (e.g. `IAsymmetricSignatureService` registered unkeyed-default + `"Rsa"`-keyed + `"Ecdsa"`-keyed, all via `CryptographyServiceCollectionExtensions.RsaSignatureServiceKey`/`EcdsaSignatureServiceKey`), the fake's DI extension reuses those REAL string constants directly rather than redeclaring fake-only key strings.** First applied at P-300/WO-049's `FakeCryptographyServiceCollectionExtensions.AddFakeCryptography()`. Why: this is not a sibling-capability-folder reference (the constants live in the production abstraction package the fake already depends on, e.g. `SharedKernel.Cryptography`) — it's the difference between a test being able to swap `AddSharedKernelCryptography()` for `AddFakeCryptography()` with zero call-site changes (since `GetRequiredKeyedService<T>(RealKeyConstant)` still resolves) versus having to know two different key-string sets depending on whether the test is faked or real.
How to apply: whenever a new fake's DI extension mirrors a production registration that uses `.NET`'s keyed-service feature, always reuse the real package's own public key constants — never invent parallel fake-only ones, even though nothing stops you syntactically.

**When a phase's acceptance criteria names a root `CLAUDE.md` update, do not create a state-map task for it or attempt it — flag it in prose only.** First hit explicitly at P-300/WO-049 (acceptance criterion asking for a root "What Goes Where" row). The root `CLAUDE.md`/`state-map.md` are arch-lead's exclusive files (this agent's own jurisdiction section forbids touching them); the correct behavior is to note the gap in the Package Board note, the Overall Progress paragraph, and the Changelog entry — three places, each explicitly labeled "out of this domain's jurisdiction, explicitly not actioned" — so the omission reads as a deliberate, tracked handoff rather than a missed acceptance-criteria item.

**When a fake needs to key its backing store by an aggregate's Id, but the interface's own generic constraint doesn't expose `.Id` at compile time, take a caller-supplied `Func<TAggregate,TKey> idSelector` constructor parameter rather than embedding expression-tree or reflection-based property access.** First hit at P-335/WO-053's `Persistence/FakeRepository<TAggregate,TId>`: `IRepository<TAggregate,TId>`/`IReadRepository<TAggregate,TId>` constrain `TAggregate : IAggregateRoot<TId>`, and `IAggregateRoot<TId>` (via `IEntity<TId>`) is a documented ZERO-MEMBER marker — confirmed against both `03.Domain/CLAUDE.md` and the root `CLAUDE.md`'s own Hard Violations list ("`IEntity<TId>` is a marker interface with no `Id` property"). Production solves this identical problem via a compiled `Expression.Parameter`/`Expression.Property(param,"Id")`/`Expression.Lambda` tree built per closed generic type (`06.Persistence`'s own mandated pattern for primary-key equality against this exact constraint). A fake should NOT copy that machinery — it's production-grade complexity solving a problem a caller-supplied delegate solves more simply and transparently, mirroring `FakeDbConnectionFactory`'s own long-standing "caller-supplied delegate over hand-rolled substitute" precedent (P-182/WO-029).
How to apply: whenever a new fake's generic constraint matches a real interface's constraint exactly, and that constraint is a thin/marker interface lacking a member the fake's own internal bookkeeping needs, prefer a constructor-supplied selector delegate over reflection/expression-tree construction — reserve expression-tree techniques for the rare case where NO delegate could plausibly be supplied (there was no such case here).

**When production splits one conceptual capability into multiple concrete classes for an architectural/DB-topology reason that has no meaning for an in-memory fake, collapse the fake into ONE type implementing every relevant interface — do not mirror a split that only exists to serve infrastructure the fake doesn't have.** First hit at P-335/WO-053: production's `EfRepository<TAggregate,TId>` (write, `IRepository`)/`EfReadRepository<TAggregate,TId>` (read, `IReadRepository`) two-class split exists specifically to support `06.Persistence`'s own WO-053/P-338 read-replica routing (`IReadReplicaContextAccessor<TContext>`) — a distinction with zero meaning for a `ConcurrentDictionary`-backed fake with no replica concept at all. `FakeRepository<TAggregate,TId>` was designed as a SINGLE type implementing BOTH interfaces instead, which also has the free side benefit of guaranteeing trivial read-after-write consistency with no shared-backing-store wiring required between two separate fake instances.
How to apply: before mirroring a production package's own class-per-interface split, ask WHY that split exists in production — if the reason is a physical/infrastructure concern (replica routing, connection pooling, a different caching tier) rather than a genuine behavioral-contract difference, collapse it into one fake type and document the divergence explicitly, rather than assuming "production has two classes" implies "the fake needs two classes."

**A domain field with a `private set` (e.g. `ISoftDeletable.IsDeleted`/`DeletedOn`/`DeletedBy`) cannot be written by a fake without reflection — and this package should not introduce reflection just to flip one.** First hit at P-335/WO-053's `FakeRepository<TAggregate,TId>.DeleteAsync`: real production only mutates these via EF Core's `ChangeTracker.Entry(entity).CurrentValues[...]` mechanism (a privileged, ORM-internal write path, not plain reflection) or via Bogus's OWN reflection-based `Faker<T>.RuleFor` engine (which is how the EXISTING `Persistence/AggregateRootFaker<TAggregate,TId>` already "pre-configures `IsDeleted = false`" — Bogus's infrastructure does the reflection, not the fake's own hand-written code). Resolution: `DeleteAsync` ALWAYS performs a hard removal from the backing store, even for `ISoftDeletable` aggregates — no attempt to soft-delete-in-place. A test wanting to exercise soft-delete-filtered READ behavior `Seed`s a pre-built aggregate whose `IsDeleted` is already `true` (via `AggregateRootFaker`'s own Bogus `RuleFor` override capability, already present in the same folder) rather than expecting `DeleteAsync` to flip a flag.
How to apply: when a fake's write-side member would need to mutate a private-setter domain field to be fully faithful to production, do not add a reflection-based property-mutation helper to bridge the gap — perform the SIMPLER, honestly-divergent operation instead (here: hard delete), and document exactly how a test should achieve the finer-grained scenario using existing SETUP-time tooling (an existing Bogus-based faker) rather than the fake's own runtime behavior.

**When a fake needs to expose an upstream data-carrier object's fields for assertion, and some of those fields don't exist upstream yet, capture a REFERENCE to the real upstream instance rather than copying its fields into a separate DTO — this converts what looks like a hard compile blocker into a non-blocker.** First hit at P-352/WO-054: `InMemoryMessageBus`/`InMemoryEventPublisher` needed to expose `PublishContext`'s full field set for test assertion, including `.TenantId`/`.PartitionKey` (P-340/P-344, `07.Messaging`, design-only/not yet on the live `PublishContext.cs` at Design time — only `CorrelationId`/`CausationId`/`Headers` existed). Instead of writing accessor code that names `.TenantId`/`.PartitionKey` explicitly (which would fail to compile today), the fake's new `ShouldHavePublishedContext<T>()`-shaped accessors simply return the real, already-populated `PublishContext` INSTANCE the fake captured during dispatch. Because the fake never writes the not-yet-existing member names anywhere in its own source, the accessor compiles and ships TODAY, and the moment `07.Messaging` adds `.TenantId`/`.PartitionKey` to the live type, a consuming test can read them through the SAME accessor with zero further `16.Testing` code changes or redeploys.
Why this matters: this is a NEW sub-flavor of the established design-ahead-of-schedule taxonomy (soft/whole-folder-hard/partial-at-member-granularity, see the entries below) — it demonstrates that even a "partial blocking at member granularity" situation can sometimes be avoided ENTIRELY for the fake's own Core-phase code, if the fake's job is to expose/relay a real upstream object rather than to independently reconstruct or validate its individual fields. The blocking, when it exists at all, moves downstream to whatever TEST FILE must write the specific not-yet-existing member names by name to prove them (T-74 in this case) — Core-phase implementation and most Tests-phase coverage (propagator-application symmetry, `CorrelationId`/`Headers` round-trip) proceed fully unblocked.
How to apply: whenever a new fake's job is to record/relay/echo a real production data-carrier type (a context object, a request/response envelope, a mutable builder) rather than to independently implement business logic over its fields, prefer capturing and returning the REAL instance over copying named fields into a fake-owned DTO — check first whether the upstream type is a class your fake can hold a reference to (not a struct requiring a snapshot, not an interface requiring wrapper logic) and whether the fake's job is genuinely passive relay rather than active validation/transformation of those fields. When it applies, this technique should be treated as the default design over field-by-field duplication — it's simpler code AND it minimizes blocking on upstream schedule.

**When a real production abstraction gains a new `IdentityKind`-style discriminator/enum member that production models via a SEPARATE immutable sentinel class (e.g. `12.Security`'s `SystemUserContext`, a singleton peer of `AnonymousUserContext`), the fake does NOT need a matching separate sentinel type if the existing fake is already a mutable, settable-property class.** First hit at P-374/WO-057: `12.Security` added `IUserContext.IdentityKind` (`Anonymous`/`User`/`ServicePrincipal`/`System`) and shipped a new immutable `SystemUserContext` singleton to represent the `System` case in production DI. `FakeUserContext` did NOT get a matching `FakeSystemUserContext` — instead it just gained a settable `IdentityKind` property (default `User`), and a test wanting a "system context" fixture writes `new FakeUserContext { IdentityKind = IdentityKind.System }` directly. Why: production needs a separate immutable sentinel because its `AnonymousUserContext`/`SystemUserContext` are DI-registered fallback singletons with fixed, non-configurable field values — but a fake test double already IS the "configure whatever fields you want" mechanism, so adding a second fake type would only duplicate `UserId`/`Roles`/`Claims`/`IsAuthenticated` for zero behavioral gain.
How to apply: when a real domain adds a new enum-discriminated identity/state value backed by a NEW dedicated immutable production sentinel class, check whether this package's existing fake for that interface is already a mutable/settable-property class before reflexively designing a matching new fake type — if yes, just add the discriminator as a new settable property on the existing fake and document the "construct it directly, no dedicated type" convention in a NOTE block, don't mirror production's class-per-sentinel shape.

**A same-named-fake naming collision across two unrelated real interfaces (already an accepted platform fact, per the `IUnitOfWork` precedent) requires cross-referencing BOTH types' XML docs — including retroactively editing the EARLIER-shipped type, not only the new one.** First hit at P-335/WO-053: `Persistence/FakeUnitOfWork` (new, implements `06.Persistence.Abstractions.ITransactionalUnitOfWork`) collides by simple name with the ALREADY-SHIPPED `Application/FakeUnitOfWork` (P-244/WO-040, implements `05.Application.Behaviors.IUnitOfWork`) — disambiguated only by namespace. The Docs-phase task for the NEW type explicitly also requires adding the cross-reference to the OLD type's doc comment, since the collision only becomes a real, doc-discoverable fact once the second same-named type exists — the first type shipped with no way to know a collision was coming.
How to apply: whenever a new fake's name collides with an existing one in a different namespace, the Docs-phase task list must include a small, explicit, additive edit to the EARLIER type's file too — never just the new one — so a reader who lands on either type first discovers the other.

**"Test-fixture builder" is a distinct design category from "fake," and it justifies a DIFFERENT (looser) cross-package reference footprint for the SAME target folder than the folder's existing fakes carry.** First hit at P-391/WO-060: `Security/`'s existing scope lock says "references `SharedKernel.Security.Abstractions` only, never `.Oidc`/`.ApiKey`/`.Mtls`" — that rule exists because `FakeUserContext`/`FakeTenantProvider`/`SecurityTestContextBuilder` FAKE the abstraction (`IUserContext`) and must stay provider-agnostic to do so honestly. But a request to test-support `12.Security`'s WO-060 hardening (DPoP `ath` binding, mTLS default posture, API-key rotation) is NOT a request to fake an abstraction at all — DPoP/mTLS/API-key-rotation are exclusively `.Oidc`/`.Mtls`/`.ApiKey` concrete-provider concerns with zero `SharedKernel.Security.Abstractions` surface. The correct design is a BUILDER that constructs INPUT DATA (a proof JWT, an X.509 certificate, a set of rotation-window key strings) for a CONSUMING SERVICE's own test to feed into the real provider's real validation logic — never a fake `: ISomeProviderInterface`. Because the builder never implements or invokes the concrete provider's own types, it can stay BCL-only (`System.Security.Cryptography`/`.X509Certificates`/`System.Text.Json`) with ZERO `ProjectReference` to the provider package, even though its entire purpose is exercising that provider's behavior — which also means it carries NO cross-domain compile-time blocker, a first in this domain's 12-occurrence "design-ahead-of-schedule" history.
How to apply: before reflexively extending an existing scope-locked folder's dependency footprint to satisfy a new request, ask whether the request is "fake this abstraction" (needs the abstraction/interface, may need the concrete provider's real member signatures to mirror faithfully) or "build a realistic input fixture for a concrete-provider's own validation logic" (needs only the WIRE-LEVEL SHAPE of what that provider consumes — a JWT string, a certificate, a plain string — never the provider's own compiled types, since the fixture is meant to be fed to code OUTSIDE this package). The second category should default to BCL-only construction and explicitly documents this in a SCOPE LOCK note so it isn't mistaken for scope creep on the folder's existing rule. When targeting internal/unreachable production validation logic (e.g. `DpopProofValidator` is `internal` to `SharedKernel.Security.Oidc`), lean into producing a genuinely well-formed, cryptographically REAL fixture (real signature, real cert chain) with ONLY the specific claim/property under test deliberately corrupted — this proves the fixture exercises genuine rejection logic in the consumer's own integration test, not a strawman, and BCL primitives (`ECDsa`, `CertificateRequest`, `CertificateRevocationListBuilder`) make this no harder than a fake/plausible-looking stand-in.

**A new blocker flavor beyond "empty package" and "member missing on an interface": a MATURE, fully-referenced interface whose COMPILED SIGNATURE has not yet caught up to a design-locked breaking change.** First hit at P-502/WO-081: `Cryptography/FakeSymmetricEncryptionService`/`FakeAsymmetricKeyProvider`/`FakeAsymmetricSignatureService` all implement real `01.Core` interfaces (`ISymmetricEncryptionService`, `IAsymmetricKeyProvider`, `IAsymmetricSignatureService`) that are shipped, referenced, and mature — but `01.Core`'s own `SK.01.P491`/`P492`/`P493` had only design-locked (every `D-*` task `●`) a BREAKING signature change to those same interfaces, with zero `C-*`/`P-*` implementation yet. A fake that must implement the interface's NEW target shape (a required `associatedData` parameter, an async method replacing a sync one) literally cannot compile until the upstream repack lands — the interface being "already referenced" does not help, because the OLD compiled signature is what's actually on disk today.
How to apply: when a fake's migration targets a signature change (not a missing type, not a missing member on an otherwise-stable interface) documented only in the upstream domain's design-locked `state-map.md` prose, mark Core/Tests/Docs/Published `⚑` Blocked exactly like the "empty package"/"missing member" flavors — re-verify by reading the actual interface `.cs` file for the OLD vs. NEW signature shape, not by checking whether the package/`ProjectReference` exists (it already does). Design/Scaffold still proceed fully, since Scaffold needs no new reference and Design sources its target shape from the owning domain's ratified prose regardless of code-shipped status, per this domain's long-standing convention.

**When a real interface's OWNERSHIP CONTRACT for a returned disposable resource changes (from "unspecified" to an explicit "not caller-owned"), a fake's pre-existing defensive fresh-clone-per-call behavior must be REVERSED to cached-instance-reuse — the old defensive behavior actively HIDES the exact regression the new contract exists to catch.** First hit at P-502/WO-081's `FakeAsymmetricKeyProvider`: under the old `IAsymmetricKeyProvider` contract, returning a fresh `RSA`/`ECDsa` clone on every call (so a caller's `Dispose()` never invalidated the cached original) was a reasonable defensive choice. Once `01.Core`'s `SK.01.P493` made "the returned instance is NOT caller-owned" an explicit, tested contract (fixing a real `RsaSignatureService`/`EcdsaSignatureService` defect where they used to wrongly dispose a provider-owned key), the SAME fresh-clone behavior became actively harmful: it would make a caller-side dispose-then-reuse regression invisible forever, since the next call always hands back a brand-new, never-disposed clone regardless of what happened to the previous one. The fix: the fake caches and returns the SAME instance per key across calls, so a disposal regression surfaces immediately as `ObjectDisposedException` on the very next use within the SAME test.
How to apply: whenever an upstream interface's XML docs gain a new explicit ownership statement about a returned disposable/mutable resource, re-examine whether this package's existing fake's DEFENSIVE behavior (cloning, snapshotting, isolating) was built for the OLD, unspecified-ownership world — if so, that defensive behavior may now be masking exactly the regression the new contract was written to prevent, and should be reversed to let the regression surface naturally inside a consuming test, not merely updated to "still compile."

**A fake should NOT reimplement a capability GATE (a conditional throw/behavior-branch keyed off a dependency's own identity/marker) that belongs to REAL production code under test — instead, design the fake's DEPENDENCIES so a downstream test can compose them with the REAL gated type and prove the gate fires or doesn't.** First hit at P-502/WO-081's P-492 `ISynchronousEncryptionKeyProvider`/`EncryptionKeyProviderCapabilities.IsGenuinelySynchronous` gate: the gate lives inside `AesGcmEncryptionService` (real `01.Core` production code, exercised in every downstream domain's own test suite), not in the abstract `ISymmetricEncryptionService` contract. Rather than teaching `Cryptography/FakeSymmetricEncryptionService` to reimplement the same `NotSupportedException`-throwing logic internally, the design instead ships TWO honestly-differentiated `IEncryptionKeyProvider` fakes — one marked `ISynchronousEncryptionKeyProvider` (an honest claim, since it performs no real I/O), one deliberately unmarked and genuinely `await Task.Yield()`-async (representing a KMS-style provider) — so a downstream test constructs the REAL `AesGcmEncryptionService` against either one and observes the gate's real behavior directly.
How to apply: when a new fake's owning interface sits behind a real production TYPE that gates behavior based on a DEPENDENCY's marker/capability (not the interface itself), do not duplicate the gate inside a fake implementation of that interface — instead design the fake's dependency-shaped types (the thing the gated type actually depends on) to honestly represent both sides of the gate, and let a downstream test compose them with the REAL gated production type. This keeps the test proving genuine production logic rather than a `16.Testing`-owned reimplementation of the exact code under test — reserve gate-reimplementation for cases where NO real production type is reasonably reachable from a downstream test (not the case here, since `AesGcmEncryptionService`/`CachedEncryptionKeyProvider` are both public, referenced `01.Core` types).
