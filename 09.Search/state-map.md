## Phase: Design <!-- phase-key: SK.09.Design -->

> Lock every interface shape, model record, filter-AST node, error factory, options contract, and DI extension signature in `09.Search/CLAUDE.md` before any implementation begins — the `08.Storage` precedent, where the full nine-member `IFileStorage` contract was ratified ahead of Scaffold and never renegotiated. Covers P-272 (Abstractions contract finalization, D-01–D-15), P-273 (`.Meilisearch` provider design, D-16–D-21), and P-274 (`.ElasticSearch` provider design, D-22–D-28). P-273/P-274 depend on P-272's contract being locked first. The governing rule for every task in this phase: **`SharedKernel.Search.Abstractions` contains no type that either provider cannot implement completely and correctly** — if implementing a member would require one adapter to throw, degrade, approximate, or no-op, that member does not belong in Abstractions.

**Design (Abstractions contract finalization, P-272) — D-01 through D-15:**

| ID | Task | Package(s) | State |
| --- | --- | --- | :---: |
| D-01 | Ratify `ISearchDocument` — a single `string DocumentId { get; }` member, self-supplied by the document type. No reflection, no `[Key]` attribute scan, no convention-based `Id` discovery (the platform's `ILoggableRequest<TResponse>` / `ICacheableQuery.CacheKey` / `IInvalidatesCache.CacheKeysToInvalidate` self-supplied-surface pattern). Lock the three contract notes: (a) **charset — the strictest engine is the contract**: `DocumentId` must match Meilisearch's constraint of `A-Z`, `a-z`, `0-9`, hyphen and underscore only, rejected with `SearchErrors.InvalidDocumentId` before any I/O on **both** providers; (b) stability — the id is the upsert key on both engines, so an unstable id silently produces duplicates instead of updates; (c) **primitive-members-only hard rule** — implementations expose only `string`/numeric/`bool`/`DateTimeOffset`/`Guid` and collections thereof, because the Meilisearch SDK declares its `JsonSerializerOptions` as `internal` and offers no seam for a `JsonSerializerContext` or custom converter, so a `StronglyTypedId<TValue>` member round-trips on the ElasticSearch path and does **not** on the Meilisearch path. Record that (c) is documentation plus code review only — a downstream consumer's document types are outside this repo's architecture-test reach | SharedKernel.Search.Abstractions | `●` |
| D-02 | Design `ISearchIndex<TDocument>`'s write surface — `IndexAsync`, `IndexManyAsync`, `DeleteAsync`, `DeleteManyAsync`, `DeleteByFilterAsync`, `ClearAsync`, `WaitUntilSearchableAsync`, plus the `string IndexName { get; }` property. Lock four decisions: (a) **`SearchWriteConsistency` is a required, non-defaultable parameter on every write** — a bare `Task IndexAsync(doc, ct)` is dishonest on both engines in two different ways (ES returns once durable in the translog but not searchable until the next refresh; Meilisearch returns only an *enqueued* `taskUid` behind a single **global sequential** queue where a different index's backlog delays yours); there is no nullable `SearchWriteOptions` to pass `null` to, because an enum value is one token and self-documenting; (b) `IndexAsync` is **upsert-only** keyed on `DocumentId` — no Create-vs-Update split, since Meilisearch has no create-if-absent primitive and at-least-once upstream delivery makes the distinction meaningless; (c) `DeleteByFilterAsync` takes `TenantScope` as a **mandatory separate parameter**, never inside the `SearchFilter` tree — a dropped tenant clause on a DELETE is cross-tenant data destruction; (d) `WaitUntilSearchableAsync` is the deferred barrier for `Accepted` writes (one barrier after N batches instead of N barriers) and **must not** be used to implement read-your-writes on a request path | SharedKernel.Search.Abstractions | `●` |
| D-03 | Ratify the deliberate **absence** of any optimistic-concurrency member on the write contract. ElasticSearch has external versioning and `if_seq_no`/`if_primary_term`; Meilisearch has nothing comparable and is last-write-by-arrival-order. Rather than carry a `Version` member one adapter silently ignores — the only genuinely silent degradation any candidate design contained — the contract carries **none** and states the requirement instead: a sync pipeline feeding these methods must guarantee ordering upstream by partitioning the change stream on `DocumentId`. Documented, not enforced, and the domain's sharpest sharp edge; ES external versioning stays reachable through `IElasticSearchRawClientAccessor` | SharedKernel.Search.Abstractions | `●` |
| D-04 | Design `ISearchIndex<TDocument>`'s read surface — `SearchAsync(SearchRequest, TenantScope, ct)`, `GetAsync(string documentId, TenantScope, ct)`, `CountAsync(SearchFilter?, TenantScope, ct)`. Lock: faceting is **not** a separate interface (`SearchRequest.Facets`/`.NumericFacetStats` are plain members on the request the caller already built, and counts return on the `SearchResults<TDocument>` the caller already has, so the briefed common case — index an aggregate, then run a filtered + faceted + paged search — costs exactly one injected dependency and zero extra types); `GetAsync` is implemented as a **filtered single-hit search, not a raw get**, whenever the index definition declares a `TenantField`, so a caller cannot read another tenant's document by guessing an id, and a miss returns `SearchErrors.DocumentNotFound` — never `null`, never a thrown exception; `CountAsync` is exact on both engines (ES `_count`; Meilisearch `page`/`hitsPerPage`) and exists separately from `SearchResults.TotalHits` precisely because that value carries an accuracy qualifier and this one does not | SharedKernel.Search.Abstractions | `●` |
| D-05 | Design `ISearchIndex<TDocument>.EnumerateAsync(SearchFilter?, TenantScope, int batchSize, ct)` returning `IAsyncEnumerable<TDocument>` — **not** `Result`-wrapped. Ratify this as the domain's one documented exception to the Result-first rule, following the established streaming precedent (`06.Persistence` P-149's `IReadRepository.StreamAsync`, `08.Storage` P-265's `IFileStorage.ListAsync`): a transport failure mid-stream surfaces as `SearchStreamException` from `MoveNextAsync`, because `Result<IAsyncEnumerable<T>>` only reports the failure that happens before the first `MoveNext` and `IAsyncEnumerable<Result<T>>` is unusable at the call site. Lock two further notes: this is a **document walk, not a deep search** (Meilisearch `GET /indexes/{uid}/documents` offset+limit; ES `search_after` + PIT), so it is not subject to Meilisearch's `maxTotalHits` ceiling — which is why "iterate every matching document" is portable while relevance-ordered deep pagination is not; and **ordering is UNSPECIFIED** — stable within a single unmodified corpus and never to be relied upon, because id-ascending order is unverified for Meilisearch's `/documents` endpoint (T-26 verifies actual behaviour against real containers before any guarantee is strengthened) | SharedKernel.Search.Abstractions | `●` |
| D-06 | Design `ISearchIndexProvisioner` (non-generic, one per provider) — `EnsureIndexAsync(SearchIndexDefinition, ct)`, `IndexExistsAsync(string, ct)`, `DeleteIndexAsync(string, ct)`, `CutoverAsync(IndexCutoverRequest, ct)`, `ProbeAsync(string indexName, ct)`. Lock four decisions: (a) **why field declarations are on the neutral surface at all** — the one place the "thin abstraction" premise is compromised, and unavoidably so: Meilisearch *rejects* a filter on any attribute absent from `filterableAttributes` and a sort on any attribute absent from `sortableAttributes`, both being index *settings* applied ahead of time, while ES filters any mapped field at query time; if field roles were provider-private the identical `SearchRequest` would succeed on ES and 400 on Meilisearch; (b) `EnsureIndexAsync` is idempotent and **additive-only** — it never drops a field and never rewrites an incompatible mapping (ES cannot change a field's type in place, so a convergent "make it match" is unimplementable on one engine), returning `SearchErrors.IndexDefinitionConflict` instead, with staging → bulk-load → `CutoverAsync` as the remedy; it also writes `SchemaFingerprint` into index metadata for drift detection; (c) `CutoverAsync` is one neutral name over two mechanics with the asymmetry **normalised, not hidden** — ES issues a single `_aliases` request containing both the remove and the add (applied atomically, so `LiveIndexName` is an **alias**), Meilisearch calls `POST /swap-indexes` (so `LiveIndexName` is a real index name and the staging name still holds the *old* data afterwards), which is exactly why `IndexCutoverRequest.DeleteStagingAfterCutover` defaults to `true`; (d) `ProbeAsync` is a **primitive, not a health check** | SharedKernel.Search.Abstractions | `●` |
